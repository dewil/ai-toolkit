# claude-toolkit

Канон правил, агентов и bootstrap-промтов для проектов с [Claude Code](https://claude.com/claude-code).

> [!IMPORTANT]
> **Этот канон сильно персонализирован под меня** - мои правила, агенты, конвенции, привычки работы. Это не универсальный дистрибутив. Если хочешь такой же инструмент - обязательно **сделай свою копию и пройди первичную настройку под себя** (см. [Свой персональный toolkit](#свой-персональный-toolkit)), а не подключай свои проекты к моему канону. Подключишь к моему - приедут мои решения, и они тебе вполне могут не подойти.

## Зачем

Claude Code из коробки - чистый помощник без памяти о твоих привычках. Чтобы он вел себя предсказуемо в проекте, обычно приходится: написать правила поведения, объяснить конвенции, описать субагентов под типовые задачи, настроить память. На один проект это полдня; на каждый новый - те же полдня заново. А правила, отлаженные в одном проекте, не доезжают до остальных - опыт не копится.

`claude-toolkit` решает это так:

- Канон правил, агентов и скиллов лежит в одном месте - в этом репо.
- Новый проект бутстрапается одной фразой: Claude фетчит канон по HTTP, раскладывает по `.claude/`, спрашивает про тип проекта (кодинг / документация / управление / учеба / wiki) и докладывает специализированные файлы. Реестр накатанного хранится в `.claude/canon.yaml`.
- Существующий проект синкается с каноном: Claude сравнивает локальные снимки с upstream, показывает diff по каждому файлу, спрашивает "обновить?". Никаких симлинков и автоматических правок.
- Полезное, выработанное в конкретном проекте, можно вынести обратно в канон через upstream-pending брифы - проект сам соберет самодостаточный пакет для разработчика toolkit'а.

## Что это дает

- **Быстрый старт.** Новый проект готов к работе за минуты, сразу с типографикой, агентами и правилами под свой тип - без копирования снипетов из других проектов.
- **Накопление опыта.** Найденное в одном проекте правило переезжает в канон и через sync доходит до всех остальных. Эффект растет с числом проектов.
- **Согласованность.** Claude ведет себя одинаково во всех твоих проектах - одни кавычки, одни агенты, одни конвенции работы с документами и кодом.
- **Специализация под тип.** Кодовый проект получает правила тестов и обработки ошибок, документационный - copy-editor агента. Лишнее не тянется.
- **Под контролем.** Канон распространяется в виде явных снимков по HTTP. Любая правка - только после явного "ок". На свежем проекте sync отрабатывает как no-op.

## Для каких проектов

Это не только про код. Bootstrap спросит про тип и докинет специализацию поверх универсального набора:

- **coding** - кодовые проекты любого стека. Дополнительно тянет правила тестов и обработки ошибок, агентов `debugger`, `implementer`, `code-reviewer`. Пример: серверный сервис, библиотека, CLI-утилита.
- **documentation** - тексты, инструкции, базы знаний. Дополнительно тянет агента `copy-editor`. Пример: документация продукта, книга, технический блог.
- **management** - управленческие проекты, продуктовые задачи, планирование. Дополнительно тянет агента `tracker`, правила формата встреч/задач/оценок и сверки имен, скиллы зеркалирования внешних источников (`telegram-snapshot`, `redmine-snapshot`, `mymeet-snapshot` - чаты, задачи, расшифровки встреч) со скриптами. Пример: roadmap-репо, продуктовые заметки, чек-листы релизов.
- **education** - учебные материалы, конспекты, разборы. Дополнительно тянет агента `note-taker`, правила формата конспектов/домашних заданий/структуры курса и скилл `tutor`. Пример: репо с заметками по предмету, конспекты лекций, разбор статей.
- **wiki** - Obsidian-vault'ы и персональные базы знаний. Дополнительно тянет правила формата заметки и перелинковки (`wiki-notes-style`, `wiki-linking-obsidian`), агентов `note-writer` (пишет заметки по конвенциям) и `librarian` (read-only ревизия vault'а: битые ссылки, дубли, сироты). Пример: заметки по велосипеду/здоровью/рецептам, личная wiki по теме, домашняя база знаний.

## Быстрый старт - новый проект

Открой Claude Code в корне нового проекта и скажи:

```
выполни инструкции из https://raw.githubusercontent.com/dewil/claude-toolkit/main/start.md
```

Дальше агент проведет через настройку памяти, базовых правил, агентов и специализацию под тип проекта (кодинг / управление / учеба / документация / wiki).

## Обновление существующего проекта

Если проект уже бутстрапленный из этого toolkit (в `.claude/canon.yaml` есть запись), открой Claude Code в его корне и запусти команду:

```
/canon
```

Команда `/canon` ставится в проект при bootstrap. Если проект бутстрапился до ее появления - синкни один раз фразой `сделай синк с canon` (или `sync canon`), и `/canon` подтянется вместе с остальным каноном.

Агент прочитает `.claude/canon.yaml`, скачает актуальные правила и агентов из этого репо, опишет расхождения по каждому файлу и спросит, что накатить. Заодно через `[manifest.yaml](./manifest.yaml)` проверит, появились ли в каноне новые файлы под тип проекта, и предложит их добавить. Логика - в `[migrations/sync-from-canon.prompt.md](./migrations/sync-from-canon.prompt.md)`.

## Как это устроено

Если хочется понять механику под капотом - вот из чего собран toolkit.

**Точка входа.** Все начинается с `start.md` в корне репо - тонкого роутера. В любом проекте достаточно попросить Claude "выполни инструкции из `<...>/start.md`"; роутер спросит, что нужно (новый проект / синк / просто посмотреть), и направит в нужный промт. Никаких установок и зависимостей - Claude сам фетчит нужные файлы по HTTP.

**Bootstrap-цепочка.** Настройка нового проекта - это три шага-промта, идущих один за другим: сначала память (`bootstrap-01`), потом универсальный scaffold с базовыми правилами и агентами (`bootstrap-02`), потом специализация под тип проекта (`bootstrap-03-<тип>`). Проект может быть **мультиспециализированным**: Obsidian-vault со встроенной кодовой частью и документацией возьмет сразу `wiki`, `coding` и `documentation` - шаг `bootstrap-03` прогоняется по каждому типу и накладывает специализации друг на друга. Каждый шаг безопасен при повторе: сначала показывает план, ждет "ок", существующее не перезаписывает.

**Реестр накатанного - `canon.yaml`.** После bootstrap в проекте появляется `.claude/canon.yaml`: где лежит канон (репозиторий, ветка), какие типы у проекта, список отслеживаемых файлов и хеш каждого на момент установки. Этот файл коммитится в репозиторий проекта и служит источником истины для синка. Хеши дают синку **трехстороннее сравнение** - база (что установили) / локальная копия (что в проекте сейчас) / текущий канон (что в репо), - чтобы отличить "проект правил файл под себя" от "канон ушел вперед", а не сваливать все в бинарное "разошелся".

**Синхронизация.** Когда в каноне что-то меняется, синк в проекте (`/canon`) проходит по всем отслеживаемым файлам, сравнивает трехсторонне и по каждому расхождению предлагает безопасное действие. Плюс **autodiscovery**: синк заглядывает в `manifest.yaml` и предлагает новые канон-файлы под тип проекта, появившиеся уже после его bootstrap. Именно так свежий скилл или правило доезжает до старых проектов - его не нужно прописывать вручную, достаточно зарегистрировать в манифесте.

**Обратный поток - upstream.** Если в конкретном проекте родилось полезное правило, которое стоит вынести в общий канон, синк собирает самодостаточный бриф (`toolkit-log/upstream-pending/`) - его можно скормить Claude в клоне toolkit, отревьюить и закоммитить. Проект при этом ничего не знает о том, где на машине лежит клон toolkit: связь строго односторонняя и через явные артефакты. На следующем синке проект видит, что правило доехало в канон, и чистит свою пометку.

**Изоляция.** Ключевой принцип: канон тянется **только по HTTP** с закоммиченного `main`. Даже если клон toolkit лежит на машине соседней папкой - проект его не ищет и не подхватывает. Это гарантирует, что везде раскатывается одна и та же зафиксированная версия, а не чье-то рабочее дерево.

## Принципы

- **Идемпотентность** - любой промт безопасен при повторном запуске.
- **Audit -> plan -> "ок" -> action** - изменения только после явного подтверждения.
- **Изоляция** - проект ничего не знает о filesystem-расположении локального клона `claude-toolkit` на твоей машине.
- **Канон в одном экземпляре** - правила и агенты живут только в этом репо, не дублируются heredoc'ом.

Как это устроено внутри - см. раздел ["Как это устроено"](#как-это-устроено) выше. Агентский контекст для правки самого канона (регистрация файлов, принципы промтов) - в `[CLAUDE.md](./CLAUDE.md)`.

## Структура

- `start.md` - точка входа (тонкий роутер).
- `bootstrap/` - цепочка для настройки проекта с нуля.
- `rules/` - канонические правила поведения Claude.
- `agents/` - канонические описания субагентов.
- `skills/` - канонические скиллы (папка на скилл).
- `commands/` - канонические слэш-команды (файл на команду, напр. `/canon` = sync).
- `scripts/` - канонические исполняемые скрипты проекта (напр. зеркалирование внешних источников).
- `templates/` - скелеты с TODO-заглушками, копируются в проект один раз (`README.md`, `project-structure.md` и др.); дальше проект владеет ими сам, sync их не контролирует.
- `migrations/` - одноразовые промты для апгрейда существующих проектов.
- `manifest.yaml` - полный список канон-файлов по типам, с однострочным описанием каждого. Единственный реестр: bootstrap и sync тянут списки отсюда.
- `CLAUDE.md` - агентский контекст для Claude, работающего внутри этого репо (правка канона). Полное человеческое описание - этот README, `CLAUDE.md` импортирует его.

## Свой персональный toolkit

Этот репо рассчитан на то, чтобы его форкнули и допилили под себя - свои правила, своих агентов, свою типографику (например, английский вместо русского), свои конвенции. Идея в том, чтобы у каждого был свой канон, к которому подключаются его проекты.

**Как сделать свой:**

1. Форкни этот репо на GitHub под свой аккаунт - например `<твой-username>/claude-toolkit` (или назови как хочешь).
2. Замени `dewil/claude-toolkit` на свой `<username>/<repo>` в этих файлах:
  - `[start.md](./start.md)` - пример с `<canon_base>`.
  - `[bootstrap/bootstrap-01-memory.prompt.md](./bootstrap/bootstrap-01-memory.prompt.md)` - команда запуска.
  - `[bootstrap/bootstrap-02-scaffold.prompt.md](./bootstrap/bootstrap-02-scaffold.prompt.md)` - шаблон `canon.yaml` (поля `repo` и `raw_base`).
  - `[README.md](./README.md)` - команды в "Быстрый старт".
3. Закоммить и запушь в свой репо.
4. В новых проектах используй ссылку на свой `start.md`:
  ```
   выполни инструкции из https://raw.githubusercontent.com/<username>/<repo>/main/start.md
  ```

**Как наполнять своим:**

- Свои правила - в `[rules/](./rules/)`, своих агентов - в `[agents/](./agents/)`, свои скиллы - в `[skills/<имя>/SKILL.md](./skills/)`, свои слэш-команды - в `[commands/<имя>.md](./commands/)`.
- Любой новый файл регистрируй одной строкой в `[manifest.yaml](./manifest.yaml)` в нужной секции (`universal` / `coding` / `documentation` / `wiki` / `management` / `education`) - это единственный реестр. Bootstrap-промты и sync тянут списки из манифеста сами, руками их дописывать не нужно. Подробности - в `[CLAUDE.md](./CLAUDE.md)`.
- Лишнее из текущего канона можно удалить (например, если не работаешь с управленческими проектами - выкинь `bootstrap-03-management.prompt.md` и его секцию из `manifest.yaml`).

После этого твои проекты будут синкаться с твоим каноном, а не с моим - и обновления будут приезжать те, которые ты сам туда положил.
