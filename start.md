# claude-toolkit - точка входа

Этот файл - точка входа в AI Toolkit. Если пользователь сказал "выполни инструкции из `<...>/start.md`", определи, хочет ли он настроить новый проект, обновить `.AI`, отдельно мигрировать legacy в `.AI` или только посмотреть репозиторий. Уточняй только недостающее и направляй в нужный промт.

## Определи canon_base (всегда HTTP)

`<canon_base>` = директория, из которой загружен ЭТОТ файл, - всегда HTTP-URL. Пример: загружен по `https://raw.githubusercontent.com/dewil/claude-toolkit/main/start.md` -> `<canon_base> = https://raw.githubusercontent.com/dewil/claude-toolkit/main`.

**Канон тянется только по HTTP.** Даже если на машине есть локальный клон toolkit (например, соседней папкой с проектом) - не ищи его, не подхватывай, не переключайся на чтение с диска. Никаких `dirname` до клона, никаких git-путей к нему. Единственный источник канона - `<canon_base>` по HTTP. Это держит изоляцию: проект работает с HTTP-снимком канона, а не с чьим-то рабочим деревом. Обновление `.AI` также использует pinned HTTP-снимок.

Все остальные файлы репо адресуются относительно `<canon_base>`:

- `<canon_base>/bootstrap/bootstrap-ai.prompt.md`
- `<canon_base>/rules/*.md`
- `<canon_base>/agents/*.md`
- `<canon_base>/skills/<name>/*`
- `<canon_base>/migrations/*.prompt.md`
- `<canon_base>/manifest.yaml`

## Что в этом репо

- `bootstrap/` - единственный маршрут установки `.AI` (`bootstrap-ai`).
- `rules/` - канонические правила поведения Claude.
- `agents/` - канонические описания субагентов.
- `skills/` - канонические скиллы (папка на скилл).
- `migrations/` - обновление `.AI` (`ai-sync.prompt.md`) и явная миграция legacy (`ai-layout.prompt.md`).
- `manifest.yaml` - полный список канон-файлов по типам (используется sync для autodiscovery).
- `README.md` - человеческое описание проекта и архитектуры (для людей и GitHub).
- `CLAUDE.md` - агентский контекст для Claude, работающего ВНУТРИ этого репо (импортирует README).

## Как получать промты

Получи промт по его HTTP-URL командой `curl -fsSL`. `WebFetch` того же URL допустим только при отсутствии или недоступности самого инструмента `curl`. Сетевая ошибка доступного `curl` не разрешает переход на `WebFetch`: если недоступен GitHub raw-хост, получи тот же файл через Contents API: `curl -fsSL -H "Accept: application/vnd.github.raw" "https://api.github.com/repos/<owner>/<repo>/contents/<path>?ref=<branch>"`, где owner, repo, path и branch взяты из исходного URL. Если загрузка не удалась, текст пустой или неполный - сообщи и останови переход, не исполняй его. Локальный клон не ищи. Это исключение для промтов не распространяется на канон-файлы и сравнение хешей. Если `canon_base` не на GitHub, Contents API недоступен - только curl по raw-URL, при сбое стоп.

Маппинг ответа -> действие:

### 1) Новый проект

- Следующий промт: `<canon_base>/bootstrap/bootstrap-ai.prompt.md`. Получение промта - см. раздел ["Как получать промты"](#как-получать-промты).
- Содержимое - инструкции для тебя. Выполни как продолжение текущей сессии. Новый маршрут устанавливает `.AI` по HTTPS-снимку, закрепленному за commit SHA; 01/02/03 после него не запускай.

### 2) Синк существующего проекта

- Прочитай общий навык `<canon_base>/skills/canon-sync/SKILL.md` и выполни его в текущей сессии. Он проверяет `.AI` и `.ai-bootstrap` (включая ссылки) и направляет к pinned `migrations/ai-sync.prompt.md`. Legacy-only клиент получает сообщение, что для перехода в `.AI` нужно отдельно запросить миграцию; legacy sync и автоматическая миграция не запускаются. Несколько журналов дают отказ; recover запускается только владельцем журнала. Получение - см. раздел ["Как получать промты"](#как-получать-промты).
- Синк не запускает bootstrap или миграцию автоматически и не меняет ID/types/adapters; локальный клон не ищи.

### 3) Миграция legacy в .AI

- Только при явном запросе на миграцию получи `<canon_base>/migrations/ai-layout.prompt.md` и выполни audit -> plan -> согласованное action. Bootstrap поверх legacy не запускай. Сам промт и оба соседних временных скрипта (`ai-migrate.py`, `ai-bootstrap.py`) должны быть из одного pinned HTTPS revision; explicit bundle допускается только по отдельной процедуре.
- Старый монолитный `.claude/canon.yaml` со списком `files` поддержан. Дополнительные архивируемые legacy-реестры (`canon.intent.yaml`, `canon.state.json`, `canon.ledger.json`) не меняют этот маршрут: при миграции они сохраняются в архиве, но не становятся источниками владения и не переносятся в активную `.claude`. Split-only без поддерживаемого монолитного реестра, чужой state и существующий `.agents` требуют другого адаптера. Не обходи отказ и не меняй клиент до согласования плана. Backup retained, recover завершает записанное поколение и не является rollback.

### 4) Ничего

- Опиши кратко состав репо (список выше) и остановись.

## Принципы (общие для всех промтов репо)

- **Идемпотентность.** Любой промт безопасен при повторном запуске. На свежем/актуальном проекте отрабатывает как no-op.
- **Audit -> plan -> "ок" -> action.** Любая правка делается только после явного подтверждения. Без "ок" - только чтение.
- **Изоляция.** Проект ничего не знает о filesystem-расположении локального клона claude-toolkit и не ищет его на машине. Канон - только по HTTP (даже если клон лежит рядом), наверх - только через самодостаточные артефакты.
- **Канон в одном экземпляре.** Правила и агенты живут только в `rules/`/`agents/` репо, не дублируются heredoc'ом в bootstrap-промтах.
- **Русская типографика.** Кавычки `"..."`, тире и дефис - один и тот же символ `-`, "е" вместо "ё". См. `rules/typography-ru.md`.
