# Раскатка канона по парку проектов

Как зафиксированная ревизия канона доезжает до проектов: чем контур fleet отличается от solo, что делает тег `canon-vN`, как проект попадает в парк и какими ключами описывается. Механику самого движка (классификатор, WAL, трехстороннее сравнение) документ не пересказывает - она в `scripts/canon-delta.py` и в README.

## Два контура, и они не заменяют друг друга

| | solo | fleet |
| --- | --- | --- |
| Кто инициирует | человек, командой `/canon` в корне проекта | `canon-maintainer` из `claude-control`, по таймеру |
| Откуда берется канон | HTTP с закоммиченного `main` | git-зеркало по ревизии тега `canon-vN` |
| Что получается | правки в рабочем дереве после "ок" по каждому файлу | PR в репозиторий проекта (или только отчет) |
| Где список проектов | **нигде** - проект знает про канон, канон про проект не знает | `~/.claude-control/canon/fleet.yaml` |

Отсюда два следствия, которые чаще всего удивляют:

- **Тег сам по себе никуда не едет.** Он фиксирует, *что* раскатывать, а не *куда*. Получатели - только те, кто перечислен в `fleet.yaml`; пустой инвентарь означает, что релиз выпущен и никому не адресован.
- **Solo-проекты тег игнорируют.** `/canon` тянет актуальный `main` по HTTP, не ревизию тега. Свежий коммит доедет до solo-проекта сразу, а до fleet - только следующим тегом.

## Выпуск релиза

1. Убедиться, что тесты движка зеленые: `python3 -m unittest discover -s tests`.
2. Поставить **аннотированный** тег: `git tag -a canon-vN -m "..."` и запушить его (`git push origin canon-vN`).
3. CI (`.github/workflows/canon-release.yml`) собирает `canon.lock.json` из дерева тега и публикует его как release-asset. Он же - server-side gate: если манифест ссылается на путь вне дерева или на неподдержанный mode, издание падает и релиза не будет.

Идентичность ревизии несет **сам git-объект тега**, а не содержимое lock: одна и та же зафиксированная ревизия раскатывается везде. Поэтому тег не переставляют задним числом - если ошиблись, выпускают следующий.

Локально дескриптор можно собрать для проверки, не выпуская релиз:

```bash
python3 scripts/build-lock.py --ref HEAD --output /tmp/canon.lock.json
```

## Инвентарь парка: `fleet.yaml`

Боевой файл - `~/.claude-control/canon/fleet.yaml` (переопределяется `CLAUDE_CANON_FLEET`), пример с комментариями - `examples/fleet.yaml.example` в `claude-control`. Формат: имя проекта -> набор ключей.

| Ключ | Значения | Смысл |
| --- | --- | --- |
| `repo_url` | git-URL | канон едет через клон и PR |
| `path` | абсолютный путь | локальный проект вместо `repo_url`; не-git путь допускает только `observe` |
| `policy` | `observe` / `branch` / `auto-merge` | что делать с готовым кандидатом |
| `ring` | `canary` / `snapshot` / `rest` | очередность раскатки, дефолт `rest` |
| `track` | `stable` | канал ревизий канона |
| `fleet_managed` | `true` / `false` | `false` - временно исключить проект, не удаляя запись |
| `smoke_cmd` | команда | смоук в candidate-worktree перед предъявлением |
| `target_cmd` | команда | целевая команда проекта для exit-кода смоука |

**Политики.** `observe` - только отчет, ничего не создается (единственный вариант для не-git проектов вроде vault'а). `branch` - ветка и PR, мержит человек. `auto-merge` - для того, что не жалко раскатывать без ревью.

**Кольца** задают порядок в одном проходе: сперва `canary`, потом `snapshot`, потом `rest`. Смысл - поймать плохую ревизию на одном проекте раньше, чем она уедет на весь парк.

**Запись в этом файле делает проект fleet-managed**, и это меняет его поведение: standalone `/canon` на нем отказывает. Так контуры не дерутся за один рабочий каталог. Убрать проект из парка - удалить запись или поставить `fleet_managed: false`.

## Как ведет себя maintainer

Живет в `claude-control` (`bin/claude-agent-canon-maintainer`), таймер - раз в 12 часов со случайной задержкой до часа, состояние - в `~/.claude-control/canon/`.

Все подкоманды ниже - у самого бинарника (`claude-agent-canon-maintainer <verb>`), не у `claude-rc`: тот про сессии и к канону отношения не имеет. Таймер запускает `once`.

- **Мутирующий режим включается вручную:** `arm` (и `disarm` как kill-switch, ждущий конца текущего прохода). До `arm` проходы идут наблюдением - это осознанно: первый прогон на новом парке должен показать, что он собирается сделать.
- **Бюджет действий на проход** - `CLAUDE_CANON_BUDGET`, по умолчанию 10. Исчерпан - остальные проекты получают вердикт `budget-exhausted` и ждут следующего прохода. Это защита от "плохая ревизия открыла PR в тридцати репозиториях".
- **Circuit breaker.** Latch защелкивают три класса вердикта: несовместимость, ошибка прохода и **провал смоука** (`held-smoke`) - то есть не только внутренний сбой, но и честно упавшая проверка проекта. Раскатка этой ревизии на это кольцо останавливается до ручного `ack <release> <ring>`. Таймаут смоука не защелкивает - он транзиентен.
- **Откат** - `rollback <project>` возвращает проект на предыдущую примененную ревизию и ставит latch до `ack`.
- **Статус** - `status` отдает JSON: armed, курсор ревизии, latch'и, бюджет.
- **`recover`** - терминализация хвостов незавершенных транзакций; нужна после аварийного обрыва прохода, в обычной работе не вызывается.

## Подключить проект - чек-лист

1. Решить политику. Не git - только `observe`. Git и есть кому смотреть PR - `branch`.
2. Дописать запись в `~/.claude-control/canon/fleet.yaml`.
3. Прогнать проход наблюдением (`once` без `arm`) и прочитать отчет: что именно движок собирается изменить.
4. Убедиться, что в проекте нет незакоммиченных правок канон-файлов - иначе трехстороннее сравнение честно покажет конфликт, и его придется разрешать вручную.
5. Только потом `arm`.

Обратная сторона шага 2: с этого момента `/canon` в проекте отказывает. Если проект живой и вы правите канон в нем руками - `observe` или отсутствие в инвентаре честнее.

## Когда парк пустой - это нормально

Проект не обязан быть в парке. Зонтики клиентов и vault'ы - не-git папки, для них максимум `observe`, а `/canon` руками работает лучше. Дети зонтиков (репозитории внутри клиентской папки) канон обычно вообще не носят: сессии и память живут в корне зонтика, а не в них (`rules/client-umbrella.md`).

Смысл fleet-контура появляется там, где проектов много и они однотипны. На парке из одного-двух проектов честнее ходить `/canon` руками, чем поддерживать инвентарь.
