# Работа по SDD

Порядок задан [правилом](../rules/sdd-pipeline.md), роли - общими инструкциями `test-writer` и `implementer`. Начать можно навыком `sdd` или просьбой "Проведи это изменение по SDD". Если среда не показывает навык, открой установленный `skills/sdd/SKILL.md` напрямую. Доступность slash-команды зависит от среды.

SDD - переносимый протокол, а не автоматический оркестратор. Агент обязан записывать этапы и доказательства; наличие файлов само по себе не гарантирует соблюдение. В `.AI` принятие и область SDD записываются в `.AI/project.md`; производные входы не редактируются. В legacy используется редактируемый `CLAUDE.md`. Канон применяет SDD ко всем своим правкам, включая тексты.

## Пример: имя выгрузки без разделителей

Требование `FR-EXPORT-01`: имя выгрузки не может содержать `/` или `\\`; допустимое имя возвращается без изменений. Доменная спека содержит инвариант "имя не содержит разделителей каталога", а спека фичи объясняет отказы и их причины. Это учебный пример, не новый API канона.

1. Владелец создает `docs/backlog/2026-10-01-export-name.md` с ID `EXPORT-NAME-01`, целью, ограничениями, этапом `spec`, ссылками на спеки и следующим шагом.
2. Автор тестов получает только спеку и публичную сигнатуру `validate_name(name)`. В отдельном контексте проверяет допустимое имя и обе разделительные черты. RED фиксирует разрешение недопустимого имени; опечатка или сломанный импорт не считается доказательством дефекта. Тесты коммитятся до передачи исполнителю.
3. Исполнитель получает спеку и те же тесты в отдельном worktree. Реализует отказ, сохраняет результаты GREEN и полного проектного CI, ревизию и измененные файлы. Независимые тесты не переписывает.
4. Другая фактическая модель в отдельной проверяющей сессии получает спеки и объект сверки. Проверяет прозу инварианта, критерии, дифф и трассируемость. Модель и источник подтверждения запуска сохраняются в задаче. При замечаниях правит автор, затем повторяются затронутые проверки и сверка.
5. После закрытых замечаний и зеленого CI на текущем объекте владелец закрывает задачу, исправляет ссылки и переносит ее и спеку фичи в `docs/done/`. Устойчивый вывод записывается в общую память. Зеленый CI не разрешает деплой автоматически.

Для текстовой правки автор независимых проверок сначала записывает сценарии/критерии и исходный RED, после правки другой источник сверяет тот же набор. Проверяемую кодом механику покрывает исполняемый тест, решение агента - eval или практический сценарий. Проверка точной фразы сама по себе не доказывает правильность поведения.

## Ограниченный пакет совместимых задач

Одиночная задача проходит прежний маршрут. Несколько изменений можно заранее объединить в ограниченный пакет только если общую спеку, критерии и интегрированные эффекты реально охватить независимым review. Не собирай в пакет весь backlog автоматически и не объединяй задачи только из-за общего срока или разных путей.

У пакета один общий Markdown-владелец и одна спека; каждый участник сохраняет свой task ID, Markdown-владельца, статус, критерии и независимый значимый RED до своей реализации. Общая матрица связывает child с инвариантом, исполнителем и проверкой:

| Child ID | Инвариант/критерий | Исполнитель | Независимый RED и проверка |
|---|---|---|---|
| UI-A | состояние фильтра сохраняется | автор A | RED-A, проверка интегрированного состояния |
| UI-B | поиск не меняет фильтр | автор B | RED-B, проверка общего API |
| UI-C | пустая выдача сообщает отсутствие | автор C | RED-C, итоговый UI-flow |

Это иллюстрация формы матрицы: реализация начинается только после отдельного RED и согласованных критериев каждого child. Совпадающий файл обслуживает один писатель либо участники работают последовательно. Разные файлы с общей зависимостью API/state/schema связываются явной интеграционной проверкой. Если child требует отдельного доказательства риска, отката или выпуска, выдели его в отдельный scope.

Во время работы запускай целевые локальные проверки. Один независимый reviewer сверяет все child, их критерии и интегрированные эффекты; полный CI проходит на стабильном интегрированном SHA. Если объем не помещается в review, раздели пакет или ревью, затем сделай общую финальную integration-сверку. Любой failing child блокирует готовность всего пакета. Исключить его можно только явным разрешенным пересмотром спеки/объема; child остается открытым и возвращается в backlog. Новая находка меняет объем до соответствующего кода либо уходит в backlog.

Исправления делает прежний автор; независимое delta-review и затронутые проверки сохраняют актуальное покрытие. После изменения ревизии полный CI повторяется на новом точном SHA; прежний GREEN не переносится. Условия безопасности, полномочий и реальной приемки устройства остаются прежними: CI не подтверждает устройство и не разрешает деплой. Уже разрешенные параллельная работа и delta-review сохраняются, этот пакетный маршрут сам не расширяет их.

Общие планирование, интеграция, review и CI владелец учитывает один раз; дочерние журналы содержат только уникальные receipts. Не складывай inclusive parent total с теми же child receipts, не отбрасывай retry и unknown и не выдумывай распределение общих затрат. Пакет и его учетные материалы закрываются вместе с общим Markdown-владельцем после прохождения всех критериев.

## Сохранение перед сменой сессии

Минимальная запись в задаче перед остановкой:

```markdown
ID: EXPORT-NAME-01
Статус: in_progress
Этап: implementation
Спеки: docs/specs/export.md, docs/2026-10-01-spec-export-name.md
Сделано: независимые тесты закоммичены; реализация готова
Проверки: команда полного CI; код 0; проверенная ревизия/хеши файлов
Автор: среда, фактическая модель, сессия; подтверждение запуска
Сверка: еще не выполнена
Блокеры: нет
Следующий шаг: независимая compliance-сверка
```

Новая сессия читает задачу, спеки и отчеты, проверяет текущую ревизию и незакоммиченные изменения. Если объект изменился, прежний GREEN требует обновления проверок затронутого результата. Итог предыдущего чата не заменяет файлы задачи. В `.AI` сначала читаются START, project.md и MEMORY.md.

Если автор и проверяющий - одна фактическая модель либо ее идентичность неизвестна, записывается `blocked`, причина и следующий шаг "подключить разрешенную независимую модель". Новая сессия той же модели не устраняет блокер. Для опасного изменения дополнительно проверяются ограничения доступа и сценарии потери данных, полномочий и восстановления. Если нужной среды нет, мерж остается заблокирован.

## Проверки репозитория

```bash
python3 -m compileall -q scripts/
python3 scripts/run-tests.py
python3 scripts/run-evals.py --scenario sdd --list
```

Runner автоматически находит непосредственные `tests/test_*.py`, проверяет список до запуска и исполняет каждый обычный файл отдельным процессом. Новые модули не требуют правки CI. Пустой/неверный каталог и symlink теста - ошибка конфигурации, код 2; падение теста - код 1 с остановкой; полный успех - 0. `--tests-dir PATH` выбирает учебную фикстуру; обычные каталоги под маской игнорируются. Запускается доверенный тестовый код: это не песочница от злонамеренного теста.

`--list` проверяет загрузку сценариев, а не поведение модели. Фактический запуск eval требует настроенной среды harness; его результат записывается отдельно. В отчете приемки различаются локальные тесты, независимое ревью, практический проход и непроверенные CLI/платформы.
