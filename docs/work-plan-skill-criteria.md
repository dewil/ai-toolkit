# Критерии приемки: навык work-plan и шаблон плана работ

Слепой шаг SDD для текстового изменения. Источники: ранбук плана `docs/runbooks/plan-rabot.md` проекта-источника (v2.3) и спека `docs/plan-dates.md`. Объекты проверки: `skills/work-plan/SKILL.md`, `templates/work-plan.md`, `templates/work-plan-sroki.example.json`. Реальный план проекта-источника - данные заказчика, в критерии не копировался.

Обозначения: `T` = `templates/work-plan.md`, `D` = `templates/work-plan-sroki.example.json`, `S` = `skills/work-plan/SKILL.md`. Команды выполняются из корня репозитория ai-toolkit.

## Критерии приемки

| ID | Критерий | Как проверить |

| WP-01 | Три файла существуют; у `S` есть frontmatter с `name: work-plan` и непустым `description`, как у соседних навыков. | `test -f` для трех путей; `head -5 skills/work-plan/SKILL.md` и сравнение формы с любым соседним `skills/*/SKILL.md`. |
| WP-02 | `T` проходит lint без ERROR на `D`. Точная команда: `python3 scripts/plan-dates.py lint --plan templates/work-plan.md --data templates/work-plan-sroki.example.json --now 2026-11-23T12:00+03:00`. Код выхода 0, в stdout нет строк `ERROR:`. WARN допустимы. Следствие: `T` содержит конкретные значения (дата `Обновлено`, N в заголовках равно числу строк, одинаковое число колонок, отметка времени у элемента "Готово за сутки"), а не буквальные `ДД.ММ ЧЧ:ММ` и `N`. | Прогнать команду, проверить `echo $?` и `grep -c '^ERROR:'` = 0. |

| WP-08 | `S` говорит, что делает скрипт и чего не делает: пересчитывает таблицу "Держатели", чистит "Готово за сутки" старше 24 часов, проверяет форму (lint); даты прогноза по графу этапов в эту версию не считает - их ведущий пишет руками по формулам нормы держателя (обычно/затяжно, остаток блокера). | WP-13 | `S` фиксирует границы: план - сводка по карточкам задач, PR и трекеру, а не их замена; в плане нет секретов, токенов, личных данных третьих лиц, полных логов и диффов; исходящее держателю из "Ускорить" сначала показывается владельцу; копия для владельца не правится, правки идут в источник. | Чтение `S`: четыре утверждения-границы; grep `секрет` и `Ускорить`. |
| WP-14 | Навык подключен по конвенциям канона: описание (`description`) называет триггеры (завести, обновить, опубликовать план работ), упомянут в каталоге навыков, если в репозитории есть реестр/индекс (`START.md` или аналог) и сборка `check` его требует; `T` и `D` перечислены в `templates/README.md`, если он ведет перечень шаблонов. | Сравнить с тем, как зарегистрированы соседние навыки и шаблоны; прогнать штатный `check`/`build` проекта, если он есть (результат - в отчет). |

## Практические сценарии (вход -> ожидаемое действие агента с навыком)

**WP-S1. Новый план из шаблона.** Вход: "заведи план работ для проекта <имя>", плана и данных нет.
Ожидается: агент берет `templates/work-plan.md` и `templates/work-plan-sroki.example.json`, создает `docs/plans/plan-<сегодняшняя дата>-<проект>.md` и `docs/plans/<проект>-sroki.json`; заменяет примерные значения реальными (или оставляет пустые таблицы с N = 0 и строкой "ничего не ждем", не оставляя `<...>` и буквальных `ДД.ММ`); время "Обновлено" берет из `date`, не из головы; прогоняет `plan-dates.py all --plan ... --data ... --write`; код 0 перед сообщением "готово". Данных о задачах нет - не выдумывает строки блокировок и работ, пишет что неизвестно.

**WP-S2. Событие: закрылось ожидание.** Вход: держатель ответил на ожидание `pr47` (в данных открыто), пункт попадает в работу и закрывается.
Ожидается: агент (1) в данных удаляет запись из `open_waits` и добавляет в `samples` держателя пару `asked`/`answered` с реальными временем из `date`; (2) запускает `all --write` - таблица "Держатели" пересчитана скриптом, не руками; (3) удаляет строку из Блокировок и уменьшает N в заголовке; (4) добавляет в "Готово за сутки" строку с итогом и отметкой `ДД.ММ ЧЧ:ММ`; (5) обновляет "Обновлено" и "Сдвинулось"; (6) lint без ERROR, затем публикует копию. Все шаги в одном обновлении, без отложенной "потом".

**WP-S3. "Горит" из lint.** Вход: результат `all` содержит `WARN: ожидание pr47 (holder reviewer) горит`.
Ожидается: агент переносит этот пункт в строку "Горит" шапки (с держателем и сроком висения), для меры, которая требует решения владельца, дописывает в "От ..."; не откладывает до суточной сверки. Исходящее держателю (напоминание) не отправляет сам - сначала показывает владельцу текст.

**WP-S4. Ошибка lint - не публиковать.** Вход: `all --write` вернул код 1, `ERROR: строка таблицы с другим числом колонок` или `ERROR: ... число N не равно числу строк`.
Ожидается: агент не копирует план в место чтения владельца и не сообщает "план обновлен"; исправляет источник (колонки, N, пустое "Снимется"/"Готово"), повторяет `all`; публикует только после кода 0. Если ошибка в данных или вызове (код 2) - чинит данные/путь, не правит таблицу вручную в обход. В отчете называет найденную ошибку.

**WP-S5. Проект без данных о держателях.** Вход: пользователь просит план, но истории ожиданий нет; в `*-sroki.json` держатели без `samples`.
Ожидается: агент заводит держателей с `label` и `default` ([обычно, затяжно] в днях по роли: умолчания из навыка или `[1, 3]`); в таблице "Держатели" видно `0 (по умолчанию: мало данных)`; агент не придумывает замеров и не выдает умолчание за измеренную норму; в плане помечено "мало данных". Вопрос про реальные роли держателей задает пользователю один раз, а не гадает.

**WP-S6 (необязательный). Расхождение с источником.** Вход: сверка дня показала, что PR влит, а в плане пункт "в работе".
Ожидается: агент устраняет расхождение по подтверждающему событию (закрывает пункт, строка в "Готово за сутки", запись замера), а не просто стирает строку; не переносит содержимое карточки в план, ставит ссылку.

## Вопросы к замыслу (развилки)

1. Шаблон и lint. Ранбук-шаблон содержит буквальные заглушки (`ДД.ММ ЧЧ:ММ`, `N`, `<...>`), на которых lint по спеке даст ERROR (нечитаемая отметка "Обновлено", N не число). Требование "шаблон проходит lint" я прочитал как: `T` хранит конкретные синтетические значения. Альтернатива - заглушки в `T` и отдельная команда подстановки или `lint` с исключением; выбрать до реализации.
2. Слово `dwl` и роль владельца. В источнике "dwl" - ключевое лицо (держатель по умолчанию, получатель "От dwl"). В WP-D2 принято: в каноне вместо имени - "владелец плана"/"пользователь". Если канон допускает личные ники (как в `addressing.md`), критерий смягчить.
3. Умолчания держателей (1/3, 1/4, 3/7, 4/14) и множитель буфера B (0.5 / 0.1) из ранбука - переносить в навык как справку или только требовать `default` в данных? Скрипт использует лишь `default` (по спеке `[1, 3]` без поля). WP-10 допускает оба, но результат различается.
4. Расчет дат прогноза (обычно/затяжно, остаток блокера, `если ответ сегодня`) скрипт в v1 не делает. Должен ли навык описывать ручной расчет по формулам ранбука, или это выходит за объем первой версии? WP-08 требует хотя бы упоминания границы.
5. Копия для владельца в Obsidian (путь `Work/...`, атомарная публикация, `plan-touch.sh`): переносить как параметризованный шаг или не включать, раз `scripts/plan-touch.sh` в спеке скрипта не описан?
