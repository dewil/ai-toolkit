# Промт: отдельная миграция legacy проекта в .AI

Выполняй этот маршрут только по явному запросу пользователя на миграцию конкретного legacy-клиента в `.AI`. Обычный `/canon` не запускает миграцию. Bootstrap нового проекта поверх `.claude` запрещен. Процедура: audit -> plan -> согласованное action; уже выданное разрешение на конкретный план повторно не запрашивай.

## 1. Аудит без изменений клиента

Сначала определи только существующий абсолютный корень ROOT. До Git-проверок, загрузки canonical package и legacy inventory проверь `/proc/self/mountinfo` по закрепленному Linux guard: точные `.agents`, `.agents/skills`, `.git`, `.claude`, `CLAUDE.md`, `AGENTS.md`, `docs/dev` и mountpoints внутри перемещаемых деревьев. Корневой и обычные окружающие mounts не блокируют маршрут. Relevant mount либо недоступный/нечитаемый/некорректный mountinfo означают недостоверную среду: прекрати inventory и исполнение, перейди к разделу «Одна команда в обычном терминале». Тип `tmpfs`, read-only или bind не доказывает происхождение пути или его отсутствия на host. Не делай umount/rmdir, не меняй настройки/права и не обходи policy через escalation. Engine повторяет этот guard перед plan/apply/check/recover.

После достоверного preflight проверь следы операций, включая ссылки и битые ссылки: `.ai-bootstrap/sync.json`, `.ai-bootstrap/migration.json`, `.ai-bootstrap/journal.json`, `.AI`, `.ai-bootstrap`. UUID пока не создавай, legacy prerequisites и отсутствие `.agents` пока не требуй. Не сканируй Work и соседние репозитории. Первый исполнительный контракт - Linux/Python 3.11+; macOS/Windows не сертифицированы, DeepSeek без оболочки не поддержан. Исполняемые инструменты получи вне клиента по закрепленному контракту раздела 2; для recovery пакет источников клиента не загружается заново.

- Несколько журналов одновременно - отказ без recover, записи или очистки. При `.ai-bootstrap/sync.json` направь к `migrations/ai-sync.prompt.md`: только `ai-sync.py check/recover --root ROOT`, migration recover к нему не применяется. После этого заверши маршрут.
- При `.ai-bootstrap/migration.json` покажи результат `ai-migrate.py check --root ROOT` и конкретное восстановление. Для своего журнала используй исходный handoff либо сохраненные matching tools и подтверждение их происхождения; неизвестная provenance - остановка, без загрузки latest/main. Если восстановление входит в уже разрешенную миграцию, выполни `ai-migrate.py recover --root ROOT`, затем check. Иначе сначала согласуй конкретное восстановление. Recover не требует source, нового UUID, типов или адаптеров: они уже зафиксированы в журнале. После успешного check прочитай сохраненные ID/config/source, отчитайся и заверши маршрут. К новой миграции или legacy prerequisites после recovery не переходи. При отказе сохрани журнал и остановись. Не запускай bootstrap check/build/recover/apply: незавершенная миграция принадлежит своему журналу.
- При `.ai-bootstrap/journal.json` останови миграцию и используй отдельную процедуру `bootstrap/bootstrap-ai.prompt.md`. Migration recover к bootstrap-журналу не применяется. Если обнаружены оба журнала или неизвестное состояние `.ai-bootstrap`, остановись без записи и ручной очистки.
- При существующей `.AI` без журналов запусти `ai-migrate.py check --root ROOT`. Только после успешной проверки прочитай `.AI/canon/canon.state.json` и `.AI/project.json`. Если state содержит запись завершенной migration, используй сохраненные project_id, типы, адаптеры и source, сообщи их и заверши маршрут. Новый UUID и повтор plan/apply не нужны; совместимая `.agents` в завершенной раскладке допустима. Если пользователь явно запросил повтор идентичного apply, используй только сохраненные ID/config/source: совпадающее поколение - no-op. Измененная конфигурация требует отдельного перехода. Чужая `.AI`, state без migration, поврежденные источники или ошибка check дают отказ без перезаписи.

Не удаляй журнал, lock или backup вручную. Только если указанных следов операции нет, проверь новую legacy-миграцию: нужны обычные `.claude/`, `CLAUDE.md` и старый монолитный `.claude/canon.yaml` со списком `files`. Дополнительные старые `canon.intent.yaml`, `canon.state.json`, `canon.ledger.json` сохраняются вместе с полной `.claude` в архиве, не читаются как источник владения и не переносятся в активную `.claude`. Split-only без поддерживаемого монолитного `canon.yaml`, versioned/неизвестный registry и существующий `.agents` требуют другого адаптера: остановись без удаления или обхода отказа. Симлинки в переносимых данных, непереносимые пути, case/Unicode и file-parent коллизии дают отказ.

После успешного legacy-аудита определи типы проекта и выбранные адаптеры (`claude`, `codex`, `kimi`). Используй согласованный UUID project_id либо создай его один раз для новой миграции и сохрани для plan/apply.

## 2. Закрепленный пакет и read-only план

Обычный источник - HTTPS-снимок `https://raw.githubusercontent.com/OWNER/REPO/COMMIT_SHA`, SHA - 40 hex-символов. `<canon_base>` берется из URL входного промта, локальный клон сам не ищи. Ветку разреши через GitHub API в SHA и покажи его. Затем получи сам этот промт, `scripts/ai-migrate.py` и его обязательный компаньон `scripts/ai-bootstrap.py` из одного SHA. Также получи `scripts/ai-migrate-terminal.py`. Сохрани все три скрипта рядом в отдельном временном каталоге вне клиента: migrate импортирует соседний bootstrap. Не запускай скрипт из другого revision и не подставляй `main` в команду установки. Сетевой отказ - остановка до изменений клиента.

Для явно предоставленного пользователем офлайн/разработческого bundle допустим `--bundle DIR` вместо `--source-base`; все три исполняемых скрипта бери из того же generation bundle и держи рядом вне клиента. Автоматический поиск клона и fallback на локальное дерево запрещены. Исполняемый пакет должен содержать все файлы manifest; plan/apply проверяют полный пакет до изменения клиента.

Запусти с реальными значениями; типы и адаптеры ниже - пример, замени согласованным набором:

```text
python3 /tmp/MIGRATION/scripts/ai-migrate.py plan --root ROOT --source-base PINNED_HTTPS_URL --project-id UUID --types coding,wiki --adapters claude,codex,kimi
```

Plan выводит JSON и не пишет в клиент даже при отказе. Покажи source/SHA, ID/config, шаги, backup, `retained`, `local_only`, перенос docs и ограничения проверки. Успех CLI - 0, отказ - 2. Не интерпретируй отказ как разрешение вручную очистить назначения.

План сохраняет память побайтно. Известный чистый legacy-файл обновляется из нового manifest universal+типов; локальная правка или неизвестная база сохраняет точные байты. `local_only`, `overrides`, `skip_sync` старого реестра исключают обновление соответствующих файлов. Неизвестные rules/skills/agents/commands становятся local-only; сохраненные канонические правки учитываются отдельно от настоящих upstream-баз. Локальные hashes не заменяют upstream `source_files`.

Полная старая `.claude`, старые root-входы и `docs/dev` при наличии архивируются в `.ai-bootstrap/legacy/`; backup сохраняется после успеха. Старый `CLAUDE.md` становится локальным `.AI/project.md` с заменой маршрутов `.claude` и `docs/dev`. Старый AGENTS-контекст сохраняется отдельным локальным файлом памяти. Приватный контекст и память не встраиваются в generated AGENTS.md/CLAUDE.md. Settings/local files остаются по совместимым маршрутам; legacy agent-memory переносится в файловую `.AI/memory/agent-memory` с alias. Внешний нативный слот автопамяти, глобальный векторный индекс, индексатор, таймеры и integrations не меняются.

`docs/dev` раскрывается в `docs` только без перезаписи; при коллизии отказ. Backlog/done - `docs/backlog`, `docs/done`. Остальные документы, подпроекты и вложенные git-репозитории не затрагиваются. Строки `.gitignore` сохраняются с добавлением защиты приватных `.AI` и `.ai-bootstrap`.

Согласуй конкретный план, если пользователь еще не разрешил его применение. До согласования - только audit/plan.

## Одна команда в обычном терминале

Этот маршрут нужен только при environmental blocker; здоровый legacy или уже migrated клиент проходит обычные plan/apply/check/no-op выше. Mount не превращает настоящий пользовательский `.agents` в поддержанный legacy: в достоверной среде обычный отказ сохраняется.

Сам подготовь handoff вне клиента. Сохрани там три sibling tools из одного разрешенного immutable commit либо явно предоставленного generation bundle, вместе с подтверждением происхождения и совпадения canonical source. Hashes сами по себе происхождение не доказывают. Не читай masked legacy inventory как достоверный: root/UUID/types/adapters/source возьми из уже подтвержденного плана/задачи или собственного retained handoff. Недостающие сведения и разрешение уточни; неизвестная provenance, чужой pending journal или несколько journals - остановка без очистки и случайного выбора. Подготовка ничего не меняет в клиенте и не означает разрешение на apply.

Выполни prepare сам, подставив реальные подтвержденные параметры (для explicit bundle замени `--source-base PINNED_HTTPS_URL` на `--bundle ABS_BUNDLE`):

```text
python3 /tmp/MIGRATION/scripts/ai-migrate-terminal.py prepare --root ROOT --source-base PINNED_HTTPS_URL --project-id UUID --types coding,wiki --adapters claude,codex,kimi --handoff-dir OUTSIDE_HANDOFF --operation OPERATION
```

OPERATION совпадает с согласованной работой: только `plan` при разрешении на план, `apply` при разрешенном применении, `check` либо конкретный `recover` своего журнала. Не перезаписывай непустой/измененный handoff. Для offline recover/check сохрани исходный handoff, исходную тройку и provenance; prepare нового recovery допустим только с этой подтвержденной тройкой и идентичностью корня, без fetch source или замены поколения. Пакет источников после прерывания может отсутствовать.

Пользователю покажи короткую причину и ровно готовую команду из prepare вида `bash '/absolute/handoff/run.sh'`, с указанием запустить ее в обычном терминале пользователя. Не перекладывай UUID/SHA/параметры на пользователя, не выдумывай slash-команды и не исполняй external apply сам из отказавшей среды. Его запуск согласованного apply - отдельное внешнее выполнение; ограниченная агентская среда от этого не меняется. Apply показывает plan, затем исполняет apply и check существующим engine; plan-only не применяет изменения. Engine перед apply повторно проверяет дерево под writer lock: показанный план не замораживает клиент.

При ошибке сохрани journal/backup/handoff; automatic recover после ошибки apply запрещен. Recovery - отдельная согласованная операция исходными matching tools offline. После сообщения пользователя прочитай именно свой `result.json`: сверь schema, operation, root, UUID и `request_sha256` с сохраненным request и фактическое завершение. Успех требует `exit_code=0`: `planned` для plan; `migrated`/`up-to-date` для apply; `recovered` для recover; `ok` для check. Для apply/recover/check нужен фактический `check=ok`; `running`, `failed`, чужая или старая квитанция успеха не доказывают. Сверь доступные `.AI/project.json` и `.AI/canon/canon.state.json` с квитанцией; при несоответствии или недоступности нужной проверки остановись без заявления об успехе. После подтверждения подхвати сохраненную Markdown-задачу через `.AI/START.md`.

Host engine устанавливает physical aliases, но runtime masks могут скрывать их и после успешного host check. Не объявляй policy снятой, native discovery или свежие адаптеры проверенными. Сохраняй handoff/tools/provenance до успешного check и завершения разбора.

## 3. Согласованное применение и recovery

Применяй тот же source, UUID, типы и адаптеры:

```text
python3 /tmp/MIGRATION/scripts/ai-migrate.py apply --root ROOT --source-base PINNED_HTTPS_URL --project-id UUID --types coding,wiki --adapters claude,codex,kimi
python3 /tmp/MIGRATION/scripts/ai-migrate.py check --root ROOT
```

Apply использует общий writer-lock, повторно проверяет исходные receipts и записывает `.ai-bootstrap/migration.json` с полным поколением. State устанавливается последним. После прерывания заверши зафиксированное поколение без новой сети или пересборки:

```text
python3 /tmp/MIGRATION/scripts/ai-migrate.py recover --root ROOT
python3 /tmp/MIGRATION/scripts/ai-migrate.py check --root ROOT
```

Recover - roll-forward, не rollback. Он валидирует журнал и отказывает при неожиданных пользовательских изменениях, сохраняя материалы для разбора. Не обещай автоматического возврата: отдельный план возврата должен опираться на retained backup и отчет. Backup не удаляется автоматически. Повтор завершенной миграции с теми же ID/config/source - no-op; изменение конфигурации требует отдельного перехода.

После успеха общий источник - `.AI`, compatible aliases - `.claude` и `.agents/skills`, authoritative state - `.AI/canon/canon.state.json`. Для правки источников и пересборки используй `ai-bootstrap.py build --root ROOT`, затем check; ручная правка generated входов блокирует build. Обновление `.AI` - навык `canon-sync` и отдельная `migrations/ai-sync.prompt.md`; `/canon` направляет к ним. Старые canon-delta/canon-migrate и legacy sync не запускай.

## 4. Отчет и границы проверки

Сообщи root, ID, SHA либо explicit bundle, типы/адаптеры, результат check, retained/local-only и путь backup. Отдельно перечисли проверки свежих сессий адаптеров, которые действительно выполнены; структурный check не сертифицирует fresh-agent поведение, автопамять или векторный поиск. До отдельного подключения используй файловую `.AI/memory` явно. Не заявляй публикацию на main по результатам локальных тестов.

### Проверка передачи между свежими сессиями

Согласуй фактическую последовательность доступных сред: например, Codex -> Kimi -> свежая сессия Codex. Не требуй Claude только из-за его имени в примере и не запускай другую CLI автоматически вместо текущего участника. Повторная сессия того же вендора проверяет возобновление; она не подтверждает поддержку отсутствующего вендора. Недоступные или не выбранные среды перечисли как непроверенные.

Перед ручным тестом снова выполни check: успешная проверка сразу после apply не гарантирует, что файлы впоследствии не изменились. Если пути из START отсутствуют, остановись и сравни фактические имена с реестром. Не создавай пустые правила и не перезаписывай возможные локальные правки. Восстановление имен требует отдельного разбора и проверки содержимого; причина внешнего переименования не определяется одним совпадением хеша.

Сохрани тестовую Markdown-задачу в `docs/backlog` со статусом, фактическими средами, сделанным и следующим шагом. Первый участник создает отдельную запись с тестовым маркером в `.AI/memory` и ссылку в MEMORY.md. Следующим свежим сессиям передавай только путь задачи: они должны самостоятельно найти запись и маркер, назвать предыдущий результат и сохранить продолжение. Общий проектный контекст читай через START; не передавай пересказ чата как замену файловой памяти. После подтверждения выбранной последовательности перенеси задачу в `docs/done` с прежним ID и обнови ссылки на нее. Запиши предел проверки: файловая память, конкретные среды, отдельно проверенные либо непроверенные native memory и vector search.

Проверяй разработку и восстановление только на отдельной временной копии. Подготовленная для ручного теста папка пользователя остается в legacy-раскладке до его запуска; исходный клиент не изменяется.

В постоянном контексте достаточно короткой ссылки: "Миграция legacy в .AI - только по явному запросу через migrations/ai-layout.prompt.md". Не помещай всю процедуру во входы каждого проекта.
