Файл-инструкция для проектов, подключенных к канону claude-toolkit. Открой Claude Code в **корне проекта** и попроси выполнить этот файл (например: `выполни инструкции из <путь>/sync-from-canon.prompt.md`, либо просто скажи "сделай синк с canon" или "sync canon").

Когда применять: проект bootstrap'нут от claude-toolkit и имеет `.claude/canon.yaml`. Промт делает две равноправные вещи: (1) тянет свежие версии уже **отслеживаемых** канонических правил/агентов/скиллов/скриптов, сравнивает с локальными копиями и по каждому расхождению спрашивает разрешения; (2) через **autodiscovery** находит канон-файлы, добавленные в репо ПОСЛЕ bootstrap проекта (их еще нет в `files[]`), и предлагает их донести. Вторая половина так же обязательна, как первая, - без нее новые канон-файлы не попадают в проект никогда (диф их не видит, проект про них не знает).

Промт **идемпотентен**: на уже синхронизированном проекте отрабатывает как no-op - ШАГ 2 выводит "расхождений нет" и промт выходит, ничего не трогая.

**ВАЖНО.** Никаких правок до явного "ок". Сначала аудит, потом план с подтверждением, потом пофайловый диалог - и только по отдельному "да" обновляется каждый файл. Файлы вне скоупа не трогаешь. Если на любом шаге что-то странное (нет `canon.yaml`, файл убран из канона, нестандартная структура) - остановись и спроси, а не "делай как умеешь".

# Задача: синхронизация проекта с каноном claude-toolkit

**Запускай из корня проекта.** Все пути относительные.

## Что делает sync

Источник истины - `.claude/canon.yaml` проекта: где канон (`raw_base`), какие файлы отслеживаются. sync читает его, фетчит канон по HTTP, ничего не знает о filesystem-расположении клона claude-toolkit. Помимо обновления отслеживаемых файлов sync находит канон-файлы, появившиеся в репо после bootstrap проекта, и проектные файлы - кандидаты на вынос в канон.

**Источник - только HTTP, точными байтами.** Канон тяни исключительно по HTTP с `raw_base`. Проект не знает и не должен искать локальный клон claude-toolkit: никаких поисков папок на машине, никаких git-путей к клону - только `raw_base`. Тяни **точными байтами**: `curl -fsSL <raw_base>/<file>` (репо публичный), а не `WebFetch` - последний прогоняет страницу через markdown и маленькую модель, что ломает побайтовое сравнение (пробелы, финальные переносы, особенно `.py`). Учитывай, что `raw.githubusercontent.com` отдает CDN-кешированный контент (кеш ~минуты): если только что запушил коммит в канон, подожди пару минут - по raw-URL он может быть еще не виден.

**Если `raw_base` (raw.githubusercontent.com) недоступен** - тяни те же байты в обход, не теряя byte-exact. Симптом: GET на raw-хост падает на TLS (`curl` - `SSL_ERROR_SYSCALL`, `WebFetch` - "certificate verification error") - типично для сетей за РКН и корпоративных периметров, блокирующих CDN (Fastly). При этом `github.com` и `api.github.com` обычно остаются доступны (другой хостинг/IP). Порядок фолбэка:

1. **GitHub Contents API с raw media type** - отдает идентичные raw-URL байты (в отличие от лоссового `WebFetch`):

   ```
   curl -fsSL -H "Accept: application/vnd.github.raw" \
     "https://api.github.com/repos/<owner>/<repo>/contents/<path>?ref=<branch>"
   ```

   `<owner>/<repo>` и `<branch>` выводятся из `canon.repo` и `canon.branch` в `canon.yaml`; `<path>` - канонический путь файла (`manifest.yaml`, `rules/<...>` и т.д.).
2. **Фолбэк при `403`** (rate-limit неавторизованного API - 60 req/час, выбивается на большом синке): `git clone --depth 1 --branch <branch> https://github.com/<owner>/<repo> <tmp>`, где `<tmp>` - системная временная папка вне проекта (`$(mktemp -d)`, не внутрь рабочего дерева). `--branch <branch>` обязателен: без него клонируется дефолтная ветка репозитория, а `canon.branch` может быть другой - байты приедут не с той ревизии. Копируй файлы из этого свежего клона (git-блобы авторитетны, byte-exact); актуальность тика (HEAD ветки) сверяй через `git ls-remote <url> <branch>`. По завершении синка удали клон (`rm -rf <tmp>`). Это **не** подхват локального клона claude-toolkit с машины (изоляция сохраняется): репо клонируется заново по сети как одноразовый источник и после синка выбрасывается. Единственное санкционированное место, где байты берутся не HTTP-фетчем raw - и только при заблокированном CDN; обычный путь остается `curl <raw_base>`.

`WebFetch` для byte-exact непригоден в принципе (markdown + модель ломают пробелы/переносы, особенно в `.py`) - годится лишь грубым фолбэком на чтение глазами, не на сравнение хешей. Обходной путь применяется везде, где предписан `curl -fsSL <raw_base>/...` (база снимка, 1b, 1c, 4b, 4d, ШАГ 5).

## Маппинг канон-пути -> локального пути

Для каждого файла из `canon.yaml.files` локальный путь в проекте определяется по началу канон-пути:

- `rules/<...>`, `agents/<...>`, `skills/<...>`, `commands/<...>` -> `.claude/<тот же путь>` (правила, агенты, скиллы и слэш-команды живут в `.claude/`).
- `scripts/<...>` -> `<тот же путь>` в корне проекта (исполняемые скрипты без `.claude/`-префикса, потому что сами скрипты ожидают этот путь при поиске `PROJECT_ROOT`).

Везде ниже под "локальный путь файла из канона" подразумевается результат этого маппинга. При сравнении, чтении, записи, удалении - используй именно его, а не голое `.claude/<file>`.

## База снимка (`file_hashes`) и трехстороннее сравнение

`canon.yaml.file_hashes` - карта `<канон-путь>: <sha256>`, где хеш = sha256 **канонических байт** файла на момент его последней установки (bootstrap) или обновления (sync). Это **база** снимка - точка отсчета, от которой меряется расхождение.

Зачем база: без нее sync видит только "локальная копия != канон" и не знает причину - правил ли проект файл локально, или канон ушел вперед. С базой расхождение раскладывается на три разных случая с разной безопасностью перезаписи (см. 1c).

sha256 считай точными байтами:

- локальный файл: `shasum -a 256 <локальный путь> | awk '{print $1}'` (на Linux - `sha256sum <путь> | awk '{print $1}'`);
- канон: `curl -fsSL <raw_base>/<files[i]> | shasum -a 256 | awk '{print $1}'` - те же байты, что сравниваешь в 1c.

Если в `canon.yaml` нет секции `file_hashes` или нет записи по конкретному файлу - база этого файла **неизвестна** (старый снимок, до введения хешей). Тогда sync по нему деградирует к бинарному сравнению (как раньше) и при первом же совпадении/обновлении проставляет базу - дальше файл отслеживается трехсторонне.

## ШАГ 1. Аудит (только чтение, ничего не меняй)

**Аудит состоит из двух равно обязательных половин - пропустить нельзя ни одну:**

- **(A) Диф отслеживаемых файлов** - `1c`: сверка каждого файла из `files[]` с каноном. Видимая, "очевидная" часть синка.
- **(B) Autodiscovery новых файлов** - `1b` (фетч манифеста) + `1d` (сверка манифеста с `canon.yaml`): единственный канал, которым в проект попадают канон-файлы, добавленные ПОСЛЕ его bootstrap. Пропустишь - такие файлы (классический пример: скилл/скрипт, доехавший в канон позже bootstrap проекта) не всплывут никогда: диф их не видит, проект про них не знает.

**Гейт.** Пока `1b` и `1d` не выполнены, аудит не завершен - переходить к ШАГ 2 и выводить план запрещено. Если autodiscovery в этом прогоне технически невозможен (манифест не зафетчился, см. 1b; либо `project_type` пуст, см. 1d) - это не "молчаливый пропуск", а ограничение, которое ты явно фиксируешь отдельной строкой в ШАГ 2.

### 1a. Прочитай `.claude/canon.yaml`

`pwd` -> должна быть корнем проекта (есть `.claude/` или `CLAUDE.md`).

Прочитай `.claude/canon.yaml`. **Если файла нет** - проект не bootstrap'нут от claude-toolkit. Сообщи: "В проекте нет `.claude/canon.yaml` - синхронизировать нечего. Чтобы подключить канон, запусти bootstrap-цепочку (`start.md`)." и **остановись**.

Из `canon.yaml` возьми: `project_type`, `canon.raw_base`, `canon.branch`, списки `files[]`, `local_only[]`, `skip_sync[]`, `upstream_pending[]`, карту `file_hashes` (база-хеши снимков, может отсутствовать в старых проектах). Проверь заодно наличие `.claude/canon.ledger.json`: если он есть - проект на canon-fleet-схеме, и реестр pending живет в нем, а не в `canon.yaml` (детали в 1f; пустой `canon.yaml.upstream_pending` в таком проекте не значит "кандидатов нет"). Покажи кратко: типы проекта (список), база канона, сколько файлов отслеживается, есть ли что-то в `skip_sync` / `upstream_pending`, какой реестр pending активен, есть ли секция `file_hashes`.

`project_type` - **всегда список** (например, `[coding]` или `[wiki, coding, documentation]`). Возможные случаи и обработка:

- Список с одним или несколькими валидными типами - норма, ничего особенного.
- Пустой список `[]`, пустая строка `""`, или поле отсутствует - старый canon.yaml до наполнения. Не остановись, продолжай аудит, но в ШАГ 2 отдельным пунктом предложишь его задать - без `project_type` autodiscovery новых файлов (1d) не работает. Пустая строка `""` дополнительно требует миграции формата в список на ШАГ 4g (но это делается одним движением вместе с заполнением).
- **Непустая скаляр-строка с валидным типом** (`project_type: coding`, старый формат до перехода на список) - помечай для **миграции формата**: внутри аудита трактуй как `[<строка>]`, в ШАГ 2 предупреди о миграции, в ШАГ 4g перепишешь поле в список. Валидные значения: `coding`, `management`, `education`, `documentation`, `wiki`.
- **Непустая скаляр-строка с невалидным значением** - не трактуй как тип. Сообщи в ШАГ 2 как ошибку: "в `canon.yaml -> project_type` лежит строка `<значение>`, это не валидный тип. Перезаписать на пустой список и задать типы заново?". Без ответа не правь.

### 1b. Фетчи манифест

Получи `manifest.yaml` точными байтами: `curl -fsSL <raw_base>/manifest.yaml`. Если raw-хост заблокирован - обходной путь из секции фетча (Contents API / клон); `WebFetch` для сравнения непригоден (лоссовый). Это полный список канон-файлов по типам (`universal`, `coding`, `documentation`, `wiki`, `management`, `education`).

Если фетч не удался (404, репо без манифеста) - autodiscovery новых канон-файлов в этом прогоне недоступен. Зафиксируй это и продолжай только с `files[]` из `canon.yaml`.

### 1c. Сравни отслеживаемые файлы (трехстороннее)

Для каждого `files[i]` из `canon.yaml`, **кроме** тех, что в `skip_sync`:

- `curl -fsSL <raw_base>/<files[i]>` - каноническая версия точными байтами (при заблокированном raw-хосте - обходной путь из секции фетча; `WebFetch` лоссовый и врет побайтовое сравнение). Посчитай ее sha256 - это `upstream`.
- Локальная копия по маппингу (см. блок "Маппинг"): для `rules/`, `agents/`, `skills/`, `commands/` - `.claude/<files[i]>`; для `scripts/` - `<files[i]>` в корне. Посчитай ее sha256 - это `local` (если файл есть).
- `base` = `file_hashes[files[i]]` из `canon.yaml` (может отсутствовать).

Классифицируй:

- **нет локально** - локального файла физически нет (путь по маппингу отсутствует).
- **нет в каноне** - фетч вернул 404 (`curl -f` завершается с ошибкой; файл убран из канона).
- **совпадает** - `local == upstream` (несущественные различия в конечных переводах строки игнорируй). Если при этом `base` отсутствует или != `upstream` - пометь на **бэкфилл базы**: на ШАГ 4 проставим `file_hashes[files[i]] = upstream`, без вопроса (это просто фиксация факта).
- `local != upstream` - расхождение; раскрой его по базе:
  - **база неизвестна** - записи в `file_hashes` нет. Направление расхождения определить нельзя (старый снимок). Обрабатывается как раньше - бинарно "разошелся", решает пользователь; после действия база проставляется.
  - **устарел** - `local == base`, `upstream != base`. Канон ушел вперед, проект файл не трогал. Обновление безопасно - локальных правок нет.
  - **локальная правка** - `local != base`, `upstream == base`. Проект правил файл локально, канон относительно базы не менялся. Это сознательный локальный форк - обновлять нечего (канон тот же), а перезапись затрет правки.
  - **конфликт** - `local != base`, `upstream != base`. Разошлись оба: и проект правил локально, и канон ушел вперед. Перезапись каноном затрет локальные правки.

**tracked-superset** (локальный файл содержит весь канонический текст целиком плюс надстройку сверху) - дополнительная пометка для случаев "локальная правка" / "конфликт" / "база неизвестна": проект сознательно расширил файл, прямое обновление затрет надстройку. Для "базы неизвестна" это основной сигнал направления.

### 1d. Autodiscovery новых канон-файлов (если 1b удался и `project_type` задан)

Если `project_type` - пустой список или поле отсутствует, autodiscovery в этом прогоне пропускается (нет способа определить, файлы каких типов предлагать). В ШАГ 2 ты предложишь пользователю задать `project_type`; после этого следующий sync сделает autodiscovery нормально.

Если `project_type` - скаляр-строка (старый формат), для целей autodiscovery трактуй как `[<строка>]`; миграция формата пройдет в 4g.

Иначе:

Собери из манифеста все файлы. **Новые канон-файлы** = есть в манифесте, но нет ни в `files[]`, ни в `skip_sync`, ни в `local_only` проекта.

Тип-набор проекта = `[universal] + project_type`. Секция `universal` всегда в наборе; за ней - все типы из списка `project_type` (для мультиспециализированного проекта это несколько секций).

- Новые файлы из секций тип-набора - **кандидаты на добавление**. Если файл встречается сразу в нескольких типах проекта (теоретически), считай его один раз.
- Новые файлы из секций вне тип-набора - по умолчанию не предлагай. Но прежде проверь **сигнал неполного `project_type`**: для каждого типа `T` вне тип-набора посмотри, есть ли в проекте локальные файлы из секции `T` манифеста - по маппингу пути либо уже записанные в `files[]`.
  - **Улик нет** (ни одного файла секции `T` локально) - тип реально не используется. Упомяни строкой ("доступны канон-файлы для типов <список> - проект их не использует, пропущено") и не предлагай.
  - **Улика есть** (хотя бы один файл секции `T` лежит локально или в `files[]`) - `project_type` почти наверняка задан уже реального: проект уже использует канон типа `T`, но в списке его нет, из-за чего autodiscovery новых файлов этого типа отключен (режим "тихого" неполного типа). В ШАГ 2 предложишь добавить `T` в `project_type`, показав найденные файлы как доказательство. После добавления типа его секция пойдет обычным autodiscovery.

### 1e. Кандидаты на вынос в канон (upstream)

- **local-original:** файлы в `.claude/rules/`, `.claude/agents/`, `.claude/skills/*/`, `.claude/commands/`, которых нет ни в манифесте, ни в `canon.yaml.local_only`, ни среди уже зарегистрированных pending-кандидатов (есть бриф в `toolkit-log/upstream-pending/` или запись в реестре, см. 1f) - зарегистрированное уже в работе, повторно не предлагай, бриф заново не генерируй. Проектные артефакты - возможно, ценны для канона. Для `scripts/` автоматическое выявление local-original не делаем - там лежит много проектных скриптов, не всем место в каноне; вынос делается явно через ручное предложение.
- **tracked-superset** (из 1c): расширенный канон-файл - проектная добавка может быть полезна канону. Уже зарегистрированный pending-кандидат по этому файлу (бриф или запись, см. 1f) повторно не предлагается - иначе каждый прогон пересоздавал бы бриф и рассинхронизировал `candidate_id`.

Для обоих типов: если по этому активу лежат брифы в `toolkit-log/upstream-rejected/` (тот же слаг, возможно с суффиксами даты/порядка - их может накопиться несколько) - сравни текущую дельту кандидата с **объединением** их предложений, не только с последним. Дельта **та же по смыслу** - кандидат уже отклонялся, повторно не предлагай: терминальный вердикт и есть durable-маркер "нет" для этой дельты, иначе каждый синк плодил бы новые rejected-брифы; предложить заново - только по явной просьбе пользователя (или если он сам убрал бриф из `upstream-rejected/`). Дельта **другая** (в активе появилось независимое новое) - это новый кандидат, старый отказ его не покрывает: покажи в ШАГ 2 с пометкой "по активу было отклонение (<бриф>), текущая дельта отличается". Пересечение **частичное** (надстройка = отклоненное ранее + новое сверху) - кандидатом идет только новая часть: бриф в 4e формируй по ней одной, отклоненное в содержимое не включай (в брифе упомяни строкой: остальная надстройка ранее отклонена, см. <бриф>), а в самом вопросе 4e "вынести в канон?" пометь "только новая часть, отклоненное ранее исключено (<бриф>)" - согласие пользователя должно быть информированным. Иначе повторно предложишь уже отклоненное. Сомневаешься - в сопоставлении ли слага, в сравнении ли дельт - не решай сам: покажи в ШАГ 2 строкой "возможно, уже отклонялся: <бриф>".

### 1f. Проверь upstream-кандидатов (каталог + реестр)

**Определи активный реестр pending** - тем же критерием, что `skills/harvest-canon`: есть `.claude/canon.ledger.json` - реестр это его список `upstream_pending` (объекты `{candidate_id, brief_path, source}`, canon-fleet-схема); нет - `canon.yaml.upstream_pending` (строки-пути, legacy). harvest и sync обязаны смотреть в один реестр - иначе pending-записи одной половины невидимы другой, и доехавший в канон кандидат зависает в реестре навсегда. Активный реестр - место **регистрации** (4e); аудит же читает **оба**: если при активном ledger в `canon.yaml.upstream_pending` остались записи - это legacy-хвосты, покажи их в ШАГ 2 (доехавшие вычистятся в 4f, недоехавшие предложи перенести в ledger).

Если ledger существует, но JSON не парсится или списка `upstream_pending` в нем нет - **блокер upstream-части**: зафиксируй в ШАГ 2 отдельной строкой ("ledger битый: <ошибка>; 1f/4e/4f пропущены, нужна ручная починка"), пропусти 1f/4e/4f целиком и продолжай остальной синк. На legacy не откатывайся - молчаливый даунгрейд схемы хуже явной остановки. Запись без `brief_path` не чини и не чисти молча - покажи в ШАГ 2, решает пользователь.

**Источник истины - каталог `toolkit-log/upstream-pending/`, реестр - только индекс поверх него.** Просканируй `toolkit-log/upstream-pending/*.md` плюс файлы, на которые указывают `brief_path` записей реестра вне этого каталога (исторические расположения вроде `toolkit-log/pending/`). Исключение - терминальные папки `toolkit-log/upstream-applied/` и `toolkit-log/upstream-rejected/`: запись, чей `brief_path` указывает туда, - недочищенный после переноса реестр, а не живой кандидат. Такой бриф не сканируй и в pending не возвращай (applied снова классифицировался бы как landed, rejected - как waiting); покажи запись в ШАГ 2 строкой "указывает в терминальную папку - вычистить", сама чистка - гигиена 4f. Каталога нет и реестры пусты - пункт пуст. Legacy-запись не-строка (рукой занесенный объект) - покажи в ШАГ 2, слаг из нее не выводи. По каждому брифу:

- выведи целевые канон-пути - **все** (бриф может нести несколько активов, например скилл + сопровождающий скрипт): из содержимого брифа (заголовок, секции "Предлагаемый путь в каноне" / "Канонический путь" / "Правимый актив"), в крайнем случае - эвристикой из слага имени файла. Однозначно не выводится - покажи бриф в ШАГ 2 отдельной строкой, не гадай молча;
- бриф, целящийся вне канона (другой репозиторий - об этом прямо сказано в самом брифе), - не канон-кандидат: в ШАГ 2 предложи перенести его в `toolkit-log/upstream-rejected/` с пометкой "вне канона" (перенос - в 4f);
- проверь по каждому целевому пути, доехал ли он **в канон**. Сверка - с каноном по HTTP (`curl -fsSL <raw_base>/<путь>`; при заблокированном raw - обходной путь из секции фетча), локальное состояние проекта на вердикт **не влияет**: pending-трекинг - про состояние канона, а локальная копия может быть форком, в `skip_sync`, или отсутствовать вовсе. Путь вне манифеста (`migrations/...`, корневой `README.md` канона) проверяется тем же фетчем - манифест для этой проверки не нужен. Критерий **содержательный, не по занятости пути**: для нового актива "доехал" = файл существует И его содержимое реализует предложение брифа (файл с тем же путем, но чужим содержимым - не приемка кандидата: покажи в ШАГ 2, решает пользователь); для amend-брифа = каноническая версия реализует **каждый пункт** предлагаемой дельты, включая отрицательные требования ("убрать/заменить X") - сверяй по пунктам, побайтовое равенство не требуется;
- **доехали все целевые пути, и по каждому реализованы все пункты** - бриф устарел: кандидат на перенос в `upstream-applied/` и чистку записи реестра, независимо от того, есть ли запись в реестре (бриф-сирота без записи переносится так же);
- реализована **часть** - целевых путей или пунктов дельты - вердикт сам не выноси: покажи в ШАГ 2 раскладку ("реализовано / нет / отклонено автором канона") - решает пользователь: ждать дальше, счесть закрытым (остальное отклонено) или перенести в `upstream-rejected/`. Сомневаешься в смысловой сверке - тоже к пользователю, не гадай: ложный applied необратим (applied-брифы больше не сканируются), ложное ожидание безопасно - кандидат просто подождет еще прогон;
- не доехал - кандидат ждет, ничего не делать. Если пользователь скажет, что кандидат **отклонен** (в канон не пойдет), - его терминальное состояние `upstream-rejected/`, см. 4f: без этого перехода отклоненный бриф висел бы в pending вечно.

Дополнительно сверь реестры с каталогом в обратную сторону: запись, по `brief_path` (ledger) или слагу из пути (legacy) которой файла-брифа нет, - кандидат в сироты. Но прежде чем счесть запись осиротевшей: если `brief_path` ledger-записи похож на канон-путь (без префикса `toolkit-log/`) - поищи `toolkit-log/upstream-pending/<slug из этого пути>.md`: миграция legacy -> ledger могла записать канон-путь вместо пути брифа. Если же `brief_path` - `toolkit-log/`-путь, файла по которому нет (историческое расположение, файл переехал), - поищи файл с тем же именем в `toolkit-log/upstream-pending/`. Нашелся (в любом из двух случаев) - это не сирота: обработай бриф как обычно и в 4f поправь `brief_path` записи. Не нашелся нигде - осиротевший индекс, кандидат на чистку (решение - через план ШАГ 2). Расхождение каталога и реестра всегда чинится в пользу каталога.

### 1g. `project-structure.md` не должен лежать в `.claude/rules/`

Справочная карта структуры живет в **корне проекта** (`project-structure.md`). В `.claude/rules/project-structure.md` ее быть не должно - это устаревшее расположение, ошибка. И в двух местах одновременно ее быть не должно. Проверь (только чтение) наличие `.claude/rules/project-structure.md`:

- **Нет в `.claude/rules/`** - все в порядке, по этому пункту ничего не предлагай.
- **Есть в `.claude/rules/`, а в корне нет** - файл лежит не там: кандидат на перенос в корень.
- **Есть и в `.claude/rules/`, и в корне** - дубль в двух местах: кандидат на удаление копии из `.claude/rules/` (источник истины - корневой файл).

Триггер по этому пункту - именно наличие файла в `.claude/rules/`.

Покажи списком:

- **project_type** - если в 1a список был пустым, поле отсутствует, или это пустая строка `""`, отдельной строкой: "в `canon.yaml` пустой `project_type` - какие типы у проекта? Можно несколько через запятую (coding / management / education / documentation / wiki). Без этого autodiscovery новых канон-файлов отключен." Будет переписано в список `[<значение>]` на ШАГ 4g. Если хочешь сразу добавить еще типы - назови их (например, `[<значение>, wiki]`)."

  Tracked-superset помечай дополнительно: "(расширен проектом - обновление затрет надстройку)".
- **Нет локально** (1c) - файлы из `files[]` без локальной копии: предложу дофетчить.
- **Нет в каноне** (1c) - убраны из канона: блокер, спрошу отдельно.
- **Новые канон-файлы** (1d) - **строка обязательна и присутствует всегда**, даже когда добавлять нечего (тогда явно: "новых канон-файлов в манифесте нет"). Если есть - список кандидатов на добавление + строка про пропущенные не-своего-типа. ## ШАГ 3. Жди "ок"

Жди явного "ок" / "go" / "делай". Это подтверждение разрешает войти в **пофайловый диалог** ШАГ 4 - там по каждому файлу будет отдельный вопрос "да/нет". Без "ок" - не действуй.

## ШАГ 4. Действуй (только после "ок")

### 4a0. Заполни / мигрируй `project_type`

Допустимые значения типов: `coding`, `management`, `education`, `documentation`, `wiki`. `project_type` **всегда** записывается как список, даже если в нем один тип.

Варианты по результатам 1a и ответам пользователя в ШАГ 2:

- **Поле было пустым списком `[]` или отсутствует**, пользователь назвал один или несколько типов через запятую - проставь:

  ```yaml
  project_type: [<тип1>, <тип2>, ...]
  ```

  Каждый тип валидируй по списку выше; невалидные отбрось и сообщи в отчете. Если в ответе ни одного валидного типа - не правь поле, autodiscovery остается отключенным до следующего синка.

- **Поле было скаляр-строкой** (`project_type: coding`) - перепиши в список. Если пользователь в ответ на вопрос про миграцию формата назвал дополнительные типы, включи их:

  ```yaml
  project_type: [<старое-значение>, <дополнительные>]
  ```

  Если пользователь ничего не добавил - просто оберни старое значение в список: `[<старое-значение>]`.

- **Поле уже было списком** - не трогай (если только пользователь явно не попросил что-то добавить/убрать вне рамок sync).

- **Добавление типа по сигналу (1d, 2b)** - если в ШАГ 2 пользователь согласился добавить `<T>` (улика неполного типа), допиши `<T>` в список `project_type` (валидируй по допустимым значениям). Тип-набор расширяется - файлы секции `<T>` пойдут обычным autodiscovery: на следующем синке, либо сразу в этом прогоне, если пересчитаешь 1d по расширенному набору и предложишь их в 4d.

### 4a. Обновление разошедшихся файлов

По каждому файлу из 1c с расхождением спрашивай отдельно (показывай локальный путь по маппингу и тип расхождения). **После любой перезаписи каноном проставляй `file_hashes[<путь>] = upstream`** (база теперь = установленная версия). Для скриптов из `scripts/` после перезаписи сохраняй executable-бит (`chmod +x`).

- **устарел** - "обновить `<путь>`? канон ушел вперед, локальных правок нет, обновление безопасно (да / нет / diff)". При **да** - перезапиши локальной версией из 1c, проставь базу. При **нет** - предложи `skip_sync`.
- **локальная правка** - по умолчанию **не трогаю**: канон относительно базы не менялся, обновлять нечего, а перезапись затрет локальные правки. Сообщи об этом. Если правка ценна для канона - предложи вынести ее (4e, upstream). Файл уже фактически форк - предложи занести в `skip_sync`, чтобы не всплывал каждый синк. Канон не навязывай.
- **конфликт** - предупреди жестко: "и проект правил `<путь>` локально, и канон ушел вперед - прямая перезапись затрет локальные правки. (diff / занести в `skip_sync` / вынести правку в канон 4e / все равно перезаписать каноном)". Перезаписывай только по явному выбору; при перезаписи - проставь базу.
- **база неизвестна** - как раньше: "обновить `<путь>`? (да / нет / diff)". **diff** - опиши различия словами (что добавилось, что убралось, какие формулировки изменились), затем спроси снова. **да** - перезапиши версией из 1c, проставь базу. **нет** - предложи `skip_sync`.

**Бэкфилл базы для совпавших.** Для файлов, классифицированных "совпадает" с пометкой на бэкфилл (база отсутствовала или устарела), проставь `file_hashes[<путь>] = upstream` без вопроса - это фиксация факта, что текущая локальная копия и есть канон.

Для tracked-superset (в "локальной правке" / "конфликте" / "базе неизвестна") перед вопросом выведи предупреждение: перезапись затрет проектную надстройку; рекомендую сначала вынести ее в канон (4e) либо занести файл в `skip_sync`.

Для скриптов из `scripts/` расхождение может означать как устаревшую копию (например, без `iter_dialogs()` прогрева), так и проектные правки исполняемого кода. Tracked-superset для бинарно-чувствительных скриптов не определяется автоматически - база-хеш тут единственный надежный сигнал направления. Перед перезаписью отдельно предупреди: канон заменит локальный скрипт целиком; если в скрипте есть проектные правки - сначала зафиксируй их (`skip_sync` или upstream-вынос в 4e). При перезаписи - сохрани executable-бит (`chmod +x`), проставь базу.

### 4b. Файлы без локальной копии

По каждому "нет локально" спроси: "создать `<локальный путь>` из канона? (да/нет)". При "да" - получи канон точными байтами (`curl -fsSL <raw_base>/<files[i]>`) + запись; промежуточные папки при необходимости создай (папку скилла, `scripts/`). Для скриптов из `scripts/` после записи поставь executable-бит (`chmod +x`). Проставь `file_hashes[<путь>] = sha256` записанных байт.

### 4c. Файлы, убранные из канона

По каждому "нет в каноне" спроси: убрать запись из `files[]` (локальная копия останется обычным файлом проекта) или оставить как есть. Сам файл **не удаляй**.

### 4d. Новые канон-файлы

По каждому кандидату из 1d спроси: "добавить `<локальный путь>` в проект? (да/нет)". Локальный путь определяется по маппингу.

- **да** - получи канон точными байтами (`curl -fsSL <raw_base>/<files[i]>`) + запись, добавь путь в `canon.yaml.files` (в каноническом виде, без подстановки `.claude/`) и проставь `file_hashes[<путь>] = sha256` записанных байт. Если файл - правило, напомни добавить `@`-ссылку в `CLAUDE.md` (по отдельному "ок"). Для скриптов из `scripts/` поставь executable-бит (`chmod +x`).
- **нет** - добавь путь в `canon.yaml.skip_sync` (чтобы не предлагался снова).

### 4e. Upstream-кандидаты

По каждому кандидату из 1e спроси: "вынести в канон? (да/нет)".

- **да** - сгенерируй бриф (формат ниже), зарегистрируй его в **активном реестре pending** (критерий из 1f): canon-fleet - объект `{"candidate_id": "<sha256 содержимого брифа>", "brief_path": "toolkit-log/upstream-pending/<slug>.md", "source": "sync-from-canon"}` в `canon.ledger.json -> upstream_pending` (дедуп по `brief_path`, точечной правкой JSON); legacy - предполагаемый канонический путь в `canon.yaml.upstream_pending`. Регистрировать в оба реестра сразу нельзя - harvest и sync смотрят в один, второй станет расхождением.
- **нет** для local-original - предложи занести путь в `canon.yaml.local_only` (чтобы файл не всплывал каждый синк).

Legacy-запись в `upstream_pending` - предполагаемый канонический путь файла (напр. `agents/my-extra-agent.md`). Бриф кладется в `toolkit-log/upstream-pending/<slug>.md`, где `<slug>` - имя файла без расширения (при коллизии имен добавь префикс директории, напр. `agents-my-extra-agent`). slug должен однозначно выводиться из пути, а целевой путь - дублироваться в заголовке брифа: sync на следующих прогонах ищет бриф по слагу, а путь выводит из содержимого.

```markdown
# Upstream-кандидат: <предлагаемый путь в каноне, напр. rules/foo.md>

Бриф для Claude в локальном клоне репозитория `claude-toolkit`. Цель - оценить файл и, если годится, добавить в канон.

## Откуда

- Проект: `<имя проекта или pwd>`
- Дата: <ISO-дата>
- Тип кандидата: local-original | tracked-superset

## Предлагаемый путь в каноне

`<rules|agents|skills|scripts/...>/<имя>`

## Содержимое

\`\`\`markdown
<для local-original - полное содержимое файла;
 для tracked-superset - только проектная добавка сверх канона,
 с пометкой, к какому канон-файлу она относится>
\`\`\`

## Rationale

<почему ценно для канона; для какого типа проектов; универсальное или тип-специфичное>

## Что сделать в клоне claude-toolkit

1. Отревьюить содержимое, депроектировать (убрать проектные имена/пути).
2. Положить в `<путь в каноне>`.
3. Зарегистрировать в `manifest.yaml` (секция по типу) по правилам раздела "Регистрация нового канон-файла" в `CLAUDE.md` - манифест единственный реестр списков, bootstrap-промты тянут файлы из него сами (руками в bootstrap не дописывать).
4. Закоммитить и запушить.
5. На следующем синке проект увидит файл в каноне и сам вычистит запись из `upstream_pending`.
```

### 4f. Чистка upstream-кандидатов

Решения этого шага уже показаны в плане ШАГ 2, и общее "ок" их покрывает - пофайловый вопрос не нужен (в отличие от 4a-4e, где правятся рабочие файлы проекта; здесь - только переносы брифов внутри `toolkit-log/` и записи реестра).

По кандидатам из 1f, для каждого брифа, все целевые пути которого доехали в канон (критерий из 1f - содержательная сверка с каноном, не с локальной копией):

- **непосредственно перед переносом повтори свежую сверку по критерию 1f - на одной ревизии канона**: возьми `<sha>` = HEAD ветки из `git ls-remote https://github.com/<owner>/<repo> <branch>`, фетчи **все** целевые пути кандидата через Contents API с `?ref=<sha>` (пункт 1 секции фетча), а после сверки повтори `git ls-remote` - HEAD сдвинулся, значит сверка недействительна: повтори с новым sha, а если и после повтора sha снова разошелся - не переноси, покажи пользователю. Ошибку фетча (`403` - rate-limit неавторизованного API) со сдвигом HEAD не путай: на нее - фолбэк из секции фетча (одноразовый клон с `--branch <branch>`), причем клон сверь с захваченной ревизией: `git -C <tmp> rev-parse HEAD` != `<sha>` - обращайся как со сдвигом HEAD (повтор, затем к пользователю), иначе сверка пройдет по байтам другой ревизии. raw и `WebFetch` фолбэком не годятся. Точечные фетчи каждого целевого пути по `?ref=<branch>` не годятся: между ними ветка может сдвинуться, и "все пункты реализованы" сложится из двух ревизий, ни одна из которых не содержит кандидата целиком. raw-CDN не годится тоже: повторный запрос внутри кеш-TTL вернет тот же устаревший ответ и не заметит откат. Вердикт 1f - это снимок аудита, а перенос в applied необратим (applied-брифы больше не сканируются); разошлось со снимком - не переноси, покажи пользователю;
- перенеси файл брифа из его **фактического расположения, найденного в 1f** (обычно `toolkit-log/upstream-pending/<slug>.md`, но бриф мог лежать и в историческом месте вроде `toolkit-log/pending/`) в `toolkit-log/upstream-applied/<slug>.md` (папку при необходимости создай). Перенос всегда **без перезаписи существующих файлов назначения**: занято `<slug>.md` (повторный кандидат по тому же активу) - переноси как `<slug>-<ISO-дата>.md`, занято и оно - добавляй порядковый суффикс (`<slug>-<ISO-дата>-2.md`, `-3`, ...); история брифов не теряется. То же правило - для переносов в `upstream-rejected/`. Отсутствие записи в реестре переносу не мешает - источник истины каталог;
- вычисти соответствующую запись из активного реестра: ledger - объект по `brief_path`; legacy - строку-путь из `canon.yaml.upstream_pending`. Запись-дубль во втором реестре (legacy-хвост доехавшего брифа) - вычисти тоже.

**Частично доехавший кандидат, по которому пользователь в ШАГ 2/3 выбрал "счесть закрытым (остальное отклонено)"**, переносится в `upstream-applied/` тем же порядком, с двумя отличиями: свежая сверка перед переносом - только по пунктам, признанным реализованными (отклоненные пункты не перепроверяются - это решение пользователя, не состояние канона), и в конец брифа допиши вердикт (дата, "закрыт решением пользователя: реализовано частично, остальное отклонено", раскладка по пунктам). Без этой ветки выбор "счесть закрытым" был бы неисполним и вопрос повторялся бы вечно. Выбор "ждать дальше" не персистится: при неизменном каноне тот же вопрос поднимется на следующем прогоне - это намеренно (канон мог измениться, а ложный applied необратим; ложный повторный вопрос безопасен).

**Гигиена реестра** - не привязана к приземлению, выполняется и для ждущих кандидатов (иначе ошибочная запись висела бы до самого applied и никогда не была бы полезна):

- ошибочный `brief_path` (канон-путь вместо пути брифа либо историческое расположение, сопоставлен в 1f по слагу/имени) - поправь на реальный путь брифа;
- записи, чей `brief_path` указывает в терминальные `upstream-applied/` / `upstream-rejected/` (из 1f - недочищенный после переноса реестр), - вычисти;
- осиротевшие записи (из 1f, после проверки по слагу) - вычисти;
- недоехавшие legacy-хвосты при активном ledger - перенеси в ledger записью `{"candidate_id": "<sha256 содержимого брифа>", "brief_path": "toolkit-log/upstream-pending/<slug>.md", "source": "legacy-canon-yaml"}` и убери из `canon.yaml.upstream_pending`. Перед добавлением - дедуп по `brief_path`: запись уже есть - ничего не добавляй, только убери YAML-строку.

**Отклоненные и внеканонные брифы** (по решению пользователя из ШАГ 2): перенеси в `toolkit-log/upstream-rejected/<slug>.md`, дописав в конец файла вердикт (дата, причина, "правок в канон не внесено"), запись из реестра вычисти. Отклоненный кандидат не доедет в канон никогда - без этого перехода он вечно висел бы в pending и всплывал каждый прогон.

**Правка ledger** - программно: загрузить JSON, изменить только записи `upstream_pending`, сохранить с тем же отступом. Полная пересериализация допустима (у JSON нет построчного патча), но чужие ключи и поля не трогаются содержательно. После записи перечитай файл: JSON валиден, прочие поля на месте.

### 4g. Обнови `.claude/canon.yaml`

Правь **точечно, не перезаписывая файл целиком**: дополни `files`, `local_only`, `skip_sync`, `upstream_pending`, `file_hashes` по решениям выше. В canon-fleet-проекте записи pending живут в `canon.ledger.json` и правятся в 4e/4f - `canon.yaml.upstream_pending` тогда здесь не пополняется (кроме чистки legacy-хвостов по 4f). Комментарии на строках списков сохрани. Пустой список `[]` при первом добавлении разверни в блочную форму. Если секции `file_hashes` в файле еще нет (старый снимок), а синк проставил хотя бы одну базу - заведи ее как карту (`<путь>: <sha256>`) рядом с `files`. Записи `file_hashes` должны быть только для путей из `files[]`; при удалении записи из `files` (4c) убери и соответствующий хеш. Если в 4a0 был проставлен или мигрирован `project_type` - убедись, что поле записано на верхнем уровне **как список** (flow-style `[a, b]` или блочная форма с дефисами), даже для одного элемента. Скаляр-строка после 4a0 в файле остаться не должна.

### 4h. Убрать `project-structure.md` из `.claude/rules/`

Только если в 1g зафиксировано наличие `.claude/rules/project-structure.md`. Если файла там нет - этот шаг пропусти целиком.

- **В `.claude/rules/` есть, в корне нет** (лежит не там) - спроси "перенести `project-structure.md` в корень проекта и поправить @-импорт в `CLAUDE.md`? (да/нет)". При "да":
  - перемести файл: если проект под git и файл отслеживается - `git mv .claude/rules/project-structure.md project-structure.md`; иначе перечитай содержимое, запиши в `project-structure.md` в корне, удали старый;
  - в `CLAUDE.md` замени `@.claude/rules/project-structure.md` на `@project-structure.md`.
- **Есть и в `.claude/rules/`, и в корне** (дубль) - спроси "убрать дубль `project-structure.md` из `.claude/rules/` (источник истины - корневой файл)? (да/нет)". При "да": удали `.claude/rules/project-structure.md`, проверь, что @-импорт в `CLAUDE.md` указывает на `@project-structure.md` (если остался старый путь - поправь).

`canon.yaml` в обоих случаях не трогай (`project-structure.md` - шаблон, в `files` не отслеживается). Полный самодостаточный вариант - в `migrations/move-project-structure.prompt.md`.

## ШАГ 5. Проверка

- Перед финальной сверкой сделай свежий `curl`-фетч обновленных файлов (при заблокированном raw-хосте - тем же обходным путем из секции фетча) - канон мог получить коммиты за время прогона синка; сверяй локальные копии против актуального тика, а не против снимка с ШАГ 1. Учитывай CDN-кеш raw (~минуты): если канон правился только что, расхождение может быть артефактом кеша, а не реальной разницей.
- Для каждого обновленного/добавленного файла перепроверь: локальная копия совпадает с канонической.
- `canon.yaml`: YAML валиден, в `files` нет дублей, нет пересечения `files` и `skip_sync`.
- `file_hashes`: каждая запись соответствует пути из `files[]` (нет хешей-сирот для путей вне `files`); каждый перезаписанный/созданный/добавленный в этом синке файл получил актуальную базу; значения - 64-символьные hex sha256.
- Для каждого upstream-кандидата с ответом "да": бриф `toolkit-log/upstream-pending/<slug>.md` создан, запись в активном реестре pending есть (ledger или `canon.yaml`, критерий из 1f).
- После 4f: у каждого брифа в `upstream-pending/` целевые пути еще не доехали в канон целиком (доехавшие перенесены в `upstream-applied/`, отклоненные - в `upstream-rejected/`), в реестрах нет записей без файла-брифа.
- Если правился `canon.ledger.json` - перечитай его: JSON валиден, поля вне `upstream_pending` не изменились.

## ШАГ 6. Отчет (в чат)

- Обновлено: список файлов.
- Пропущено по моему решению: список + куда занесено (`skip_sync`).
- Добавлено новых канон-файлов: список.
- Upstream-кандидаты: что оформлено в брифы, что занесено в `local_only`.
- `upstream_pending`: что вычищено, какие брифы перенесены в `upstream-applied/` / `upstream-rejected/`, что ждет (в т.ч. частично доехавшие).
- `project-structure.md`: перенесен в корень / убран дубль из `.claude/rules/` / не лежал в правилах (по 4h).
- Если ничего не делалось - "проект уже синхронизирован с каноном".

## Критерий готовности

- Каждый файл из `files[]` (вне `skip_sync`) либо совпадает с каноном, либо сознательно оставлен расходиться (локальная правка / конфликт без перезаписи / `skip_sync`).
- `canon.yaml` отражает решения: новые файлы в `files`, отказы в `skip_sync`, кандидаты в активном реестре pending (`canon.yaml.upstream_pending` либо `canon.ledger.json` - критерий из 1f) / `local_only`, актуальные базы в `file_hashes`.
- Каждый upstream-кандидат с ответом "да" имеет самодостаточный бриф в `toolkit-log/upstream-pending/`.
- На уже синхронизированном проекте промт отрабатывает как no-op: ШАГ 2 выводит "расхождений нет", дальше шаги не идут.

## Правила безопасности

- Никаких правок до "ок" после плана.
- Каждый файл обновляется/добавляется только по отдельному "да" в пофайловом диалоге.
- Файлы в `skip_sync` не трогаются.
- Ничего вне `.claude/`, `scripts/` и `toolkit-log/` не меняется. Исключения: `@`-ссылки в `CLAUDE.md` при добавлении нового правила (по отдельному "ок"); `scripts/<имя>` при обновлении/создании канонических скриптов через маппинг (по тому же пофайловому диалогу); перенос `project-structure.md` из `.claude/rules/` в корень (или удаление дубля из `.claude/rules/`) и правка его @-импорта в `CLAUDE.md` (4h, по отдельному "да").
- `canon.yaml` правится точечно, не пересоздается. В `canon.ledger.json` содержательно правятся только записи `upstream_pending` (пересериализация допустима, чужие ключи сохраняются байт-в-байт по смыслу; после записи - перечитать и провалидировать, см. 4f).
- Брифы из `toolkit-log/upstream-pending/` не удаляются - только переносятся (в `upstream-applied/` или `upstream-rejected/`), без перезаписи существующих файлов назначения.
- Файлы не удаляются: для "нет в каноне" убирается только запись из `files[]`, сам файл остается.
- Никаких `rm -rf` и git-операций по проекту. Единственное исключение - обходной фолбэк при заблокированном CDN (секция фетча): одноразовый `git clone` канона во временную папку **вне проекта** и ее последующая очистка (`rm -rf <tmp>`). Репозиторий и рабочее дерево проекта это не затрагивает.
