Файл-инструкция для проектов, подключенных к канону claude-toolkit. Открой Claude Code в **корне проекта** и попроси выполнить этот файл (например: `выполни инструкции из <путь>/sync-from-canon.prompt.md`, либо просто скажи "сделай синк с canon").

Когда применять: проект bootstrap'нут от claude-toolkit и имеет `.claude/canon.yaml`. Промт тянет свежие версии канонических правил/агентов/скиллов, сравнивает с локальными копиями и по каждому расхождению спрашивает разрешения.

Промт **идемпотентен**: на уже синхронизированном проекте отрабатывает как no-op - ШАГ 2 выводит "расхождений нет" и промт выходит, ничего не трогая.

**ВАЖНО.** Никаких правок до явного "ок". Сначала аудит, потом план с подтверждением, потом пофайловый диалог - и только по отдельному "да" обновляется каждый файл. Файлы вне скоупа не трогаешь. Если на любом шаге что-то странное (нет `canon.yaml`, файл убран из канона, нестандартная структура) - остановись и спроси, а не "делай как умеешь".

# Задача: синхронизация проекта с каноном claude-toolkit

**Запускай из корня проекта.** Все пути относительные.

## Что делает sync

Источник истины - `.claude/canon.yaml` проекта: где канон (`raw_base`), какие файлы отслеживаются. sync читает его, фетчит канон по HTTP, ничего не знает о filesystem-расположении клона claude-toolkit. Помимо обновления отслеживаемых файлов sync находит канон-файлы, появившиеся в репо после bootstrap проекта, и проектные файлы - кандидаты на вынос в канон.

## ШАГ 1. Аудит (только чтение, ничего не меняй)

### 1a. Прочитай `.claude/canon.yaml`

`pwd` -> должна быть корнем проекта (есть `.claude/` или `CLAUDE.md`).

Прочитай `.claude/canon.yaml`. **Если файла нет** - проект не bootstrap'нут от claude-toolkit. Сообщи: "В проекте нет `.claude/canon.yaml` - синхронизировать нечего. Чтобы подключить канон, запусти bootstrap-цепочку (`start.md`)." и **остановись**.

Из `canon.yaml` возьми: `project_type`, `canon.raw_base`, `canon.branch`, списки `files[]`, `local_only[]`, `skip_sync[]`, `upstream_pending[]`. Покажи кратко: тип проекта, база канона, сколько файлов отслеживается, есть ли что-то в `skip_sync` / `upstream_pending`.

Если `project_type` отсутствует или пустое (`""`) - это старый canon.yaml, бутстрапленный до введения поля. Не остановись, продолжай аудит, но в ШАГ 2 отдельным пунктом предложишь его проставить - без `project_type` autodiscovery новых файлов (1d) не работает.

### 1b. Фетчи манифест

`WebFetch <raw_base>/manifest.yaml` - полный список канон-файлов по типам (`universal`, `coding`, `documentation`, `claude-tooling`, `wiki`, `management`, `education`).

Если фетч не удался (404, репо без манифеста) - autodiscovery новых канон-файлов в этом прогоне недоступен. Зафиксируй это и продолжай только с `files[]` из `canon.yaml`.

### 1c. Сравни отслеживаемые файлы

Для каждого `files[i]` из `canon.yaml`, **кроме** тех, что в `skip_sync`:

- `WebFetch <raw_base>/<files[i]>` - каноническая версия.
- Сравни с локальным `.claude/<files[i]>`.

Классифицируй:

- **совпадает** - локальная копия идентична канону (несущественные различия в конечных переводах строки игнорируй).
- **разошелся** - содержимое отличается.
- **нет локально** - файл есть в `files[]`, но `.claude/<file>` физически отсутствует.
- **нет в каноне** - WebFetch вернул 404 (файл убран из канона).

Среди "разошелся" отметь **tracked-superset**: локальный файл содержит весь канонический текст целиком плюс что-то сверху. Такой файл проект сознательно расширил - прямое обновление из канона затрет проектные добавки.

### 1d. Autodiscovery новых канон-файлов (если 1b удался и `project_type` задан)

Если `project_type` пустое или отсутствует - autodiscovery в этом прогоне пропускается (нет однозначного способа определить, файлы какого типа предлагать). В ШАГ 2 ты предложишь пользователю проставить `project_type`; после этого следующий sync сделает autodiscovery нормально.

Иначе:

Собери из манифеста все файлы. **Новые канон-файлы** = есть в манифесте, но нет ни в `files[]`, ни в `skip_sync`, ни в `local_only` проекта.

Тип-набор проекта = `[universal, <project_type>]`. Секция `universal` всегда в наборе.

- Новые файлы из секций тип-набора - **кандидаты на добавление**.
- Новые файлы из секций вне тип-набора - не предлагай, только упомяни строкой ("доступны канон-файлы для типа X - проект его не использует, пропущено").

### 1e. Кандидаты на вынос в канон (upstream)

- **local-original:** файлы в `.claude/rules/`, `.claude/agents/`, `.claude/skills/*/`, которых нет ни в манифесте, ни в `canon.yaml.local_only`. Проектные артефакты - возможно, ценны для канона.
- **tracked-superset** (из 1c): расширенный канон-файл - проектная добавка может быть полезна канону.

### 1f. Проверь `upstream_pending`

Для каждой записи в `upstream_pending`: если файл уже доехал в канон (есть в манифесте, и локальная копия совпадает с канонической версией) - запись устарела, на ШАГ 4 будет вычищена.

## ШАГ 2. План

Покажи списком:

- **project_type** - если в 1a поле было пустым/отсутствовало, отдельной строкой: "в `canon.yaml` нет `project_type` - какой тип проекта? (coding / management / education / documentation / claude-tooling / wiki). Без этого autodiscovery новых канон-файлов отключен."
- **Обновления** (1c, "разошелся") - пути файлов. Tracked-superset помечай явно: "(расширен проектом - обновление затрет добавки)".
- **Нет локально** (1c) - файлы из `files[]` без локальной копии: предложу дофетчить.
- **Нет в каноне** (1c) - убраны из канона: блокер, спрошу отдельно.
- **Новые канон-файлы** (1d) - кандидаты на добавление + строка про пропущенные не-своего-типа. Если 1d был пропущен (нет `project_type`) - вместо этого строка "autodiscovery пропущен - сначала задай project_type".
- **Upstream-кандидаты** (1e) - local-original и tracked-superset.
- **Чистка `upstream_pending`** (1f) - какие записи устарели.
- **Не трону:** файлы в `skip_sync`; все вне `.claude/` и `toolkit-log/`.

**Если все пусто** (нет расхождений, новых файлов, кандидатов, устаревших pending, и `project_type` уже задан) - выведи "проект синхронизирован с каноном - расхождений нет" и **выйди**, ничего не меняя.

## ШАГ 3. Жди "ок"

Жди явного "ок" / "go" / "делай". Это подтверждение разрешает войти в **пофайловый диалог** ШАГ 4 - там по каждому файлу будет отдельный вопрос "да/нет". Без "ок" - не действуй.

## ШАГ 4. Действуй (только после "ок")

### 4a0. Заполни `project_type` (если был пустым/отсутствовал)

Если в 1a поле `project_type` отсутствовало или было `""`, и пользователь в ответ на вопрос ШАГ 2 назвал тип - проставь его на верхнем уровне `.claude/canon.yaml`:

```yaml
project_type: <выбранный-тип>
```

Допустимые значения: `coding`, `management`, `education`, `documentation`, `claude-tooling`, `wiki`. Если ответа не было или ответ не из списка - не правь поле, autodiscovery остается отключенным до следующего синка.

### 4a. Обновление разошедшихся файлов

По каждому файлу из "разошелся" спроси отдельно:

> Обновить `.claude/<file>`? (да / нет / diff)

- **diff** - опиши различия словами (что добавилось, что убралось, какие формулировки изменились), затем спроси снова.
- **да** - перезапиши `.claude/<file>` канонической версией (полученной в 1c).
- **нет** - спроси: "занести в `skip_sync`? (да/нет)". Если да - добавь путь в `canon.yaml.skip_sync`.

Для tracked-superset перед вопросом выведи предупреждение: "да" затрет проектные добавки; рекомендую сначала вынести добавку в канон (4e) либо занести файл в `skip_sync`.

### 4b. Файлы без локальной копии

По каждому "нет локально" спроси: "создать `.claude/<file>` из канона? (да/нет)". При "да" - WebFetch + запись; папку скилла при необходимости создай.

### 4c. Файлы, убранные из канона

По каждому "нет в каноне" спроси: убрать запись из `files[]` (локальная копия останется обычным файлом проекта) или оставить как есть. Сам файл **не удаляй**.

### 4d. Новые канон-файлы

По каждому кандидату из 1d спроси: "добавить `.claude/<file>` в проект? (да/нет)".

- **да** - WebFetch + запись, добавь путь в `canon.yaml.files`. Если файл - правило, напомни добавить `@`-ссылку в `CLAUDE.md` (по отдельному "ок").
- **нет** - добавь путь в `canon.yaml.skip_sync` (чтобы не предлагался снова).

### 4e. Upstream-кандидаты

По каждому кандидату из 1e спроси: "вынести в канон? (да/нет)".

- **да** - сгенерируй бриф (формат ниже), добавь запись в `canon.yaml.upstream_pending`.
- **нет** для local-original - предложи занести путь в `canon.yaml.local_only` (чтобы файл не всплывал каждый синк).

Запись в `upstream_pending` - предполагаемый канонический путь файла (напр. `agents/my-extra-agent.md`). Бриф кладется в `toolkit-log/upstream-pending/<slug>.md`, где `<slug>` - имя файла без расширения (при коллизии имен добавь префикс директории, напр. `agents-my-extra-agent`). slug должен однозначно выводиться из пути - sync на следующих прогонах будет искать бриф по этому слагу.

```markdown
# Upstream-кандидат: <предлагаемый путь в каноне, напр. rules/foo.md>

Бриф для Claude в локальном клоне репозитория `claude-toolkit`. Цель - оценить файл и, если годится, добавить в канон.

## Откуда

- Проект: `<имя проекта или pwd>`
- Дата: <ISO-дата>
- Тип кандидата: local-original | tracked-superset

## Предлагаемый путь в каноне

`<rules|agents|skills/...>/<имя>`

## Содержимое

\`\`\`markdown
<для local-original - полное содержимое файла;
 для tracked-superset - только проектная добавка сверх канона,
 с пометкой, к какому канон-файлу она относится>
\`\`\`

## Rationale

<почему ценно для канона; для какого типа проектов; универсальное или тип-специфичное>

## Что сделать в клоне claude-toolkit

1. Отревьюить содержимое, депроектировать (убрать проектные имена/пути).
2. Положить в `<путь в каноне>`.
3. Зарегистрировать в `manifest.yaml` (секция по типу) и в нужном `bootstrap-0X`.
4. Закоммитить и запушить.
5. На следующем синке проект увидит файл в каноне и сам вычистит запись из `upstream_pending`.
```

### 4f. Чистка `upstream_pending`

Для устаревших записей (из 1f): убери запись из `canon.yaml.upstream_pending`, перенеси бриф `toolkit-log/upstream-pending/<slug>.md` -> `toolkit-log/upstream-applied/<slug>.md` (папку `upstream-applied/` при необходимости создай).

### 4g. Обнови `.claude/canon.yaml`

Правь **точечно, не перезаписывая файл целиком**: дополни `files`, `local_only`, `skip_sync`, `upstream_pending` по решениям выше. Комментарии на строках списков сохрани. Пустой список `[]` при первом добавлении разверни в блочную форму. Если в 4a0 был проставлен `project_type` - убедись, что поле действительно записано на верхнем уровне.

## ШАГ 5. Проверка

- Для каждого обновленного/добавленного файла перепроверь: локальная копия совпадает с канонической.
- `canon.yaml`: YAML валиден, в `files` нет дублей, нет пересечения `files` и `skip_sync`.
- Для каждого upstream-кандидата с ответом "да": бриф `toolkit-log/upstream-pending/<slug>.md` создан, запись в `upstream_pending` есть.

## ШАГ 6. Отчет (в чат)

- Обновлено: список файлов.
- Пропущено по моему решению: список + куда занесено (`skip_sync`).
- Добавлено новых канон-файлов: список.
- Upstream-кандидаты: что оформлено в брифы, что занесено в `local_only`.
- `upstream_pending`: что вычищено и какие брифы перенесены в `upstream-applied/`.
- Если ничего не делалось - "проект уже синхронизирован с каноном".

## Критерий готовности

- Каждый файл из `files[]` (вне `skip_sync`) либо совпадает с каноном, либо сознательно занесен в `skip_sync`.
- `canon.yaml` отражает решения: новые файлы в `files`, отказы в `skip_sync`, кандидаты в `upstream_pending` / `local_only`.
- Каждый upstream-кандидат с ответом "да" имеет самодостаточный бриф в `toolkit-log/upstream-pending/`.
- На уже синхронизированном проекте промт отрабатывает как no-op: ШАГ 2 выводит "расхождений нет", дальше шаги не идут.

## Правила безопасности

- Никаких правок до "ок" после плана.
- Каждый файл обновляется/добавляется только по отдельному "да" в пофайловом диалоге.
- Файлы в `skip_sync` не трогаются.
- Ничего вне `.claude/` и `toolkit-log/` не меняется. Исключение - `@`-ссылки в `CLAUDE.md` при добавлении нового правила, и только по отдельному "ок".
- `canon.yaml` правится точечно, не пересоздается.
- Файлы не удаляются: для "нет в каноне" убирается только запись из `files[]`, сам файл остается.
- Никаких `rm -rf`, никаких git-операций.
