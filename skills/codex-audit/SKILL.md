# codex-audit

Скилл для делегирования в `codex` CLI на этой машине задач, требующих **другой модели как независимого второго взгляда**, без права что-либо менять в репо (read-only). Codex изолирован: не видит контекст текущей сессии Claude, но читает файлы репозитория. Ценность не в том, что он "умнее" - а в **разнообразии мышления**: другая модель ловит другие классы ошибок, чем основной агент.

## Режимы

| Режим | Когда | Effort | Формат ответа Codex | Файлы в `docs/dev/` |
|---|---|---|---|---|
| `audit` (дефолт) | глубокий разбор кода/диффа/плана; "отправь на аудит", "пусть codex проверит" | `medium` | по каждому вопросу вердикт ok / risk / blocker + 1-2 предложения | `audit-plan-<topic>` / `audit-report-<topic>` |
| `adversarial` | состязательное ревью со скептической позицией; "сломай решение", "состязательное ревью", "попробуй сломать через codex" - нужно не подтверждение, а активный поиск дыр | `medium`, на необратимом `high` | по каждому компоненту: чем и при каких условиях сломается; "проблем нет" - только с перечнем проверенных атак | `adversarial-plan-<topic>` / `adversarial-report-<topic>` |
| `second-opinion` | независимый взгляд на подход/решение/дифф; "второе мнение", "посоветуйся"; по умолчанию после крупной работы | `medium` | согласен / не согласен + альтернативы + трейдоффы (не чеклист блокеров) | `consult-plan-<topic>` / `consult-report-<topic>` |
| `compliance` | сверка реализации с исходным планом; "проверь, что реализовал план", "сверь дифф с планом" - что сделано, что пропущено, что добавлено сверх плана | `low` | таблица "пункт плана -> статус (реализовано / частично / пропущено / отклонено) -> комментарий" + блок "сверх плана" | `compliance-plan-<topic>` / `compliance-report-<topic>` |
| `advocate` | проверить не объект, а **наш вывод о нем**: "справедлив ли разбор", "не придираемся ли", перед тем как отдать оценку наружу | `medium` | по каждому пункту вывода: справедлив / преувеличен / несправедлив / не проверяем + счет по вердиктам | `advocate-plan-<topic>` / `advocate-report-<topic>` |
| `escalation` | основной агент застрял (3+ провалившихся фикса, гипотезы не подтверждаются, субагент BLOCKED) - до похода к человеку | `high` | диагноз + root cause с доказательствами + рекомендованный подход | `escalate-plan-<topic>` / `escalate-report-<topic>` |

Общая обвязка одинакова во всех режимах: запуск через `codex exec -s read-only`, фиксация `-C <project-root>`, модель - новейшая доступная (резолвится динамически, см. правило 3), pre-check и пост-сбор лимитов, блок про субагентов в плане, требование к Codex писать `session id` первой строкой отчета. Различаются только `effort`, фрейминг плана/промпта, формат ответа и имена файлов.

## Когда применять

- Пользователь явно просит передать что-то в codex ("отправь codex", "пусть codex посмотрит", "второе мнение", "посоветуйся с codex").
- Нужна независимая проверка плана/диффа/архитектурного решения второй моделью.
- Нужно **состязательное (adversarial) ревью** (режим `adversarial`): не "подтверди, что ок", а "исходи из того, что дефект есть, и найди, чем решение сломается". Зовется фразами "состязательное ревью", "сломай решение", "попробуй сломать через codex".

  Важно понимать его границу: `adversarial` направлен **на объект** и наши выводы о нем не проверяет. Два прохода с общей установкой "найди дефекты" - не независимая проверка, а удвоение одного уклона: вопрос "а справедлив ли сам вывод" не задает ни один из них, зато их совпадение читается как схождение. Для проверки выводов есть `advocate` (ниже).
- Нужно **проверить собственный разбор** (режим `advocate`): на вход идет не объект, а **наша аналитика по нему** плюс сам объект, установка - "исходи из того, что вывод необоснован". Зовется фразами "проверь мой разбор", "не придираемся ли", "проход адвоката". Прецедент: разбор, где два прохода "подтвердили" друг друга, у адвоката дал 3 справедливых пункта из 16 - и все возражения, которые потом прислал клиент, воспроизвелись независимо, притом что его текст на вход не подавался.
- Нужна **сверка кода с планом** (режим `compliance`): сравнить реализованный дифф с исходным планом - что сделано, что пропущено, что отклонилось, что добавлено сверх плана. Зовется фразами "проверь, что реализовал план", "сверь дифф с планом", "compliance check". Уместно после фазы плана, до закрытия задачи.
- Основной агент застрял (режим `escalation`): отладка зашла в тупик, делегированный субагент вернул BLOCKED, несколько фиксов подряд не сработали - зовем Codex до того, как идти к пользователю.
- **Second-opinion по умолчанию.** После крупного изменения или завершенной фазы плана уместно прогнать `second-opinion`, не дожидаясь явной просьбы - это часть нормального workflow. Но с оглядкой: сначала pre-check лимита, и не на каждую мелочь (см. "Когда НЕ применять"). Forcing-функции через hook здесь намеренно нет - дисциплину держит этот скилл, а не блокировка.

## Когда НЕ применять

- Любые изменения файлов/коммиты/деплой - codex в этом скилле всегда read-only. Фиксы по находкам применяет сам Claude в своей сессии, не Codex.
- Опечатки, пропущенные импорты, очевидные ошибки - не повод звать вторую модель.
- До того как сам провел первичное расследование - сначала разберись, потом эскалируй.
- Если задача мелкая и решается тут же без второго мнения - не плодим вызовы.

## Как встроить валидацию в поток, чтобы ее не выключили

Второе мнение ловит то, чего свой взгляд не ловит по построению, но платится временем: прогон на `high` думает минутами. Если каждое решение превращается в паузу, валидацию тихо перестают звать - отказываются не от качества, а от простоя. Пять правил ниже про то, **когда звать, что подавать и где ставить гейт**; механика (режимы, `resume`, фон, pre-check) - в остальных разделах этого файла.

**Валидируется решение, а не реализация.** На вход - записка на 10-15 строк: что меняем, почему именно так, какая альтернатива отвергнута и чем. Не дифф и не список файлов. Разбор диффа требует перечитать код - это десятки минут на `high`; разбор решения идет на `medium` за минуты и ловит ровно то, ради чего валидацию заводят, - неверную развилку, причем до того, как написана первая строка. Дифф отдается отдельно и только там, где цена ошибки в реализации выше цены ошибки в замысле: миграция боевых данных, проверка полномочий, тонкое место с гонкой.

**Одна тема - одна сессия.** Первый заход дорогой: модель читает репозиторий и восстанавливает картину. Продолжение той же сессии (`resume`) стоит доли этого. Практически: один глубокий заход в начало темы, дальше вся серия решений по ней идет продолжениями. Новая сессия - когда сменилась тема или нужны другие модель и effort (`resume` их наследует).

**Запуск фоновый.** Ожидание перекрывается работой, а не встает в нее паузой.

**Гейт на мерж, а не на старт.** Реализация начинается сразу, вердикт учитывается перед вливанием в основную ветку. Обратный порядок ("сперва одобрение, потом код") дает тот же результат по качеству и вдвое больший срок: ожидание встает в критический путь, хотя ждать в нем нечего. Риск переделки невелик - записку на 15 строк переписать дешево, а вердикт приходит раньше, чем ветка готова.

**Глубина по необратимости.** Дефолт везде `medium`; `high` берется только там, где ошибка не откатывается, - миграции боевых данных, границы доступа и полномочий, схема данных, механика доставки или удаления файлов. Обычная развилка проектирования на `high` не нужна. Иначе упираешься в квоту, и на необратимое ее не остается: после одного глубокого аудита в пятичасовом окне оставалось 43 процента.

**Граница приема.** Он про решения, у которых есть развилка: два допустимых способа, и выбор между ними меняет результат. То, что проверяется фактом - упал тест, вернулся код ответа, сработала команда, - валидировать тратно: там дешевле проверить, чем спросить. Записка "правильно ли я понимаю, что запрос вернет 404" стоит минут ожидания там, где сам запрос занимает секунду.

Ничего из этого не отменяет pre-check лимита перед каждым запуском (правило 8), верификацию находок своими руками и запрет делегировать проверку собственной работы (`rules/subagents-usage.md`): ценность здесь именно в другой модели, а не во втором проходе тем же взглядом.

## Жесткие правила

1. **Всегда** запускать с `-s read-only`. Других режимов в этом скилле нет.
2. **Всегда** фиксировать рабочий каталог через `-C <project-root>`. В `-C` подставляй корень текущего проекта (абсолютный путь рабочего каталога), не хардкодь путь.
3. **Всегда** явно фиксировать модель и effort в команде:
   - **Модель - новейшая доступная, резолвится динамически**; номер версии в скилле не хардкодим. Резолв берет эффективный дефолт самого codex (значение `model` из `config.toml` в домашней папке codex, при отсутствии - из строки `model <slug> · openai`, которую печатает `codex doctor`) - сниппет в "Шаблоне вызова". Codex сам держит этот дефолт актуальным и мигрирует его при устаревании модели (`[notice.model_migrations]`), поэтому скилл не протухает и подхватывает новую модель без правки. Если резолв пуст (нет ни `model` в конфиге, ни ответа `doctor`) - флаг `-c model` автоматически не передается (собран в `MODEL_FLAG`, см. "Шаблон вызова"); codex возьмет собственный дефолт, а пользователя предупреждаем, какой моделью пошел запуск.
   - `-c model_reasoning_effort="<effort>"` - по режиму (доступно: minimal / low / medium / high / xhigh): `low` у `compliance`, `medium` у `audit`, `adversarial`, `advocate` и `second-opinion`, `high` у `escalation` и у `adversarial` на необратимом.
   - **`minimal` не использовать** - ломается в codex-cli.
   - **`high` - исключение, а не дефолт.** Он думает минутами и съедает окно лимита быстрее всего: одного глубокого аудита хватает, чтобы от пятичасового окна осталась половина. Ось та же, что в разделе "Как встроить валидацию в поток", - **необратимость**: `high` берется, когда ошибка не откатывается (миграция боевых данных, границы доступа и полномочий, схема данных, механика доставки или удаления файлов) либо когда мы уже застряли (`escalation`, зовется редко). Все остальное - `medium`.
   - `compliance` - `low`: это механическая сверка пунктов плана с диффом, глубина рассуждения там не работает. `second-opinion` - `medium` по своей природе: ценность в стороннем взгляде, а не в исчерпывающей проверке.
   - Цену занижения стоит знать: на прогоне 29-31.08.2026 состязательное ревью на `high` дало настоящие блокеры в каждом из трех раундов (удаление брифа соседнего проекта, path traversal через непроверенное поле, запись мимо целевой папки). Поэтому у `adversarial` право на `high` сохраняется - но по признаку необратимости, а не по умолчанию.
4. **План** класть в `docs/dev/<plan-file>.md` (рабочая заметка, не едет на прод; имя файла - по таблице "Режимы").
5. **Отчет** писать в `docs/dev/<report-file>.md` через shell-редирект, потом читать через `Read`.
6. Bash-таймаут поднимать до 600000ms (10 мин) - codex может думать долго, особенно на `high`.
7. **Всегда** после сессии собирать статистику лимитов аккаунта (см. блок "Статистика лимитов после сессии") - дописывать в конец `<report-file>.md` и показывать пользователю в саммари. Без этого скилл считается выполненным некорректно: непонятно, насколько мы близко к ограничению по тарифу. Статистика по самим токенам (input/output/reasoning) намеренно не собирается - она шум, важны только проценты лимитов.
8. **Всегда** перед запуском codex делать pre-check короткого окна (`5h` / `primary`) лимита по последнему rollout (см. блок "Pre-check лимита перед запуском"). Если осталось `< 10%` - НЕ запускать codex; вернуть пользователю алерт с фактическим остатком и временем до сброса, и попросить решить (подождать или все равно запустить). Иначе мы тратим контекст и время на запуск, который завершится частичным ответом или ошибкой лимита. Пустой результат читается **двумя разными состояниями, и вести себя надо по-разному**:
   - **папка codex найдена, rollout-логов в ней нет** - это действительно первый запуск на машине: предупредить пользователя и разрешить запуск;
   - **домашняя папка codex не резолвилась вовсе** - это не первый запуск, а промах резолва: проверка лимита **не выполнялась**, и про остаток квоты мы не знаем ничего. Не рапортовать это тоном штатной ветки - сказать пользователю, что путь не определился и лимит не проверен, и спросить, запускать ли. Резолв - в блоке "Резолв домашней папки codex".
9. **Домашнюю папку codex резолвить, а не брать из окружения** (блок "Резолв домашней папки codex"). Не заменяй сниппеты на `~/.codex` и не пиши `~/.codex` в собственных командах. Одного `"${CODEX_HOME:-$HOME/.codex}"` мало: он защищает от захардкоженного пути, но не от того, что переменная задана в интерактивном профиле пользователя и в неинтерактивный shell агента не доходит - тогда фолбэк берет пустую `$HOME/.codex`, и промах выглядит штатно. Признак - pre-check рапортует "первый запуск на машине" на устройстве, где codex заведомо работал (наблюдалось: `CODEX_HOME=/data/.codex` в профиле, 141 rollout-файл на диске, pre-check отчитался о первом запуске). Промах бьет по трем местам сразу: pre-check рапортует "rollout-логов нет", пост-сбор статистики не находит сессию, сверка `session id` перед `resume` объявляет настоящий id сфабрикованным.
10. **В не-git проекте обязателен `--skip-git-repo-check`.** Перед запуском проверить, git ли проект (`git -C <project-root> rev-parse >/dev/null 2>&1`); если нет - добавлять флаг во ВСЕ вызовы `codex exec`, включая `resume`. Без него codex не стартует вообще, причем молча (rc=0 и отчет из двух строк - см. "Ограничения"). Флаг снимает только проверку trusted-каталога, `-s read-only` продолжает действовать. Актуально для проектов типов wiki и management - это обычно vault'ы и папки заметок без git.

## Шаблон вызова

Сначала **разрешить модель** - новейшую доступную, из эффективного дефолта codex (номер версии не хардкодим). Флаг собираем в массив `MODEL_FLAG`: он пуст, если модель не резолвилась, - тогда `-c model` не передается вовсе (codex возьмет свой дефолт), а не уходит пустым:

```bash
if ! { [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; }; then
  CODEX_HOME=$(grep -hs -E '^[[:space:]]*(export[[:space:]]+)?CODEX_HOME=' \
      ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zshenv 2>/dev/null \
    | sed -E "s/.*CODEX_HOME=//; s/^[\"']//; s/[\"']$//; s|^~|$HOME|; s|\\\$HOME|$HOME|g; s|/+$||" \
    | while IFS= read -r d; do [ -n "$d" ] && [ -d "$d/sessions" ] && [ -r "$d/sessions" ] \
        && [ -x "$d/sessions" ] && echo "$d"; done | sort -u)
  [ -z "$CODEX_HOME" ] && [ -r "$HOME/.codex/sessions" ] && [ -x "$HOME/.codex/sessions" ] \
    && CODEX_HOME="$HOME/.codex"
  [ "$(printf '%s' "$CODEX_HOME" | grep -c .)" -gt 1 ] && CODEX_HOME=""
fi
{ [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; } || CODEX_HOME=""
# экспорт - для дочернего codex exec (проверкам скилла он не нужен: они читают
# файлы в этом же bash). Пустое значение не экспортируем - не затирать окружение
[ -n "$CODEX_HOME" ] && export CODEX_HOME
CODEX_MODEL=$(awk -F'"' '/^[[:space:]]*model[[:space:]]*=/{print $2; exit}' "$CODEX_HOME"/config.toml 2>/dev/null)
[ -z "$CODEX_MODEL" ] && CODEX_MODEL=$(codex doctor 2>/dev/null | grep -E '^[[:space:]]*model[[:space:]]+\S+ · ' | awk '{print $2}' | head -1)
MODEL_FLAG=(); [ -n "$CODEX_MODEL" ] && MODEL_FLAG=(-c model="$CODEX_MODEL")
```

Затем **проверить, git ли проект**: в не-git каталоге codex откажется стартовать (см. правило 10 и "Ограничения"). Флаг собираем в массив по той же схеме - в git-проекте он пуст и в команду не попадает:

```bash
GIT_FLAG=(); git -C <project-root> rev-parse >/dev/null 2>&1 || GIT_FLAG=(--skip-git-repo-check)
```

Если резолв модели пуст (`MODEL_FLAG` пустой) - предупредить пользователя, что запуск пошел дефолтной моделью codex. Дальше подставить оба массива в вызов:

```bash
codex exec -s read-only \
  -C <project-root> \
  "${MODEL_FLAG[@]}" \
  "${GIT_FLAG[@]}" \
  -c model_reasoning_effort="<effort>" \
  < docs/dev/<plan-file>.md \
  > docs/dev/<report-file>.md 2>&1
```

**План подается через stdin, а не аргументом.** У агента stdin не терминал, и в этом режиме `codex exec` ждет промт именно оттуда: при вызове с планом-аргументом он печатает `Reading additional input from stdin...` и висит, пока stdin не закроется. Прогон уходит в таймаут целиком - наблюдалось 10 минут впустую при `timeout: 600000`. Форма с аргументом рабочая только в интерактивном терминале, поэтому в скилле ее нет. Если аргумент по какой-то причине нужен, добавляй `< /dev/null`, иначе повиснет то же самое.

Легенда: `"${MODEL_FLAG[@]}"` - `-c model=<новейшая>` из резолва выше (или ничего, если не резолвилось); `"${GIT_FLAG[@]}"` - `--skip-git-repo-check` в не-git проекте (или ничего в git-проекте); `<effort>` - по таблице "Режимы": `low` (compliance), `medium` (audit, adversarial, advocate, second-opinion) или `high` (escalation и adversarial на необратимом); `<plan-file>` / `<report-file>` - имена из таблицы "Режимы"; `<project-root>` - абсолютный путь корня текущего проекта, в котором сейчас идет работа.

**Резолв (включая `export CODEX_HOME`) и `codex exec` - в одном Bash-вызове.** Shell-состояние между Bash-вызовами агента не переживает: резолв из предыдущей команды в следующей уже не виден. Без экспорта дочерний codex берет дефолт `~/.codex`, где на машине с нестандартным путем нет авторизации, - и падает в `401`, хотя все проверки скилла (pre-check, резолв модели) отработали штатно в том же bash.

Если план уже в переменной или буфере, а не в файле - тот же вызов, только stdin из here-string: `<<< "$PLAN"` вместо `< docs/dev/<plan-file>.md`.

### Опционально: resume существующей сессии

Для повторного раунда по той же теме (re-review после применения фиксов, уточнение мутного ответа, догрузка вопросов) можно переиспользовать сессию Codex через `resume <SESSION_ID>` - тогда Codex не нужно заново скармливать план, файлы и фрейминг, он помнит контекст первого прохода. Экономит входной токен-бюджет и сохраняет преемственность анализа.

```bash
codex exec -s read-only -C <project-root> "${GIT_FLAG[@]}" \
  resume "$SESSION_ID" \
  < docs/dev/<followup-plan-file>.md \
  > docs/dev/<followup-report-file>.md 2>&1
```

> **Порядок флагов.** `-s`/`-C`/`-c`/`--skip-git-repo-check` - опции `codex exec`, а `resume` - его подкоманда; глобальные флаги обязаны идти ДО `resume`. Если поставить `-C`/`-s` ПОСЛЕ `resume` (как аргумент подкоманды), codex падает на парсинге: `error: unexpected argument '-C' found` (проверено на codex v0.144.1). Первый (нессессионный) запуск - наоборот: там нет подкоманды, флаги идут сразу после `codex exec`.

`SESSION_ID` берется из шапки предыдущего отчета (Codex по нашей просьбе пишет `session id: <id>` первой строкой - см. "Упаковка контекста в план"):

```bash
SESSION_ID=$(awk -F': ' '/^session id:/ {print $2; exit}' docs/dev/<previous-report-file>.md)
```

**Шапке отчета не доверяй вслепую** - модель может сфабриковать id (наблюдалось: в отчете UUID, которого нет ни в одном rollout). Перед resume сверь, что файл `$CODEX_HOME/sessions/*/*/*/rollout-*-<SESSION_ID>.jsonl` существует (`CODEX_HOME` - через резолв из блока "Резолв домашней папки codex", иначе сверка объявит настоящий id сфабрикованным); нет - настоящий id достань из имени свежайшего rollout-файла (`ls -1t "$CODEX_HOME"/sessions/*/*/*/rollout-*.jsonl | head -1`). Папка не резолвилась - сверять нечем: скажи это прямо, а не выдавай "id не найден". Учти при этом, что codex в multi-agent-режиме пишет рядом с основной сессией rollout'ы **субагентов** (таймстампы почти совпадают, и свежайшим может оказаться именно субагентский): resume субагентского id падает с `direct app-server input is not allowed for multi-agent v2 sub-agents (code -32600)`. Поймал эту ошибку - не перебирай соседние файлы той же минуты (наблюдалось, что субагентскими оказываются все); надежный кандидат - id, которым сессия запускалась изначально (из первого запуска или прошлого resume - он остается resumable через все раунды).

Особенности resume:
- `-c model="..."` и `-c model_reasoning_effort="..."` в resume **игнорируются** - resume наследует модель и effort исходной сессии. Это нормально для re-review того же режима; если нужна другая модель/effort - стартуй свежую сессию, не resume.
- Просьба про `session id` в новом плане **не нужна** - sessionID у продолженной сессии тот же; пост-сбор лимитов работает по тому же `SESSION_ID` (можно его же переиспользовать или достать из новой шапки, если Codex ее напишет).
- Pre-check лимита перед resume - такой же обязательный, как перед новым запуском: короткое окно могло быть исчерпано предыдущим раундом.
- Для каждой итерации используй отдельные имена файлов плана/отчета (`<plan-file>-r2.md`, `<report-file>-r2.md`, дальше `-r3` и т.д.), не перезаписывай предыдущие - история раундов нужна для разбора.

### Опционально: фоновый запуск для долгих аудитов

`codex exec` синхронный и на `high` может думать минутами, блокируя сессию Claude. Если есть чем заняться параллельно - запускать ту же команду в фоне через `run_in_background: true` у Bash-тула (не через `&`). **Стдин обязан быть закрыт или занят планом** - иначе без TTY codex ждет "additional input from stdin" до EOF, которого не будет, и виснет с пустым отчетом (наблюдалось зависание почти на 7 часов; "процесс жив" - не признак прогресса, проверяй, что отчет растет). Форма из "Шаблона вызова" (`< <plan-file>`) это закрывает сама: файл кончился - stdin закрылся. Фоновый запуск - отдельный Bash-вызов: резолв `CODEX_HOME`/`MODEL_FLAG`/`GIT_FLAG` из предыдущих команд в нем не виден - повторяй блок резолва (с `export CODEX_HOME`) в этом же вызове перед `codex exec`, иначе воспроизведешь `401` из "Ограничений". Пример: `<блок резолва из "Шаблона вызова"> && codex exec -s read-only -C <root> "${MODEL_FLAG[@]}" "${GIT_FLAG[@]}" < <plan-file> > docs/dev/<report>.md 2>&1`. Уже поймал зависание (отчет не растет, в нем "Reading additional input from stdin...") - убей процесс и перезапусти план через stdin; потерь нет, зависшая сессия фактически не начиналась. Сессия не блокируется, по завершении придет нотификация; тогда: собрать статистику лимитов и прочитать отчет. Это нативный способ Claude Code - никаких плагинов/обвязок не нужно. Pre-check лимита делается до фонового запуска как обычно.

## Как codex выбирает модель

Порядок приоритета (от высшего к низшему):
1. `-m <model>` / `--model <model>` или `-c model="..."` в командной строке - переопределяет все.
2. `[profiles.<name>]` через `-p <profile>` - если указан профиль.
3. `config.toml` в домашней папке codex (где она - см. "Резолв домашней папки codex"; своими командами путь не собирать) - глобальный дефолт.

В этом скилле мы **не хардкодим номер версии**, а резолвим модель динамически (см. "Шаблон вызова") и передаем через `"${MODEL_FLAG[@]}"` явно. Источник резолва - эффективный дефолт самого codex (`model` из `config.toml`, при отсутствии - `codex doctor`): codex держит его новейшим и мигрирует при устаревании модели, так что скилл идет актуальной моделью без правки. Явная передача (а не расчет на неявный дефолт в момент запуска) фиксирует, какой именно моделью пошел прогон, - это попадает в лог и саммари.

## Процесс

1. **Определить режим** (`audit` / `adversarial` / `advocate` / `second-opinion` / `compliance` / `escalation`) - от него зависят `effort`, фрейминг плана, формат ответа и имена файлов (таблица "Режимы").
2. **Pre-check лимита** (см. блок "Pre-check лимита перед запуском"). Если короткое окно (`5h` / `primary`) показывает `left < 10%` - НЕ запускать codex, вернуть пользователю алерт с остатком и временем до сброса, спросить как поступить. Если папка codex найдена, но rollout-логов нет - предупредить и идти дальше; если папка не резолвилась - лимит не проверен, сказать это пользователю и спросить (правило 8).
3. **Сформулировать план** - записать в `docs/dev/<plan-file>.md`. План самодостаточный (Codex не видит историю чата): по чеклисту "Упаковка контекста в план". Фрейминг и формат ответа - под выбранный режим.
4. **Запустить codex** по шаблону выше, `timeout: 600000` (либо в фоне, см. "Опционально: фоновый запуск").
5. **Собрать статистику лимитов** (см. блок "Статистика лимитов после сессии") - дописать в конец `<report-file>.md`.
6. **Прочитать отчет** через `Read docs/dev/<report-file>.md`.
7. **Разобрать находки** (см. блок "Разбор находок") - верифицировать каждую, разделить на "применил / предлагаю / нужно решение". Кратко изложить пользователю (3-5 пунктов) + блок "лимиты" из двух строк (по одной на каждое окно `5h` и `1w`):
   - `<окно>: left N% (used M%), reset [D day ]H:MM hour` (целые сутки + часы:минуты до конца окна);
   - если по любому окну `left < 20%` - отдельной строкой над блоком вынести предупреждение "близко к лимиту по окну <окно>".
   Спросить, какие пункты брать в работу. Не браться за все молча.
8. После завершения задачи решить судьбу файлов: если задача закрыта, можно удалить `<plan-file>` и `<report-file>` или сослаться на них из соответствующего todo.

## Упаковка контекста в план

Каждый вызов Codex изолирован - план обязан быть самодостаточным. Минимум (адаптируй под режим):

- **Проблема / цель** - 1-2 предложения: что проверяем (`audit`), что пытаемся сломать (`adversarial`), какое решение/подход оцениваем (`second-opinion`), что сверяем с планом (`compliance`), где застряли (`escalation`).
- **Контекст** - 2-5 строк: что за фича, почему сейчас этим занимаемся.
- **Ключевые файлы** - конкретные пути с номерами строк (Codex видит репо, но укажи куда смотреть), не общие "посмотри в app/". Для ревью большого PR/диффа НЕ вставляй в план полный патч - дай список `git diff --name-only <base>..HEAD` плюс 2-3 хот-спота с номерами строк; Codex сам подтянет нужное через `-C`. Это экономит контекст ревьюера и снижает риск упереться в окно.
- **Что уже пробовали** (особенно для `escalation`) - гипотезы/фиксы и почему не сработали.
- **Evidence** - точные ошибки, стектрейсы, вывод тестов.
- **Ожидаемый результат / формат ответа** - что значит "готово"; попросить отвечать структурно по формату режима (`audit` -> вердикт ok/risk/blocker; `adversarial` -> список атак с серьезностью, "проблем нет" только с перечнем проверенного; `advocate` -> по каждому пункту нашего вывода вердикт справедлив / преувеличен / несправедлив / не проверяем, со счетом по вердиктам в конце; `second-opinion` -> согласие + альтернативы + трейдоффы; `compliance` -> таблица "пункт плана -> статус -> комментарий" + блок "сверх плана"; `escalation` -> диагноз + root cause + подход).
- **`session id` первой строкой** - попросить Codex первой строкой отчета написать `session id: <id>` (нужно для пост-сбора статистики лимитов). Использовать его без сверки нельзя - см. "Шапке отчета не доверяй вслепую" в секции resume.
- **Делегирование субагентам** - отдельным блоком в начале плана (шаблон ниже).

### Шаблон плана для `advocate`

У этого режима вход и установка обратные остальным, поэтому план строится иначе: объект идет **приложением**, а разбирается наш собственный вывод.

```text
Ты - адвокат объекта. Установка: **исходи из того, что наш вывод о нем необоснован**,
и опровергай ЕГО, а не объект. Твоя задача не найти новые дефекты объекта, а
проверить, справедливо ли то, что мы уже написали.

Вход: наш разбор и сам объект. По КАЖДОМУ пункту разбора - вердикт:
справедлив / преувеличен / несправедлив / не проверяем. В конце - счет
по вердиктам.

## Наш разбор (проверяется)

<ВСТАВЬ СЮДА РАЗБОР ЦЕЛИКОМ, по пунктам>

## Объект (приложение, для сверки)

<ВСТАВЬ СЮДА ОБЪЕКТ ИЛИ ПУТЬ К НЕМУ В РЕПО>

Проверяй по каждому пункту разбора:
- жанр объекта: не требуем ли того, чего жанр не предполагает;
- противоречие требований: не просим ли одновременно взаимоисключающего;
- норма предметной области: не названо ли дефектом то, что здесь принято;
- точность цитирования: не атакуем ли формулировку сильнее написанной в объекте;
- додуманный контекст: не истолковали ли за автора его цель или ограничения;
- операциональность: понятно ли по находке, что менять (вывод без критерия
  адресату бесполезен и проверке не поддается);
- двойной счет: не разложена ли одна проблема на несколько пунктов;
- проверяемость: не предъявлено ли как факт то, чего мы знать не можем.
```

**Условие чистоты: возражения, уже поступившие от автора объекта или заказчика, адвокату не подаются.** Иначе он их пересказывает, и проверка перестает отвечать на главный вопрос - ловится ли проблема заранее. Ценность прецедента, из которого взят режим, ровно в этом: адвокат независимо воспроизвел все пять возражений клиента, не видя их.

**Когда звать.** Перед отправкой разбора наружу (клиенту, заказчику, автору кода); когда два прохода "подозрительно сошлись" - сначала проверь, не ставили ли им одну задачу; в ревью, где дорог ложноположительный вывод. Не нужен там, где вывод дешево проверяется фактом: упавший тест не нуждается в адвокате.

```text
Вердикт "проблем нет" допустим ТОЛЬКО если перечислил,
```


## Разбор находок

Codex не видит контекст сессии и **может ошибаться**. Не доверять слепо.

1. **Сначала независимо верифицируй каждую находку** в коде (Read/Grep) - Codex не видел контекст сессии, мог ошибиться. Пометь оценку: подтверждаю / сомневаюсь / не согласен. Находка без цитируемой мотивирующей строки (помечена unverified, либо указанный файл:строка не содержит того, что утверждается) - по умолчанию "сомневаюсь": не поднимать как подтвержденную и не чинить, пока сам не нашел подтверждение в коде.
2. **Технические находки** (баги, security, race, performance, API misuse) - оцени и применяй сам, в своей сессии (Codex здесь read-only, файлы не правит).
3. **К пользователю иди только за продуктовым решением**: бизнес-логика, scope ("баг или фича?"), приоритет, trade-off ("чинить сейчас или отложить?").
4. **В итоговом резюме пользователю раздели на три группы**: "проверил и применил / предлагаю / нужно твое решение".
5. **Хвост под режим**:
   - `audit`: **blocker** - обсудить с пользователем, не править молча; **risk** - поднять в саммари, дать выбрать; **ok** - упомянуть одной строкой.
   - `adversarial`: каждую найденную атаку верифицируй в коде - Codex со скептической установкой склонен к ложным тревогам (репортит дефект там, где инвариант на деле держится). Подтвержденные - в группы "применил / предлагаю"; неподтвержденные - отметь как проверенные и отклоненные, не тащи в саммари как реальные. **Опциональный re-review после фиксов:** adversarial-фиксы часто переписывают тонкие места (race, валидация, error handling), и сам фикс может породить новый дефект или закрыть атаку не полностью. После применения подтвержденных находок уместно дернуть второй проход Codex'а только на дифф фиксов через `codex exec resume <SESSION_ID>` (см. "Опционально: resume существующей сессии") - Codex помнит контекст исходного ревью и проверяет, что атаки реально закрыты и фиксы не сломали соседних инвариантов. Решение делать второй проход - **за пользователем, не молча**: после первого раунда предложи в саммари, перечислив, какие фиксы будут проверяться. Pre-check лимита перед re-review - обязательный.
   - `advocate`: вердикты - не приговор, а вход для решения. "Несправедлив" и "не проверяем" убирай из вывода до отправки: первое портит отношения с адресатом, второе выдает за факт то, чего мы знать не можем. "Преувеличен" - переформулируй по факту, а не выбрасывай. Считай долю справедливых: если она мала, проблема не в отдельных пунктах, а в рамке разбора, и его надо пересобирать, а не править построчно.
   - `second-opinion`: вынести согласие/расхождения и альтернативы; это advisory, а не чеклист на закрытие.
   - `compliance`: пропуски и отклонения - к пользователю (продуктовое решение: доделать сейчас, отложить, зафиксировать в TODO, признать осознанным отклонением). Блок "сверх плана" - проверить самостоятельно: это могло быть оправданное доработкой, а могло быть scope creep; подсветить пользователю при втором случае.
   - `escalation`: верифицировать диагноз прежде чем строить фикс; если root cause подтвердился - применить рекомендованный подход; если Codex не помог - эскалировать к пользователю, привести findings обоих.
6. Если codex ушел в сторону или дал слишком общий ответ - уточнить план и перезапустить, не принимать мутный ответ как готовый.

## Дисциплина итераций (сходимость)

Цикл "ревью -> фиксы -> re-review" без явных стоп-условий не сходится: фиксы тонких мест порождают новые находки, а скептическая установка codex всегда найдет, что назвать дефектом. Правила, выведенные из практики:

- **Критерий сходимости - в первый же план.** Каждый adversarial/verify-план завершай инструкцией: "остаточный риск, требующий стека из 3+ независимых маловероятных условий, называй остаточным/приемлемым, а не находкой". Без нее находки мельчают, но не кончаются.
- **Бюджет раундов - по умолчанию 2** (ревью + verify фиксов; verify - это re-review, который по "Разбору находок" п.5 предлагается пользователю, бюджет этот вопрос не отменяет, а ограничивает цикл сверху). Третий и дальше - только явным решением пользователя; в саммари второго раунда дай свою рекомендацию (сошлось / есть незакрытый реальный риск) и перечисли остаточные.
- **Фиксы копить пачкой, ревью гонять параллельно.** Не ревьюить каждый инкремент отдельно: собери фиксы раунда в один дифф; prompt-reviewer (если правится промт) и codex - параллельно на одном диффе, не цепочкой. Ожидание codex (5-15 мин на прогон) - главная статья wall-clock.

## Резолв домашней папки codex

Все проверки скилла (pre-check лимита, пост-сбор статистики, сверка `session id`) читают `sessions/` и `config.toml` из домашней папки codex. Ее расположение переопределяется переменной `CODEX_HOME`, и **написать `"${CODEX_HOME:-$HOME/.codex}"` недостаточно**: переменная обычно задана в интерактивном профиле пользователя и в неинтерактивный shell агента не приходит. Тогда фолбэк честно берет `$HOME/.codex`, там пусто - и проверка молча превращается в "логов нет, первый запуск на машине".

Поэтому папку **резолвим**, а не берем из окружения. Сниппет вставляй в начало каждого блока, где путь нужен: shell-состояние между вызовами не переживает, экспорт из прошлой команды в следующей уже не виден. Блок, который сам запускает `codex exec`, добавляет к сниппету строку `export CODEX_HOME` (см. "Шаблон вызова"): проверкам скилла экспорт не нужен (читают файлы в том же bash), а дочернему процессу codex - обязателен, без него он уходит в дефолт `~/.codex` и падает в `401`.

```bash
if ! { [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; }; then
  CODEX_HOME=$(grep -hs -E '^[[:space:]]*(export[[:space:]]+)?CODEX_HOME=' \
      ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zshenv 2>/dev/null \
    | sed -E "s/.*CODEX_HOME=//; s/^[\"']//; s/[\"']$//; s|^~|$HOME|; s|\\\$HOME|$HOME|g; s|/+$||" \
    | while IFS= read -r d; do [ -n "$d" ] && [ -d "$d/sessions" ] && [ -r "$d/sessions" ] \
        && [ -x "$d/sessions" ] && echo "$d"; done | sort -u)
  [ -z "$CODEX_HOME" ] && [ -r "$HOME/.codex/sessions" ] && [ -x "$HOME/.codex/sessions" ] \
    && CODEX_HOME="$HOME/.codex"
  [ "$(printf '%s' "$CODEX_HOME" | grep -c .)" -gt 1 ] && CODEX_HOME=""
fi
{ [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; } || CODEX_HOME=""
```

На выходе `CODEX_HOME` либо указывает на папку с `sessions/`, либо **пуст - это отдельное состояние "не нашли"**, и трактовать его как первый запуск нельзя (см. правило 8). Свойства, которые важно сохранить при любой переработке сниппета:

- **кандидат проверяется тройкой `-d` + `-r` + `-x` на `sessions/`**, и каждая часть закрывает свой промах. Без `-d` кандидатом становится обычный файл с таким именем. Без `-r` проходит папка, которую нельзя прочитать. Без `-x` проходит папка, которую можно перечислить, но нельзя обойти вглубь - а rollout лежит на три уровня ниже (`sessions/<год>/<месяц>/<день>/`), и глоб вернет пусто. Любой из этих промахов дает один и тот же результат: логов "нет", и предохранитель квоты вырождается в ложный "первый запуск". Одного `ls` для этого мало - он успешен во всех трех случаях. Пустая, но полноценная `sessions/` тройку проходит: это и есть настоящий первый запуск;
- **несколько РАЗНЫХ живых кандидатов - тоже "не нашли"**, а не повод взять первый: в профилях бывает старое определение рядом с актуальным, и молча выбранный не тот путь хуже честного "не определился" - pre-check покажет квоту чужой установки, а сверка `session id` не найдет настоящую сессию. Один и тот же путь, повторенный в двух файлах, неоднозначностью не считается (дедуп через `sort -u`);
- **профили читаются грепом, а не `source`** - исполнять профиль ради одного значения лишний риск;
- **`codex doctor` для этого не годится** - он печатает то же эффективное значение и промахивается одинаково с нами.

## Pre-check лимита перед запуском

Цель: не запускать `codex exec`, если короткое окно (`primary`, у plus-плана это **5h**) на тарифе кончается. Иначе мы тратим минуты ожидания и контекст на ответ, который codex оборвет на полпути по rate-limit.

Источник данных - тот же rollout-лог, что и в "Статистика лимитов после сессии". Берем **последний** rollout-файл по mtime (не привязываемся к session id - его еще нет, мы только собираемся запускать новую сессию). В нем находим последний `token_count` event и из `rate_limits.primary` берем `used_percent` и `resets_at`.

Порог: **`left < 10%`** в окне `primary` - блокировать запуск. Цифра намеренно меньше порога "близко к лимиту" из саммари (20%): 10-20% хватит на средний аудит, а ниже 10% - уже почти гарантированно оборвет.

### Команда (запускать до `codex exec`)

Сначала - резолв домашней папки (см. "Резолв домашней папки codex"), в том же вызове: без него проверка молча выродится в "первый запуск".

```bash
if ! { [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; }; then
  CODEX_HOME=$(grep -hs -E '^[[:space:]]*(export[[:space:]]+)?CODEX_HOME=' \
      ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zshenv 2>/dev/null \
    | sed -E "s/.*CODEX_HOME=//; s/^[\"']//; s/[\"']$//; s|^~|$HOME|; s|\\\$HOME|$HOME|g; s|/+$||" \
    | while IFS= read -r d; do [ -n "$d" ] && [ -d "$d/sessions" ] && [ -r "$d/sessions" ] \
        && [ -x "$d/sessions" ] && echo "$d"; done | sort -u)
  [ -z "$CODEX_HOME" ] && [ -r "$HOME/.codex/sessions" ] && [ -x "$HOME/.codex/sessions" ] \
    && CODEX_HOME="$HOME/.codex"
  [ "$(printf '%s' "$CODEX_HOME" | grep -c .)" -gt 1 ] && CODEX_HOME=""
fi
{ [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; } || CODEX_HOME=""

ROLLOUT=""
[ -n "$CODEX_HOME" ] && ROLLOUT=$(ls -1t "$CODEX_HOME"/sessions/*/*/*/rollout-*.jsonl 2>/dev/null | head -1)
if [ -z "$CODEX_HOME" ]; then
  echo "PRE_CHECK: codex home not resolved - LIMIT NOT CHECKED, ask the user before running"
elif [ -z "$ROLLOUT" ]; then
  echo "PRE_CHECK: no rollout logs found - first codex session on this machine, proceed with warning"
else
  python3 - "$ROLLOUT" <<'PY'
import json, sys, datetime

def fmt_until(s):
    s = int(s)
    if s < 60: return f"{s} sec"
    days  = s // 86400
    rem   = s - days * 86400
    hours = rem // 3600
    mins  = (rem - hours * 3600) // 60
    if days:  return f"{days} day {hours}:{mins:02d} hour"
    if hours: return f"{hours}:{mins:02d} hour"
    return f"{mins} min"

last = None
for line in open(sys.argv[1]):
    try:
        o = json.loads(line)
        p = o.get('payload') or {}
        if p.get('type') == 'token_count' and (p.get('rate_limits') or {}).get('primary'):
            last = p
    except Exception:
        pass
if not last:
    print("PRE_CHECK: no rate_limits event in latest rollout - proceed with warning")
    sys.exit(0)
pr = last['rate_limits'].get('primary') or {}
used = pr.get('used_percent', 0)
left = max(0.0, 100.0 - used)
rt = pr.get('resets_at')
if isinstance(rt, str):
    try:
        rt = datetime.datetime.fromisoformat(rt.replace('Z','+00:00')).timestamp()
    except Exception:
        rt = None
now = datetime.datetime.now(datetime.timezone.utc).timestamp()
reset = fmt_until(max(0, rt - now)) if rt else "unknown"
if left < 10:
    print(f"PRE_CHECK: BLOCKED - 5h window left {left:.0f}% (used {used:.0f}%), reset {reset}")
else:
    print(f"PRE_CHECK: ok - 5h window left {left:.0f}% (used {used:.0f}%), reset {reset}")
PY
fi
```

### Как обрабатывать результат

- `PRE_CHECK: ok ...` - продолжить, запустить codex.
- `PRE_CHECK: BLOCKED ...` - НЕ запускать codex. Вернуть пользователю строку как есть + спросить: "ждать сброса или запустить все равно (рискуя оборваться)?". Не самочинно ставить таймер - решение пользователя. Если пользователь явно скажет "запускай" - запустить, иначе ждать.
- `PRE_CHECK: no rollout ...` / `no rate_limits event ...` - предупредить пользователя ("данных о лимите нет, запускаю") и идти дальше.

### Почему только короткое окно (5h)

Длинное окно (`1w` / `secondary`) тоже отдается в rollout, но один аудит за пару минут не сожжет неделю - там обычно остаток с большим запасом. Блокировать по `secondary` смысла нет: пользователю придется ждать дни до сброса. Если когда-нибудь окажемся в ситуации `secondary < 10%` - вынести отдельно в саммари как warning, но не блокировать запуск.

## Статистика лимитов после сессии

Codex CLI пишет лог сессии в `<домашняя папка codex>/sessions/<YYYY>/<MM>/<DD>/rollout-<ts>-<session_id>.jsonl` (папку резолвить сниппетом из "Резолв домашней папки codex", не собирать путь вручную). Внутри в событиях `token_count` есть блок `rate_limits` с двумя окнами:

- `primary` - короткое окно (для plus-плана `window_minutes=300`, то есть **5h**).
- `secondary` - длинное окно (для plus-плана `window_minutes=10080`, то есть **1w**).

Каждое окно содержит `used_percent` (сколько уже потрачено) и `resets_at` (unix-timestamp, когда счетчик обнулится).

Сами токены (input/cached/output/reasoning) намеренно НЕ собираются - в этом скилле важно одно: насколько мы близко к ограничениям тарифа и когда они сбросятся.

> **Почему не через `/status`.** Слаш-команда `/status` в TUI Codex показывает лимиты, но через `codex exec "/status"` она не работает - модель воспринимает строку как обычный prompt и отвечает текстом про workdir/sandbox без чисел. Отдельного `codex status` subcommand-а тоже нет (`codex --help` не содержит). Поэтому стат собирается из локального rollout-лога, который codex пишет автоматически.

### Команда (запускать сразу после codex exec)

`<report-file>` - отчет твоего режима из таблицы "Режимы" (`audit-report-<topic>` / `consult-report-<topic>` / `escalate-report-<topic>`). Извлечь `session id` из шапки только что созданного отчета, найти соответствующий rollout-файл, достать последний `rate_limits` и дописать блок в конец отчета:

```bash
if ! { [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; }; then
  CODEX_HOME=$(grep -hs -E '^[[:space:]]*(export[[:space:]]+)?CODEX_HOME=' \
      ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zshenv 2>/dev/null \
    | sed -E "s/.*CODEX_HOME=//; s/^[\"']//; s/[\"']$//; s|^~|$HOME|; s|\\\$HOME|$HOME|g; s|/+$||" \
    | while IFS= read -r d; do [ -n "$d" ] && [ -d "$d/sessions" ] && [ -r "$d/sessions" ] \
        && [ -x "$d/sessions" ] && echo "$d"; done | sort -u)
  [ -z "$CODEX_HOME" ] && [ -r "$HOME/.codex/sessions" ] && [ -x "$HOME/.codex/sessions" ] \
    && CODEX_HOME="$HOME/.codex"
  [ "$(printf '%s' "$CODEX_HOME" | grep -c .)" -gt 1 ] && CODEX_HOME=""
fi
{ [ -d "$CODEX_HOME/sessions" ] && [ -r "$CODEX_HOME/sessions" ] && [ -x "$CODEX_HOME/sessions" ]; } || CODEX_HOME=""

SESSION_ID=$(awk -F': ' '/^session id:/ {print $2; exit}' docs/dev/<report-file>.md)
if [ -z "$SESSION_ID" ] || [ -z "$CODEX_HOME" ]; then
  ROLLOUT=""
else
  ROLLOUT=$(ls -1t "$CODEX_HOME"/sessions/*/*/*/rollout-*-${SESSION_ID}.jsonl 2>/dev/null | head -1)
fi

{
  echo
  echo "## Rate limits"
  echo
  if [ -z "$ROLLOUT" ]; then
    if [ -z "$SESSION_ID" ]; then
      echo "no session id in report header - rate limits not collected"
    elif [ -z "$CODEX_HOME" ]; then
      echo "codex home not resolved - rate limits not collected (session id is fine)"
    else
      echo "no rollout file for session $SESSION_ID - rate limits not collected"
    fi
  else
  python3 - "$ROLLOUT" <<'PY'
import json, sys, datetime

def fmt_window(m):
    if m % 10080 == 0: return f"{m//10080}w"
    if m % 1440 == 0:  return f"{m//1440}d"
    if m % 60 == 0:    return f"{m//60}h"
    return f"{m}min"

def fmt_until(s):
    s = int(s)
    if s < 60: return f"{s} sec"
    days  = s // 86400
    rem   = s - days * 86400
    hours = rem // 3600
    mins  = (rem - hours * 3600) // 60
    if days:  return f"{days} day {hours}:{mins:02d} hour"
    if hours: return f"{hours}:{mins:02d} hour"
    return f"{mins} min"

last = None
with open(sys.argv[1]) as f:
    for line in f:
        try:
            o = json.loads(line)
            p = o.get('payload') or {}
            if p.get('type') == 'token_count' and (p.get('rate_limits') or {}).get('primary'):
                last = p
        except Exception:
            pass
if not last:
    print("no rate_limits event found"); sys.exit(0)
rl = last['rate_limits']
now = datetime.datetime.now(datetime.timezone.utc).timestamp()
for key in ('primary', 'secondary'):
    w = rl.get(key) or {}
    if not w: continue
    label = fmt_window(w.get('window_minutes', 0))
    used  = w.get('used_percent', 0)
    left  = max(0.0, 100.0 - used)
    rt    = w.get('resets_at')
    if isinstance(rt, str):
        try:
            rt = datetime.datetime.fromisoformat(rt.replace('Z','+00:00')).timestamp()
        except Exception:
            rt = None
    if rt:
        secs = max(0, rt - now)
        print(f"{label:>4}: left {left:.0f}% (used {used:.0f}%), reset {fmt_until(secs)}")
    else:
        print(f"{label:>4}: left {left:.0f}% (used {used:.0f}%)")
PY
  fi
} >> docs/dev/<report-file>.md
```

Пример того, что получается в конце отчета:

```text
## Rate limits

  5h: left 98% (used 2%), reset 2:35 hour
  1w: left 99% (used 1%), reset 1 day 2:35 hour
```

### Как читать

- `left` - сколько процента квоты тарифа доступно сейчас. Если `< 20%` (для любого из двух окон) - вынести в саммари отдельной строкой "близко к лимиту по окну <5h|1w>".
- `reset [D day ]H:MM hour` - компактный таймер до конца текущего окна: целые сутки (если есть), затем часы:минуты с ведущим нулем у минут. Примеры: `2:35 hour`, `1 day 0:00 hour`, `7 day 4:12 hour`, `45 min` (когда меньше часа), `30 sec` (когда меньше минуты). Окна скользящие: `resets_at` в исходных данных - это конец **текущего** окна, не "ровно через 5 часов от сейчас".
- Окна берутся из `window_minutes`. Лейблы `5h` / `1w` подставляются автоматически (300min -> `5h`, 10080min -> `1w`); если codex когда-нибудь сменит тариф/окна - в отчете появятся новые лейблы автоматически, скилл переписывать не надо.

### Если статистика не нашлась

- Файл rollout может не появиться, если codex упал на старте (например, проблемы с авторизацией) или сессия запущена с `--ephemeral`. В этом случае команда напечатает `no rollout file for session <id>` либо (если в шапке отчета нет `session id:`) `no session id in report header`. Это безопаснее, чем подцеплять чужой rollout - статистики просто не будет, и пользователь увидит причину.
- Не использовать `--ephemeral` в этом скилле - теряется возможность собрать статистику.
- Если в шапке отчета нет строки `session id:` - проверь сам план: по чеклисту "Упаковка контекста в план" Codex должен первой строкой отчета писать `session id: <id>`. Без этой строки пост-сборка статистики не работает.

## Ограничения

- Codex не получает контекст текущего чата, плана Claude Code, открытых файлов - только то, что в плане и что прочитает сам в репо.
- **`401 Missing bearer` при работающем интерактивном codex - это не протухший логин, а неэкспортированный `CODEX_HOME`**: дочерний `codex exec` не увидел резолвнутую переменную и ушел в дефолт `~/.codex` без авторизации. Симптом: отчет из строк `ERROR: unexpected status 401 Unauthorized` + `Reconnecting...` при rc=0, а пост-сбор пишет "no rollout file for session" (сессии и не было). Проверка в две строки: `codex login status` с переменной и без - разные ответы. Чинится экспортом в том же Bash-вызове (см. "Шаблон вызова"), а не просьбой перелогиниться.
- **В не-git проекте codex не стартует, причем молча.** Если `<project-root>` не git-репозиторий и не в trusted-каталогах codex, запуск без `--skip-git-repo-check` завершается с **rc=0** и отчетом ровно из двух строк:

  ```text
  Reading additional input from stdin...
  Not inside a trusted directory and --skip-git-repo-check was not specified.
  ```

  Опасность в том, что это неотличимо от "модель отработала и ничего не нашла": код возврата нулевой, файл отчета создан. Такой отчет за результат не принимать - перезапустить с флагом (правило 10). Статистику лимитов собирать бессмысленно: сессии не было, строки `session id` в отчете нет. Проверено на codex v0.144.x, поймано на vault-проекте без git.
- Read-only означает: codex не правит файлы, не коммитит, не запускает разрушительные команды. Но он **может** читать любые файлы внутри `-C` каталога, включая `.env` если тот есть. Не пихать в план секреты - они попадут в `<plan-file>.md` (рабочая заметка, в git не едет, но локально лежит).
- Разрешение в `settings.local.json` строго `Bash(codex exec -s read-only:*)` - без этого префикса вызов потребует подтверждения.
- Скилл намеренно использует синхронный `codex exec`, а не async-плагин `codex-plugin-cc` (`codex-companion.mjs`). Async дает non-blocking, но он Linux-only (нужны `/proc`, `flock`, GNU coreutils) и тащит классы зависаний (зомби-джобы, заклинивший per-cwd broker - в цепочке worker->broker->app-server нет таймаута на запрос), для лечения которых нужна отдельная обвязка. У синхронного `codex exec` этих проблем нет: один foreground-процесс, Bash-таймаут чисто его снимает, чистить нечего. Non-blocking при необходимости берется нативным `run_in_background` (см. "Опционально: фоновый запуск").
