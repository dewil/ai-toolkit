# codex-audit

Скилл для делегирования аудита/ревью кода в `codex` CLI на этой машине без права что-либо менять в репо.

## Когда применять

- Пользователь явно просит передать что-то в codex ("отправь codex", "пусть codex посмотрит", "codex-аудит").
- Нужна независимая проверка плана/диффа/архитектурного решения вторым агентом.

## Когда НЕ применять

- Любые изменения файлов/коммиты/деплой - codex в этом скилле всегда read-only.
- Если задача мелкая и решается тут же без второго мнения - не плодим вызовы.

## Жесткие правила

1. **Всегда** запускать с `-s read-only`. Других режимов в этом скилле нет.
2. **Всегда** фиксировать рабочий каталог через `-C <project-root>`. В `-C` подставляй корень текущего проекта (абсолютный путь рабочего каталога), не хардкодь путь.
3. **Всегда** явно фиксировать модель и уровень reasoning в команде, не полагаться на `~/.codex/config.toml`:
   - `-c model="gpt-5.5"` - максимально качественная доступная модель.
   - `-c model_reasoning_effort="xhigh"` - максимальный уровень рассуждений (доступно: minimal / low / medium / high / xhigh).
   - Цель скилла - качество аудита, поэтому модель и reasoning всегда на максимуме. Если для конкретной задачи качество избыточно - не использовать этот скилл вообще.
4. **План** класть в `docs/dev/audit-plan-<topic>.md` (рабочая заметка, не едет на прод).
5. **Отчет** писать в `docs/dev/audit-report-<topic>.md` через shell-редирект, потом читать через `Read`.
6. Bash-таймаут поднимать до 600000ms (10 мин) - codex может думать долго, особенно на `xhigh`.
7. **Всегда** после сессии собирать статистику лимитов аккаунта (см. блок "Статистика лимитов после сессии") - дописывать в конец `audit-report-*.md` и показывать пользователю в саммари. Без этого скилл считается выполненным некорректно: непонятно, насколько мы близко к ограничению по тарифу. Статистика по самим токенам (input/output/reasoning) намеренно не собирается - она шум, важны только проценты лимитов.
8. **Всегда** перед запуском codex делать pre-check короткого окна (`5h` / `primary`) лимита по последнему rollout (см. блок "Pre-check лимита перед запуском"). Если осталось `< 10%` - НЕ запускать codex; вернуть пользователю алерт с фактическим остатком и временем до сброса, и попросить решить (подождать или все равно запустить). Иначе мы тратим контекст и время на запуск, который завершится частичным ответом или ошибкой лимита. Если rollout-логов нет вообще (первый запуск на машине) - предупредить пользователя и разрешить запуск.

## Шаблон вызова

```bash
codex exec -s read-only \
  -C <project-root> \
  -c model="gpt-5.5" \
  -c model_reasoning_effort="xhigh" \
  "$(cat docs/dev/audit-plan-<topic>.md)" \
  > docs/dev/audit-report-<topic>.md 2>&1
```

Альтернатива со stdin (если план уже в переменной/буфере):

```bash
codex exec -s read-only \
  -C <project-root> \
  -c model="gpt-5.5" \
  -c model_reasoning_effort="xhigh" \
  - < docs/dev/audit-plan-<topic>.md \
  > docs/dev/audit-report-<topic>.md 2>&1
```

В `-C <project-root>` подставляй корень текущего проекта - абсолютный путь рабочего каталога, в котором сейчас идет работа.

## Как codex выбирает модель

Порядок приоритета (от высшего к низшему):
1. `-m <model>` / `--model <model>` или `-c model="..."` в командной строке - переопределяет все.
2. `[profiles.<name>]` через `-p <profile>` - если указан профиль.
3. `~/.codex/config.toml` - глобальный дефолт, но опираться на него нельзя - конфиг может быть изменен между запусками.

В этом скилле мы **всегда** передаем модель через `-c` явно, чтобы качество аудита не зависело от состояния глобального конфига.

## Процесс

1. **Pre-check лимита** (см. блок "Pre-check лимита перед запуском"). Если короткое окно (`5h` / `primary`) показывает `left < 10%` - НЕ запускать codex, вернуть пользователю алерт с остатком и временем до сброса, спросить как поступить. Если rollout-логов нет - предупредить и идти дальше.
2. **Сформулировать план** - записать в `docs/dev/audit-plan-<topic>.md`. План должен быть самодостаточным: цель аудита, контекст, конкретные пути к файлам, что именно проверить, формат ожидаемого ответа. Codex не видит историю чата.
3. **Запустить codex** по шаблону выше, `timeout: 600000`.
4. **Собрать статистику лимитов** (см. блок "Статистика лимитов после сессии") - дописать в конец `audit-report-<topic>.md`.
5. **Прочитать отчет** через `Read docs/dev/audit-report-<topic>.md`.
6. **Кратко изложить** пользователю что нашел codex (3-5 пунктов) + блок "лимиты" из двух строк (по одной на каждое окно `5h` и `1w`):
   - `<окно>: left N% (used M%), reset [D day ]H:MM hour` (целые сутки + часы:минуты до конца окна);
   - если по любому окну `left < 20%` - отдельной строкой над блоком вынести предупреждение "близко к лимиту по окну <окно>".
   Спросить, какие пункты брать в работу. Не браться за все молча.
7. После завершения задачи решить судьбу файлов: если аудит закрыт, можно удалить `audit-plan-*` и `audit-report-*` или сослаться на них из соответствующего todo.

## Что писать в план аудита

Минимум:
- **Цель** - одна фраза: "проверить, что новая логика X не ломает Y".
- **Контекст** - 2-5 строк: что за фича, почему сейчас аудим.
- **Файлы** - конкретные пути с номерами строк, не общие "посмотри в app/".
- **Вопросы** - пронумерованный список конкретных вопросов.
- **Формат ответа** - попросить codex отвечать структурно: "по каждому вопросу - вердикт (ok / risk / blocker) + 1-2 предложения".
- **Делегирование субагентам** - в самом начале плана отдельным блоком попросить codex использовать собственных субагентов на более дешевых моделях для вспомогательных шагов (поиск по репо, чтение больших файлов, сбор статистики, проверка тривиальных условий). Главный критерий - качество итогового аудита; экономия токенов вторична. Финальные выводы (вердикты ok/risk/blocker, рекомендации) codex обязан формировать сам, не делегируя их дешевым моделям.

### Шаблон блока про субагентов

Вставлять в начало плана дословно или близко к тексту:

```text
## Использование субагентов

По возможности делегируй вспомогательную работу собственным субагентам на более дешевых моделях:
- поиск файлов/символов, grep по репо;
- чтение больших файлов и выборка релевантных фрагментов;
- сбор фактов (версии, конфиги, наличие/отсутствие чего-либо);
- проверка тривиальных условий ("есть ли тест на X", "используется ли функция Y").

Что НЕ делегировать дешевым моделям:
- финальные вердикты (ok / risk / blocker);
- рассуждения о безопасности, корректности логики, инвариантах;
- сводное заключение в конце отчета.

Главный критерий - качество аудита. Если задача требует основной модели для сохранения качества - используй основную модель, не экономь.
```

## Что делать с ответом codex

- **blocker** - обсудить с пользователем, не править молча.
- **risk** - поднять в саммари, дать пользователю выбрать.
- **ok** - упомянуть одной строкой, дальше игнорировать.
- Если codex ушел в сторону или дал слишком общий ответ - уточнить план и перезапустить, не принимать мутный ответ как готовый.

## Pre-check лимита перед запуском

Цель: не запускать `codex exec`, если короткое окно (`primary`, у plus-плана это **5h**) на тарифе кончается. Иначе мы тратим минуты ожидания и контекст на ответ, который codex оборвет на полпути по rate-limit.

Источник данных - тот же rollout-лог, что и в "Статистика лимитов после сессии". Берем **последний** rollout-файл по mtime (не привязываемся к session id - его еще нет, мы только собираемся запускать новую сессию). В нем находим последний `token_count` event и из `rate_limits.primary` берем `used_percent` и `resets_at`.

Порог: **`left < 10%`** в окне `primary` - блокировать запуск. Цифра намеренно меньше порога "близко к лимиту" из саммари (20%): 10-20% хватит на средний аудит, а ниже 10% - уже почти гарантированно оборвет.

### Команда (запускать до `codex exec`)

```bash
ROLLOUT=$(ls -1t ~/.codex/sessions/*/*/*/rollout-*.jsonl 2>/dev/null | head -1)
if [ -z "$ROLLOUT" ]; then
  echo "PRE_CHECK: no rollout logs found - first codex session on this machine, proceed with warning"
else
  python3 - "$ROLLOUT" <<'PY'
import json, sys, datetime

def fmt_until(s):
    s = int(s)
    if s < 60: return f"{s} sec"
    days  = s // 86400
    rem   = s - days * 86400
    hours = rem // 3600
    mins  = (rem - hours * 3600) // 60
    if days:  return f"{days} day {hours}:{mins:02d} hour"
    if hours: return f"{hours}:{mins:02d} hour"
    return f"{mins} min"

last = None
for line in open(sys.argv[1]):
    try:
        o = json.loads(line)
        p = o.get('payload') or {}
        if p.get('type') == 'token_count' and (p.get('rate_limits') or {}).get('primary'):
            last = p
    except Exception:
        pass
if not last:
    print("PRE_CHECK: no rate_limits event in latest rollout - proceed with warning")
    sys.exit(0)
pr = last['rate_limits'].get('primary') or {}
used = pr.get('used_percent', 0)
left = max(0.0, 100.0 - used)
rt = pr.get('resets_at')
if isinstance(rt, str):
    try:
        rt = datetime.datetime.fromisoformat(rt.replace('Z','+00:00')).timestamp()
    except Exception:
        rt = None
now = datetime.datetime.now(datetime.timezone.utc).timestamp()
reset = fmt_until(max(0, rt - now)) if rt else "unknown"
if left < 10:
    print(f"PRE_CHECK: BLOCKED - 5h window left {left:.0f}% (used {used:.0f}%), reset {reset}")
else:
    print(f"PRE_CHECK: ok - 5h window left {left:.0f}% (used {used:.0f}%), reset {reset}")
PY
fi
```

### Как обрабатывать результат

- `PRE_CHECK: ok ...` - продолжить, запустить codex.
- `PRE_CHECK: BLOCKED ...` - НЕ запускать codex. Вернуть пользователю строку как есть + спросить: "ждать сброса или запустить все равно (рискуя оборваться)?". Не самочинно ставить таймер - решение пользователя. Если пользователь явно скажет "запускай" - запустить, иначе ждать.
- `PRE_CHECK: no rollout ...` / `no rate_limits event ...` - предупредить пользователя ("данных о лимите нет, запускаю") и идти дальше.

### Почему только короткое окно (5h)

Длинное окно (`1w` / `secondary`) тоже отдается в rollout, но один аудит за пару минут не сожжет неделю - там обычно остаток с большим запасом. Блокировать по `secondary` смысла нет: пользователю придется ждать дни до сброса. Если когда-нибудь окажемся в ситуации `secondary < 10%` - вынести отдельно в саммари как warning, но не блокировать запуск.

## Статистика лимитов после сессии

Codex CLI пишет лог сессии в `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<ts>-<session_id>.jsonl`. Внутри в событиях `token_count` есть блок `rate_limits` с двумя окнами:

- `primary` - короткое окно (для plus-плана `window_minutes=300`, то есть **5h**).
- `secondary` - длинное окно (для plus-плана `window_minutes=10080`, то есть **1w**).

Каждое окно содержит `used_percent` (сколько уже потрачено) и `resets_at` (unix-timestamp, когда счетчик обнулится).

Сами токены (input/cached/output/reasoning) намеренно НЕ собираются - в этом скилле важно одно: насколько мы близко к ограничениям тарифа и когда они сбросятся.

> **Почему не через `/status`.** Слаш-команда `/status` в TUI Codex показывает лимиты, но через `codex exec "/status"` она не работает - модель воспринимает строку как обычный prompt и отвечает текстом про workdir/sandbox без чисел. Отдельного `codex status` subcommand-а тоже нет (`codex --help` не содержит). Поэтому стат собирается из локального rollout-лога, который codex пишет автоматически.

### Команда (запускать сразу после codex exec)

Извлечь `session id` из шапки только что созданного отчета, найти соответствующий rollout-файл, достать последний `rate_limits` и дописать блок в конец отчета:

```bash
SESSION_ID=$(awk -F': ' '/^session id:/ {print $2; exit}' docs/dev/audit-report-<topic>.md)
if [ -z "$SESSION_ID" ]; then
  ROLLOUT=""
else
  ROLLOUT=$(ls -1t ~/.codex/sessions/*/*/*/rollout-*-${SESSION_ID}.jsonl 2>/dev/null | head -1)
fi

{
  echo
  echo "## Rate limits"
  echo
  if [ -z "$ROLLOUT" ]; then
    if [ -z "$SESSION_ID" ]; then
      echo "no session id in report header - rate limits not collected"
    else
      echo "no rollout file for session $SESSION_ID - rate limits not collected"
    fi
  else
  python3 - "$ROLLOUT" <<'PY'
import json, sys, datetime

def fmt_window(m):
    if m % 10080 == 0: return f"{m//10080}w"
    if m % 1440 == 0:  return f"{m//1440}d"
    if m % 60 == 0:    return f"{m//60}h"
    return f"{m}min"

def fmt_until(s):
    s = int(s)
    if s < 60: return f"{s} sec"
    days  = s // 86400
    rem   = s - days * 86400
    hours = rem // 3600
    mins  = (rem - hours * 3600) // 60
    if days:  return f"{days} day {hours}:{mins:02d} hour"
    if hours: return f"{hours}:{mins:02d} hour"
    return f"{mins} min"

last = None
with open(sys.argv[1]) as f:
    for line in f:
        try:
            o = json.loads(line)
            p = o.get('payload') or {}
            if p.get('type') == 'token_count' and (p.get('rate_limits') or {}).get('primary'):
                last = p
        except Exception:
            pass
if not last:
    print("no rate_limits event found"); sys.exit(0)
rl = last['rate_limits']
now = datetime.datetime.now(datetime.timezone.utc).timestamp()
for key in ('primary', 'secondary'):
    w = rl.get(key) or {}
    if not w: continue
    label = fmt_window(w.get('window_minutes', 0))
    used  = w.get('used_percent', 0)
    left  = max(0.0, 100.0 - used)
    rt    = w.get('resets_at')
    if isinstance(rt, str):
        try:
            rt = datetime.datetime.fromisoformat(rt.replace('Z','+00:00')).timestamp()
        except Exception:
            rt = None
    if rt:
        secs = max(0, rt - now)
        print(f"{label:>4}: left {left:.0f}% (used {used:.0f}%), reset {fmt_until(secs)}")
    else:
        print(f"{label:>4}: left {left:.0f}% (used {used:.0f}%)")
PY
  fi
} >> docs/dev/audit-report-<topic>.md
```

Пример того, что получается в конце отчета:

```text
## Rate limits

  5h: left 98% (used 2%), reset 2:35 hour
  1w: left 99% (used 1%), reset 1 day 2:35 hour
```

### Как читать

- `left` - сколько процента квоты тарифа доступно сейчас. Если `< 20%` (для любого из двух окон) - вынести в саммари отдельной строкой "близко к лимиту по окну <5h|1w>".
- `reset [D day ]H:MM hour` - компактный таймер до конца текущего окна: целые сутки (если есть), затем часы:минуты с ведущим нулем у минут. Примеры: `2:35 hour`, `1 day 0:00 hour`, `7 day 4:12 hour`, `45 min` (когда меньше часа), `30 sec` (когда меньше минуты). Окна скользящие: `resets_at` в исходных данных - это конец **текущего** окна, не "ровно через 5 часов от сейчас".
- Окна берутся из `window_minutes`. Лейблы `5h` / `1w` подставляются автоматически (300min -> `5h`, 10080min -> `1w`); если codex когда-нибудь сменит тариф/окна - в отчете появятся новые лейблы автоматически, скилл переписывать не надо.

### Если статистика не нашлась

- Файл rollout может не появиться, если codex упал на старте (например, проблемы с авторизацией) или сессия запущена с `--ephemeral`. В этом случае команда напечатает `no rollout file for session <id>` либо (если в шапке отчета нет `session id:`) `no session id in report header`. Это безопаснее, чем подцеплять чужой rollout - статистики просто не будет, и пользователь увидит причину.
- Не использовать `--ephemeral` в этом скилле - теряется возможность собрать статистику.
- Если в шапке отчета нет строки `session id:` - проверь сам план аудита: в "Формат ответа" должно быть прямое указание codex'у первой строкой отчета писать `session id: <id>`. Без этой строки пост-сборка статистики не работает.

## Ограничения

- Codex не получает контекст текущего чата, плана Claude Code, открытых файлов - только то, что в плане и что прочитает сам в репо.
- Read-only означает: codex не правит файлы, не коммитит, не запускает разрушительные команды. Но он **может** читать любые файлы внутри `-C` каталога, включая `.env` если тот есть. Не пихать в план секреты - они попадут в `audit-plan-*.md` (рабочая заметка, в git не едет, но локально лежит).
- Разрешение в `settings.local.json` строго `Bash(codex exec -s read-only:*)` - без этого префикса вызов потребует подтверждения.
