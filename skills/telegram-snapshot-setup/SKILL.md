# telegram-snapshot-setup

Скилл для первой настройки или починки автоматизированного pull Telegram-чатов проекта через Telethon. Фиксирует **накопленный опыт по граблям**, на которые натыкаешься в первый раз.

Скрипты-эталоны лежат в каноне в `scripts/telegram-snapshot.py` и `scripts/telegram-deltas.py` (top-level папка `scripts/`, не внутри папки скилла). Bootstrap-03-management копирует их в `scripts/` в корне проекта - оттуда же, где их ожидает скилл при запуске (`python3 scripts/telegram-snapshot.py`). В эталонной версии уже есть `iter_dialogs()` прогрев (см. шаг 5).

## Когда применять

- Пользователь впервые настраивает скрипты `scripts/telegram-snapshot.py` / `telegram-deltas.py` на новом устройстве.
- my.telegram.org возвращает голое `ERROR.` при создании приложения и не дает api_id/api_hash.
- Telethon ругается `Could not find the input entity for PeerUser(...)` на свежей сессии.
- Сессия отозвана (`AuthKeyUnregisteredError`), нужно перелогиниться.
- Подключается новый проект - нужно создать `.telegram-snapshot.json` и проверить, что общая авторизация на устройстве уже есть.

## Когда НЕ применять

- Обычный регулярный pull (запуск `telegram-snapshot.py` для свежих сообщений) - это просто Bash-команда из шаблона дейлика, отдельный скилл не нужен.
- Любые задачи по экспорту/анализу самих сообщений - они уже в `result.json`, читай напрямую.

## Алгоритм

### Шаг 1. Проверить общую авторизацию устройства

```bash
ls ~/.config/telegram-snapshot/
```

Должно быть:
- `auth.json` (api_id, api_hash, session_name) - права 600.
- `<session_name>.session` - SQLite-сессия Telethon.

Если файлов нет - идем к шагу 2. Если `auth.json` есть, а `.session` нет - идем к шагу 4 (первый интерактивный логин).

### Шаг 2. Получить api_id и api_hash

**Сначала пробовать свои через my.telegram.org**.

Если my.telegram.org возвращает `ERROR.` при "Create application" - это блокировка на стороне аккаунта (антифрод по новизне аккаунта и/или IP VPN). По состоянию на май 2026 воспроизведено на разных комбинациях полей формы (platform=desktop/other, разные title/shortname, с url и без) - сервер режет одинаково. Лечится:
1. Сменой VPN-узла на другую страну/провайдера (см. список ниже).
2. Ожиданием 6-24 часа после неудачных попыток.
3. Использованием другого, более старого активного Telegram-аккаунта.

VPN-предпочтения для my.telegram.org: лучше Германия/Нидерланды/Финляндия, хуже США/UK. Резиденциальные IP > datacenter. Свой WireGuard на личном VPS почти всегда проходит.

**Fallback - публичные ключи Telegram Desktop OSS**:
- `api_id`: `17349`
- `api_hash`: `344583e45741c457fe1862106095a5eb`

Это публичные значения из исходников tdesktop. Технически серая зона по ToS, но не банится при некоммерческом личном использовании.

### Шаг 3. Заполнить auth.json

```bash
mkdir -p ~/.config/telegram-snapshot
chmod 700 ~/.config/telegram-snapshot
```

Содержимое `~/.config/telegram-snapshot/auth.json` (выставить права 600):
```json
{
  "api_id": 17349,
  "api_hash": "344583e45741c457fe1862106095a5eb",
  "session_name": "<имя_аккаунта>"
}
```

`session_name` - произвольное (например `dwl`), под этим именем будет файл `<name>.session` в той же папке.

### Шаг 4. Поставить telethon и сделать первый запуск

```bash
pip3 install --user telethon
cd <project-root>
python3 scripts/telegram-snapshot.py
```

Первый запуск **обязательно интерактивный** - в Bash из этого скилла НЕ запускать (stdin недоступен). Сказать пользователю запустить в его терминале и продиктовать ввод:

- Phone: `+7...` (международный формат).
- Code: из приложения Telegram (приходит в Saved Messages от "Telegram").
- Password: 2FA, если включена.

После успеха появится `~/.config/telegram-snapshot/<session_name>.session`. Дальше запуски без ввода - **в любом проекте на этом устройстве**.

### Шаг 5. Лечение типичных ошибок при первом pull

**`Could not find the input entity for PeerUser(...)` на нормальных групповых чатах.** На свежей сессии telethon без подсказки трактует голый int chat_id как user_id. Лечится прогревом - перед циклом обработки чатов в `amain()` должен быть:

```python
async for _ in client.iter_dialogs():
    pass
```

В канонической версии `scripts/telegram-snapshot.py` этот блок уже есть. Если в проекте старая версия скрипта без прогрева - перекопировать из канона (см. `migrations/sync-from-canon.prompt.md`).

**`AuthKeyUnregisteredError` / сессия отозвана.** Удалить `~/.config/telegram-snapshot/<session_name>.session` и перезапустить - пройдет авторизация с нуля.

**`Server closed the connection: 0 bytes read on a total of 8 expected bytes`** на старте. Безобидное, telethon просто перезаключает соединение, продолжает дальше. Если повторяется на каждом ивенте - проблема с VPN, попробовать сменить узел.

### Шаг 6. Подключение нового проекта

В корне нового проекта создать `.telegram-snapshot.json`:
```json
{
  "chats_root": "Встречи/чаты",
  "chats": {
    "с заказчиком": 4715985727,
    "с командой": 2644101635,
    "1-1/Иванов И.И.": 504935520
  }
}
```

`chat_id` для уже-экспортированного чата берется из `result.json` (поле `id` в шапке). Для чата, которого еще нет на диске, скрипт сделает **bootstrap** - создаст шапку и подтянет всю историю через Telethon (см. ниже).

**Конвенция подпапок.** Label интерпретируется буквально как путь внутри `chats_root`: `result.json` для label `с заказчиком` лежит в `<chats_root>/с заказчиком/`, а для label `1-1/Иванов И.И.` - в `<chats_root>/1-1/Иванов И.И./`. Префикс `1-1/` имеет особый смысл - персональные чаты (личные диалоги с участниками 1-1-встреч). `telegram-deltas.py` выводит их отдельным блоком `#### 1-1` под общим списком групповых чатов, со срезанным префиксом в display name. Прочие подпапки скрипт просто проксирует как часть пути, без специальной обработки.

Сами скрипты `scripts/telegram-snapshot.py` и `scripts/telegram-deltas.py` приходят из канона при bootstrap-03-management или при `sync-from-canon`. Не пересобирать руками из других проектов - старые копии могут не содержать `iter_dialogs()` прогрев и режим миграции legacy формата.

### Шаг 7. Формат `result.json` и режимы скрипта

Канонический формат result.json - **расширенный** Telegram Desktop export:

```json
{
  "name": "<имя чата>",
  "type": "private_supergroup",
  "id": 2644101635,
  "topics": [
    { "id": 167, "title": "Маршруты", "date": "...", "date_unixtime": "...", "icon_color": 13338331 }
  ],
  "messages": [
    {
      "id": 168, "type": "message",
      "date": "...", "date_unixtime": "...",
      "from": "...", "from_id": "user...",
      "text": "...", "text_entities": [...],
      "topic_id": 167,
      "reply_to_message_id": 200,
      "edited": "...", "edited_unixtime": "..."
    }
  ]
}
```

Дополнения относительно сырого TG Desktop экспорта:

- `topics: []` в шапке - метаданные форумных тем (`id`, `title`, `date`, `date_unixtime`, `icon_color`). При переименовании топика обновляется `title`.
- `topic_id` у сообщения - id корневого сообщения форум-темы. Заполняется только для сообщений в форум-чатах с топиками.
- `reply_to_message_id` остается **только** для настоящих реплаев (когда пользователь ответил на конкретное сообщение внутри топика). "Цепляние к шапке топика" больше не выражается через reply - оно в `topic_id`.
- `edited` / `edited_unixtime` - если сообщение было отредактировано в TG.
- `topic_created` / `topic_edited` service-сообщения в `messages[]` **не сохраняются** - вся инфа о топиках в `topics[]`.

Скрипт `telegram-snapshot.py` работает в трех режимах:

1. **Bootstrap.** `result.json` отсутствует -> создается шапка через `get_entity(chat_id)`, история целиком подтягивается с `min_id=0`. Удобно для проектов, где нет ручного TG Desktop экспорта.
2. **Migration.** `result.json` есть, но в формате сырого TG Desktop экспорта (без `topics[]` в шапке). Скрипт:
   - сохраняет копию в `result.pre-migration.json` (бэкап перезаписывается, если миграция запускается повторно);
   - извлекает `topic_created` / `topic_edited` из `messages[]` в `topics[]`;
   - проставляет `topic_id` сообщениям, поднимаясь по цепочке `reply_to_message_id` до сообщения, чей id есть в множестве корней тем;
   - очищает `reply_to_message_id`, если он указывал ровно на корень темы (теперь это выражается через `topic_id`);
   - удаляет `topic_created` / `topic_edited` service-сообщения из `messages[]`.
   - При ошибке миграции (поломанный JSON, неполные данные) - файл не трогается, чат пропускается, бэкап остается.
3. **Incremental pull.** Стандартный режим: тянем сообщения с `id > max(messages.id, topics.id)` (high-water mark учитывает оба массива - иначе service-only хвост после последнего обычного сообщения тянулся бы каждый запуск), апдейтим `topics[]`, дописываем в `messages[]`. Если есть реальные новые сообщения/топики/правки - сохраняем `result.prev.json` как baseline до них (для `telegram-deltas.py`); если миграция случилась без новых сообщений - `result.prev.json` не трогаем, дельта будет посчитана при следующем pull с реальными новыми. Запись `result.json` и `result.prev.json` атомарная - через `*.tmp` + `os.replace`, чтобы Ctrl+C / OOM не оставили битый JSON.

Все три режима могут сработать в одном запуске: для разных чатов из конфига - разное состояние. Скрипт принимает решение по каждому чату отдельно.

**Известные ограничения:**

- **Старые edits не подхватываются.** Скрипт тянет только сообщения с `id > high_water`. Если старое сообщение было отредактировано после прошлого pull - запись в `result.json` останется без нового `edited`. Если важно зафиксировать правки - удалить result.json и сделать bootstrap заново.
- **Bootstrap не делает checkpoint.** Долгий первый pull многотысячного чата при сбое (Ctrl+C, network) начнется заново - частично сохраненного `result.json` не будет, потому что атомарная запись делается только в конце. Это компромисс простоты против устойчивости.
- **Migration по reply-цепочке имеет лимит.** `migrate_legacy` определяет `topic_id` обычного сообщения, поднимаясь от его `reply_to_message_id` до сообщения, чей id есть в множестве корней тем. Если цепочка обрывается (reply на сообщение, которого нет в экспорте - например, удалено) - `topic_id` не проставится. Контент сообщения не теряется, только связь с темой.

### Шаг 8. Апгрейд скриптов в существующем проекте

Скрипты эволюционируют (новые поля, новые режимы, фиксы). Для апгрейда в существующем management-проекте используется `migrations/sync-from-canon.prompt.md`:

1. Открой Claude Code в корне проекта.
2. Скажи "сделай синк с canon".
3. Sync найдет, что `scripts/telegram-snapshot.py` / `scripts/telegram-deltas.py` разошлись с каноном. По каждому файлу отдельно спросит "обновить?".
4. Согласишься - локальная копия перезаписывается каноном, executable-бит сохраняется. Проектные правки скрипта (если были) затрутся.
5. Запусти `python3 scripts/telegram-snapshot.py` - на чатах в старом формате при первом запуске сработает migration-режим.

Не копировать скрипты вручную из других проектов - они могут расходиться по версии.

## Жесткие правила

1. **Auth-файл и .session - НЕ кладем в проектную папку.** Если проектная папка синхронизируется через облако (Yandex.Disk, Dropbox, iCloud), утечка api_hash и сессии в облако недопустима. Только в `~/.config/telegram-snapshot/` (локально на каждом устройстве отдельно).
2. **Первый интерактивный запуск делает пользователь сам в терминале.** Bash из этого скилла на интерактивный ввод не способен. Подготовить auth.json, дать команду, дождаться отчета пользователя.
3. **Не запускать `iter_messages` напрямую без get_dialogs() прогрева на свежей сессии** - получишь PeerUser-ошибку. Прогрев один раз на старте `amain()`.
4. **При использовании публичных ключей Telegram Desktop** - помнить, что это серая зона по ToS. Сами числа `api_id`/`api_hash` не секрет (они в открытых исходниках tdesktop), но ответственность за использование лежит на пользователе. Ограничения: не использовать для коммерческой автоматизации; не выходить за объем активности живого пользователя (без массовых запросов, рассылок, бот-подобных паттернов); не подключать к публичным сервисам/ботам. Только некоммерческие персональные сценарии (свой архив чатов, дейлики).

## Связанные файлы

- `scripts/telegram-snapshot.py` в корне проекта - эталонный скрипт инкрементального pull с `iter_dialogs()` прогревом и форматом записи, совместимым с Telegram Desktop export.
- `scripts/telegram-deltas.py` в корне проекта - расчет дельт между текущим и предыдущим snapshot для блока "Новое в чатах" в дейликах.
- `~/.config/telegram-snapshot/auth.json` - локальные credentials на устройство (не в проекте).
- `.telegram-snapshot.json` в корне проекта - проектная карта `{label: chat_id}`.
