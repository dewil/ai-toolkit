# Релиз Android APK в собственном канале

Применяй, когда проект раздает подписанный APK через собственный HTTPS-канал. Следуй release-контракту, версиям и действующим разрешениям проекта. Скилл не разрешает публикацию, не создает сервис раздачи и не дает реализацию updater.

## Подготовь и опубликуй релиз

- Сначала изучи инструкции релиза и сборочную конфигурацию проекта. Используй закрепленные в проекте версии Android SDK, Gradle, плагинов и build variants. Если нужного toolchain нет в `PATH`, найди существующую установку прежде чем предлагать установку; не назначай проектную версию глобальным default. См. [Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html).
- Сохраняй `applicationId`, непрерывность установленного сертификата/ключа подписи и `versionCode` выше уже установленного релиза. Если release key недоступен, останови релиз; не переключайся на debug key. Храни ключ вне Git и синкаемых папок; используй отдельную утвержденную процедуру off-host backup. См. [подпись Android-приложений](https://developer.android.com/studio/publish/app-signing).
- Собирай релиз по процедуре проекта и запускай его CI. Зафиксируй revision исходников, toolchain, package/application ID, fingerprint сертификата, размер и SHA-256 артефакта, а также состояние каждого CI-теста. Незапущенное отмечай `NOTRUN`; успешная компиляция, включая компиляцию instrumentation tests, не доказывает работу на устройстве.
- Для прямого HTTPS-канала сначала загрузи версионный APK как неизменяемый объект. Проверь его публичный HTTPS-ответ анонимным запросом без учетных данных и сверь hash; только затем атомарно обнови feed, чтобы он указывал на этот артефакт. Возврат feed к старой версии меняет предлагаемую загрузку, но не понижает уже установленный Android-пакет. Это не публикация в store.
- Принимай release workflow только после реального обновления N→N+1 с сохранением данных на матрице устройств/ОС проекта. Сборка, CI и device runtime - разные свидетельства; обязательный сценарий со статусом `NOTRUN` оставляет acceptance открытой.
- Перед публикацией следуй SDD проекта и действующим разрешениям. Успешная сборка или тест не дает права на deploy.

## Если проект отдельно запросил updater

Updater - отдельная задача по принятой проектной спеке; этот скилл не разрешает добавлять updater, сервис или автоматическую установку. Если такая задача поручена, используй условный [runbook](runbook.md) как список проверок, сверяя каждую с принятой спекой.

Не переноси в общий скилл код конкретного проекта, пути к signing keys, данные устройств и receipts релиза. Примеры для будущей документации создавай независимо и только синтетические.
