# asana-project

Пакетная запись в Asana из JSON-плана: `create` - проект с секциями и задачами с нуля, `tasks` - досыпка задач в существующий проект. Скрипт-эталон - `scripts/asana-project.py` (top-level папка `scripts/` в корне проекта). Только stdlib, из внешнего - опционально `certifi`.

## Зачем это поверх Asana MCP

MCP заводит задачи по одной, каждая - отдельное интерактивное подтверждение (даже там, где у конкретной версии MCP есть пакетное создание, у него нет идемпотентного повтора и синка сроков из плана-файла). Развернуть доску по итогам встречи (13 задач по трем секциям, у каждой исполнитель, описание, срок) - десятки шагов; через JSON-план - одна команда и одно подтверждение. Пробел не в "MCP не умеет", а в **пакетности и повторяемости**: план приходит целиком, живет файлом под рукой, и повторный прогон того же файла безопасен.

## Границы

- **Единичные операции** (создать одну задачу, сменить статус, написать комментарий) - Asana MCP: OAuth из коробки, отдельный токен не нужен.
- **Чтение длинной ленты комментариев** - скилл `asana-comments` (потолок MCP - 50 штук).
- **Пакетное разворачивание, досыпка, пересмотр сроков** - этот скилл.
- Скрипт намеренно НЕ делает: перенос существующей задачи в другую секцию, стирание срока (срок только добавляется и двигается), смену исполнителя существующей задачи, удаление и закрытие задач. Это единичные операции - MCP.

## Жесткий гейт перед --send

Доска общая: созданные задачи сразу видит команда, а откатывать массовую заливку - руками удалять задачи. Поэтому:

1. **Всегда сначала dry-run** (дефолт, без `--send`). Он показывает построчно: секция (есть / будет создана), задача, исполнитель, срок, и что произойдет - `ПРОПУСК (уже есть, без изменений)` либо `СРОК: 2026-08-03 -> 2026-08-10`. У `tasks` dry-run и send решают по одной и той же функции (`plan_effect`) - предпросмотр не разойдется с действием; у `create` действие всегда одно (создать все перечисленное), там расходиться нечему.
2. **Чей токен - реши до `--send`.** Dry-run показывает содержимое, но не от чьего имени уйдет запись. В проекте, где аккаунты Asana разведены (личный и заказчика - см. `rules/mcp-multi-account.md`), `--auth <файл>` обязателен в каждой команде: без него скрипт молча возьмет `ASANA_TOKEN` или дефолтный `~/.config/asana/auth.json`, а это может быть не тот аккаунт.
3. **Показать вывод пользователю и получить явное "ок"** на этот конкретный вывод - только потом `--send`, сразу после "ок". Прошло заметное время или доску кто-то трогал - повтори dry-run: доска общая, состояние могло уехать, а send перечитывает ее заново.
4. План со сроками - это еще и даты, которые увидят исполнители: проверь их на здравость (не в прошлом, не на выходных без причины).

## CLI

```bash
python3 scripts/asana-project.py workspaces                      # аккаунт и gid воркспейсов
python3 scripts/asana-project.py create --plan план.json         # предпросмотр
python3 scripts/asana-project.py create --plan план.json --send  # создать проект
python3 scripts/asana-project.py tasks --plan досыпка.json --send # досыпать в существующий
python3 scripts/asana-project.py tasks --plan план.json --auth ~/.config/asana/auth-work.json
```

В проекте с разведенными аккаунтами `--auth <файл>` добавляется к каждой из этих команд, включая dry-run (пункт 2 гейта).

Формат плана для `create` - `workspace` (gid из `workspaces`), `name`, `notes`, `sections`; для `tasks` вместо них один ключ `project` (gid доски - последнее число в ее URL):

```json
{
  "project": "1216875635976802",
  "sections": [
    {"name": "Этап 0", "tasks": [
      {"name": "Задача", "notes": "контекст", "assignee": "user@example.com", "due_on": "2026-08-03"}
    ]}
  ]
}
```

**Исполнитель задается почтой** - Asana принимает email в `assignee` наравне с gid, резолвить пользователей отдельным запросом не нужно; в плане человекочитаемые адреса. Опечатка в почте уронит прогон на середине. Для `tasks` это безопасно: повторный прогон доздаст недостающее без дублей. Для `create` - НЕТ: проект к этому моменту уже создан, повтор `create` создаст второй; скрипт при обрыве сам печатает в stderr gid проекта и напоминание доздать через `tasks` (то же напечатано в начале вывода: "проект создан ... gid").

**Повтор имени задачи внутри одного плана - ошибка**, скрипт откажется до первого сетевого вызова: какую из двух строк исполнять - неоднозначно. Имена в плане должны быть уникальны (сравниваются без хвостовых пробелов).

## Идемпотентность и повторные прогоны

- **Ключ - имя задачи.** Повторный прогон `tasks` с тем же планом не плодит дубли; изменение имени в плане означает новую задачу. Секции тоже переиспользуются по имени.
- **Матчинг не различает, кто задачу создал.** Одноименная задача, заведенная человеком руками, считается плановой: ей подтянется срок (а если она multi-homed - срок изменится во всех проектах, где она видна). В dry-run это видно как неожиданный `ПРОПУСК`/`СРОК` у задачи, которую ты считал новой - разберись до `--send`, обычно достаточно переименовать задачу в плане.
- **`create` НЕ идемпотентен**: повторный прогон создаст второй проект с тем же именем. Развернул доску - дальше только `tasks` с gid проекта.
- **Срок синхронизируется.** Если `due_on` существующей задачи отличается от плана - подтягивается (в dry-run видно `было -> стало`). Практический смысл: план дат живет в JSON под рукой, пересмотр сроков после этапа - правка файла и один прогон, а не ручной обход доски. Убрать дату из плана - НЕ стирает ее на доске.

## Авторизация

Та же, что у `asana-comments`: Personal Access Token в `~/.config/asana/auth.json` (`{"token": "..."}`, права 600) либо `ASANA_TOKEN`. Дополнительно `--auth <файл>` - для нескольких аккаунтов (файл на аккаунт); в проекте с разведенными аккаунтами он обязателен в каждой команде (см. гейт выше и `rules/mcp-multi-account.md`). Токен - секрет: в синкаемые папки, заметки и артефакты не класть (`rules/secrets-handling.md`).

Как получить PAT по шагам и три способа словить 401 (OAuth-токен MCP, client_id, client_secret - все не подходят) - в скилле `asana-comments`, раздел "Авторизация".

## Связанные файлы

- `scripts/asana-project.py` в корне проекта - эталонный скрипт (workspaces / create / tasks, dry-run по умолчанию).
- `scripts/asana-comments.py` - чтение ленты комментариев (read-only сосед по токену).
- `~/.config/asana/auth.json` - PAT, вне репозитория, права 600.
