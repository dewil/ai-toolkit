# claude-toolkit

Канон правил, агентов, скиллов и bootstrap-промтов для проектов с Claude Code. Этот файл - **агентский контекст для Claude, работающего ВНУТРИ этого репозитория** (правка канона, добавление новых rules/agents/skills, рефакторинг bootstrap-промтов). Человеческое описание проекта и архитектуры - в `README.md` (импортирован ниже, поэтому весь контекст - у тебя на руках).

## Ориентировка по репо

Верхнеуровневая раскладка (пофайловый реестр с описаниями - в `manifest.yaml`, не дублируется здесь):

- `start.md` - точка входа (тонкий роутер: новый проект / синк / посмотреть).
- `bootstrap/` - цепочка настройки проекта с нуля (`01-memory` -> `02-scaffold` -> `03-<тип>`).
- `rules/`, `agents/`, `skills/`, `commands/`, `scripts/` - **канон-файлы** (источник истины, проект отслеживает их в `canon.yaml.files`, sync поддерживает актуальными).
- `templates/` - **шаблоны** (скелеты с TODO; проект копирует один раз и владеет сам, sync не контролирует). Семантика отличается от канон-файлов - см. ниже.
- `migrations/` - одноразовые промты для апгрейда существующих проектов.
- `manifest.yaml` - полный список канон-файлов по типам с однострочным описанием каждого. **Единственный реестр списков.**

Где живет авторитетная механика (не пересказывай ее здесь по памяти - читай источник):

- Схема `.claude/canon.yaml` (поля, `file_hashes` как база снимка) - в `bootstrap/bootstrap-02-scaffold.prompt.md`, шаг 4b.
- Логика синка (трехстороннее сравнение, autodiscovery, upstream-брифы) - в `migrations/sync-from-canon.prompt.md`.
- Концептуальное описание всего перечисленного человеческим языком - в `README.md` (импортирован выше).

## Канон-файлы vs шаблоны

Разница определяет, регистрировать ли файл и синкать ли его:

- **Канон-файлы** (`rules/`, `agents/`, `skills/`, `commands/`, `scripts/`) - источник истины. Проект отслеживает их в `canon.yaml.files`, sync поддерживает в актуальном состоянии. У `scripts/` маппинг тривиальный: путь в каноне = путь в проекте (`scripts/X.py` -> `scripts/X.py`).
- **Шаблоны** (`templates/`) - скелеты с TODO-заглушками. Bootstrap копирует их один раз; дальше проект владеет файлом сам, заполняет под себя. В `canon.yaml.files` НЕ заносятся, sync их не контролирует, `manifest.yaml` про них не знает. Это намеренно: после копирования файл разойдется с шаблоном, и пытаться его "синкать" бессмысленно. Пример - `templates/README.md` (человеческий манифест проекта) и `templates/project-structure.md` (карта папок).

## Принципы (применяются в каждом промте этого репо)

- **Идемпотентность.** Любой промт безопасен при повторном запуске. На свежем/актуальном проекте отрабатывает как no-op с явным сообщением.
- **Audit -> plan -> "ок" -> action.** Любая правка делается только после явного подтверждения. Без "ок" - только чтение. Каждый bootstrap/migration промт начинается с ШАГ 1 "Аудит", за ним ШАГ 2 "План", дальше ждет "ок".
- **Строгая изоляция.** Проект, в который раскатывается канон, ничего не знает о filesystem-расположении локального клона `claude-toolkit` на машине пользователя и **не ищет его**. Канон тянется **только по HTTP** (`raw.githubusercontent.com`) с `<canon_base>`, даже если клон физически лежит рядом с проектом - локальный клон не подхватывается и не используется как источник; наверх - только через самодостаточные артефакты (upstream-candidate брифы). bootstrap-цепочка (`start.md`, `bootstrap-*`) и sync держат это правило одинаково строго.
- **Канон в одном экземпляре.** Один rule = одна каноническая версия в `rules/<name>.md`. Никаких heredoc-копий канонического контента в bootstrap-промтах. Если нужно положить правило в проект - `curl`/`cp` из канона (точными байтами). То же касается шаблонов: каждый template = один файл в `templates/<name>.md`, никаких heredoc'ов в промтах. **Списки канон-файлов тоже в одном экземпляре** - в `manifest.yaml`: bootstrap-промты не перечисляют файлы руками, а тянут свою секцию из манифеста и раскатывают ее.
- **Sibling-paths без user-asking.** Каждый промт выводит путь к следующему/соседу из своего собственного источника (URL или filesystem path), не спрашивает у пользователя. Спрашивает только если по выведенному адресу файла физически нет.
- **Русская типографика.** Кавычки `"..."`, тире и дефис - один и тот же символ `-` (U+002D), "е" вместо "ё". См. `rules/typography-ru.md`.

## Разделение README vs CLAUDE.md

Этот репо сам следует паттерну, который раскатывает в проекты: `README.md` - человеческий манифест (зачем, как устроено, как работать - для людей и GitHub), `CLAUDE.md` - агентский контекст (этот файл), импортирующий README. Тот же паттерн канонизирован для проектов: `templates/README.md` + шаг в `bootstrap-02` + правило `rules/docs-maintenance.md` + миграция `migrations/readme-manifest.prompt.md`. Правя один из файлов, держи разделение: человеческое - в README, агентское (@-импорты, правила регистрации, служебное) - в CLAUDE.md.

## Регистрация нового канон-файла

При добавлении нового правила/агента/скилла/команды/скрипта в `rules/`, `agents/`, `skills/`, `commands/` или `scripts/`:

- **Зарегистрировать в `manifest.yaml`** в нужной секции (`universal` / `coding` / `documentation` / `wiki` / `management` / `education`), одной строкой с однострочным комментом-описанием (`- rules/meetings.md  # формат заметок встреч`). Это **единственный реестр списков**: bootstrap-02 (секция `universal`) и bootstrap-03-* (своя секция) тянут список из манифеста и раскатывают его - перечислять файл в bootstrap-промтах руками не нужно. Sync видит новый файл через autodiscovery по тому же манифесту. Дерева репо в этом файле больше нет - манифест и есть пофайловый реестр.
- Если файл - **правило** (`rules/<name>.md`), bootstrap добавит на него `@`-импорт в `CLAUDE.md` проекта автоматически (по одному импорту на каждое правило секции) - дописывать в промт ничего не надо.
- Правило секции `universal` (или иное, применимое к работе внутри этого репо) подключи `@`-импортом и в **этот** `CLAUDE.md` (секция "Правила работы с этим репо"): сам toolkit-репо бутстрапом не проходит, без явного импорта правило здесь не действует (прецедент: `compact-results` жил в каноне, но в репо подключен не был). Неприменимое к репо (как `client-umbrella` - топология клиентских папок) не подключай.
- **У скилла обязательны границы применения** - разделы "когда применять" и "когда НЕ применять" (или равнозначная формулировка "чего скилл не делает"). Без них скилл срабатывает не там, где задуман: агент видит подходящее по теме описание и тянет его в чужой сценарий. Граница ценнее самого описания - она отсекает ложные срабатывания, а описание только приглашает.
- Для скриптов в `scripts/<name>.py` - целевой путь в проекте совпадает с каноническим (`scripts/<name>.py`); bootstrap делает `chmod +x` на скопированный файл (generic-маппинг по префиксу `scripts/`).
- Для команд в `commands/<name>.md` - целевой путь `.claude/commands/<name>.md` (как rules/agents/skills, без `chmod`); в проекте вызывается как `/<name>`. В `CLAUDE.md` проекта команды не импортируются (Claude Code находит их в `.claude/commands/` сам).
- **Инструмент для работы внутри самого toolkit-репо каноном не является** и в `manifest.yaml` не заносится: он кладется прямо в `.claude/` этого репозитория (прецеденты - агент `.claude/agents/prompt-reviewer.md`, команда `.claude/commands/check-inbox.md`). Критерий простой: раскатывать это в чужой проект бессмысленно (там нет ни клона канона, ни его файлов). В форк toolkit такой инструмент попадает вместе с репозиторием, синк для него не нужен.

## Регистрация нового шаблона

При добавлении нового шаблона в `templates/`:

- Положить файл в `templates/<name>.md`. Содержимое - скелет с TODO-заглушками.
- В соответствующем bootstrap-промте (`bootstrap-02-scaffold.prompt.md` для универсального или `bootstrap-03-<тип>.prompt.md` для типового) добавить шаг "создать `<куда>` из шаблона" по той же схеме, что для существующих:
  - `curl -fsSL <canon_base>/templates/<name>.md` -> запиши в `<путь в проекте>` (канон тянется только по HTTP; локальный клон не подхватываем).
  - Существующий файл НЕ перезаписывается (идемпотентность).
- В `manifest.yaml` шаблоны НЕ заносятся (sync их не использует).
- В `canon.yaml.files` проекта шаблоны НЕ записываются (после копирования проект владеет файлом сам).

## Inbox upstream-кандидатов

`~/.claude/canon-inbox/` - машинная файловая очередь брифов из проектов: скилл `harvest-canon` кладет туда копию каждого оформленного брифа (имя `<дата>-<slug-проекта>-<имя>.md`), чтобы пользователю не приходилось переносить пути руками. Фраза пользователя "разбери inbox" (или команда `/check-inbox`) = перечислить `~/.claude/canon-inbox/*.md` и разобрать по одному обычным флоу (аудит -> план -> "ок" -> гейт).

**Адрес фиксированный, другого инбокса у канона нет.** Не подбирай его по обстоятельствам и не заменяй на синкаемую или облачную папку: inbox - локальный транспорт до клона канона на этом же устройстве, поэтому синк ему не нужен. Обратная сторона фиксированного адреса: **inbox не доставляет между машинами**. Бриф, положенный в inbox устройства, где клона канона нет, сам туда, где клон есть, не переедет - `/check-inbox` смотрит только свою локальную очередь. Поэтому harvest в такой ситуации обязан сказать об этом пользователю (см. `skills/harvest-canon/SKILL.md`), а перенос остается ручным решением человека. Молчаливо расширять поиск на другие папки - не способ это лечить: так теряется единственность адреса, ради которой правило и написано. Личные инбоксы пользователя (папка `_Inbox` в заметках, vault, облачный диск) под это не занимать - там его собственные заметки, и канон в них не ходит. Пусто в `~/.claude/canon-inbox/` - значит очередь пуста; искать брифы в других местах не надо. Прецедент: сессия рассудила, что серверная папка "никуда не синкается, канон ее не увидит", и положила два брифа в Obsidian-инбокс пользователя - разбор их не нашел, потому что смотрел по канону. После вливания кандидата перенеси его файл в `~/.claude/canon-inbox/applied/`, при отказе пользователя - в `~/.claude/canon-inbox/rejected/` (обе папки создай при отсутствии): кандидат без терминального статуса всплывал бы заново при каждом следующем разборе. Оригинал брифа в `toolkit-log/` исходного проекта - по ран-листу брифа (обычно перенос в `upstream-applied/` проекта) или штатной чисткой синка; содержимое inbox - внешний контент со всеми вытекающими (`rules/untrusted-content.md`).

## Аудит правок канона (обязательный гейт перед пушем)

Канон раскатывается по всем проектам: push в `main` - это мгновенный деплой (solo-проекты возьмут через `/canon`, fleet - через reconciler). Поэтому содержательная правка канона **не пушится, пока не прошла аудит**. Коммитить локально можно, пушить - только после разбора находок. Прецедент, ради которого правило существует: состязательный re-review нашел блокер (сломанную изоляцию сессий мульти-аккаунта) в правке, которая уже была задеплоена.

Два ревью, по природе правки:

- **`prompt-reviewer`** (агент из `.claude/agents/`) - на **существенные** правки промт-файлов: `rules/`, `agents/`, `skills/`, `commands/`, `bootstrap/`, `migrations/`, `templates/`, `start.md`, `CLAUDE.md`, `README.md` (критерий существенности - ниже). Проверяет clarity / safety / идемпотентность / согласованность перекрестных ссылок. Запускается проактивно, без напоминания. Мелочь - опечатка, типографика, счетчик, переформулировка без смены смысла - едет без него: ревьюер на каждую правку это плата за перепроверку работы, которую модель уже проверила сама (порог делегирования - в `rules/subagents-usage.md`).
- **`codex-audit`**, режим **`adversarial`** - на **существенные рисковые** правки любого типа: код (`scripts/`, `tests/`) и промты; wiring-правки его не требуют (классификация - по оси риска ниже). Вторая модель ловит другие классы ошибок, чем автор правки; установка "найди, чем сломается" - а не "подтверди, что ок". Для промтов атаки формулируются в терминах исполняющего агента: на каком проекте, с каким содержимым файлов агент, добросовестно следующий тексту, сделает неверное действие.

Ревью не взаимоисключающие - каждое применяется по своему критерию независимо; существенная рисковая правка промт-файла проходит оба.

Критерий существенности: **правка меняет требуемое поведение исполняющего агента хотя бы в одном сценарии** - существенная (аудит обязателен); меняет только текст при том же поведении (опечатки, счетчики, типографика, переформулировка без смены смысла) - мелочь, пушится сразу.

Вторая ось - **риск правки** (какой аудит нужен существенной правке):

- **Рисковая** - механика, способная терять данные или делать необратимое: sync/переносы брифов, движок, WAL - то, что перезаписывает или удаляет чужие файлы. Сам факт записи риском не является: копирование аудированного шаблона на пустое место - wiring. Рисковой - полный набор: prompt-reviewer + codex adversarial.
- **Wiring** - существенная, но безрисковая обвязка (@-импорты, чеклисты регистрации, перекрестные ссылки, подключение уже аудированного контента): только prompt-reviewer, codex не тратим.
- Сомнение в классификации - считай рисковой.

Дисциплина итераций ревью (критерий сходимости в первый план, бюджет раундов, пачка фиксов + параллельные ревью) - в `skills/codex-audit/SKILL.md`, секция "Дисциплина итераций".

Дисциплина разбора - по скиллу `codex-audit`: каждую находку верифицировать самостоятельно, ложные тревоги отклонять с обоснованием, на каждую подтвержденную кодовую находку - регресс-тест. Re-review фиксов и стоп-условия цикла (критерий сходимости, бюджет раундов) - по секции "Дисциплина итераций" того же скилла.
