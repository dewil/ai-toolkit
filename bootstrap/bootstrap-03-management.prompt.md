# Промт: scaffold для управленческих проектов

Этот файл - инструкция для Claude Code. Запускать **после** `bootstrap-02-scaffold-common.prompt.md`: открой Claude Code в **корне проекта** и попроси выполнить этот файл (например: `выполни инструкции из <путь>/bootstrap-03-management.prompt.md`).

Для проектов, где AI ничего не забывает, ведет саммари встреч, генерит планы, контролирует команду.

Промт безопасен для существующих проектов. Сначала аудит, действия - после "ок". Существующие файлы не перезаписываются.

Добавляет к общему scaffold:

  - `meetings.md` - формат заметок встреч
  - `tasks-tracking.md` - формат задач и планов
  - `artifacts-structure.md` - структура папок управленческого проекта
  - `meeting-transcripts.md` - двойной формат транскрипций (KTalk + mymeet) и резюме `.summary.md`
  - `name-cross-check.md` - сверка имен из транскрипций по справочнику команды/стейкхолдеров

  - `estimates-in-hours.md` - оценки в часах, не в человеко-днях

# Заметки встреч

## Именование файлов

`Встречи/<YYYY-MM-DD>-<короткая-тема-через-дефис>.md`

Примеры:
- `Встречи/2026-05-08-product-roadmap-q3.md`
- `Встречи/2026-05-12-team-standup.md`

## Обязательные секции

```markdown
# <Тема>

**Дата:** YYYY-MM-DD
**Участники:** <имена через запятую>
**Тип:** созвон / письменно / личная встреча

## Контекст

Зачем встреча, что было до.

## Обсуждение

- Тема 1: краткое содержание.
- Тема 2: ...

## Решения

- <Решение>. Владелец: <имя>. Срок: <дата или TBD>.

## Action items

- [ ] <Задача>. Кто: <имя>. Срок: <дата>.

## Открытые вопросы

- <Вопрос>, ждет от <кого/чего>.
```

## Правила ведения

- Если стенограмма есть - клади ее в `Встречи/Транскрипции/<имя>.md` и ссылайся из заметки.
- Если решение принято - оно идет и в `Решения/` отдельным файлом, если важное (см. artifacts-structure.md).
- Action items с дедлайном - попадают в Планы/ или в общий tracker.
- Не редактируй заметки прошедших встреч; коррекции - через "Обновление от <дата>" в конце файла.

# Задачи, планы, контроль

## Формат задачи

Каждая задача в Планы/ или в action items встречи:

```markdown
- [ ] <Описание задачи в инфинитиве>
  - **Владелец:** <имя или TBD>
  - **Срок:** <YYYY-MM-DD или TBD>
  - **Статус:** todo / in-progress / blocked / done
  - **Зависит от:** <ссылка на задачу или "-">
  - **Блокеры:** <текст или пусто>
```

Минимально достаточный набор: описание + владелец + срок. Остальное - по необходимости.

## Статусы

- `todo` - еще не начато.
- `in-progress` - в работе, есть прогресс.
- `blocked` - ждет внешнего фактора, нужно явно указать какого.
- `done` - завершено, есть подтверждение.

## Правила

- Не закрывай задачу, пока не подтверждено выполнение.
- Просроченную задачу не "молча" переноси - сначала фиксируй причину переноса.
- При смене владельца - явно отметь в истории файла.
- Статус устарел больше 14 дней - tracker должен это видеть.

# Структура артефактов

```text
.
├── Встречи/             # Заметки встреч (см. meetings.md)
│   └── Транскрипции/      # Сырые стенограммы (опционально)
├── Планы/                # Текущие планы и активные задачи
│   ├── current.md        # Что в работе сейчас
│   └── archive/          # Завершенные планы
├── Решения/            # Важные решения отдельными файлами
│   └── YYYY-MM-DD-<тема>.md
├── Команда/                 # Профили команды, роли, контакты
│   └── people.md
└── docs/                 # Постоянная документация (общая для проекта)
    └── dev/              # Рабочие черновики (если применимо)
```

## Правила

- Решение становится файлом в `Решения/`, если: меняет курс, требует объяснения "почему именно так", влияет на нескольких людей, дорого откатывать. Иначе - остается только в заметке встречи.
- `Команда/people.md` - единое место с ролями и зонами ответственности. Обновляется при изменении состава.
- Что не подходит ни под одну категорию - класть в `docs/`.
- Папки создаются по мере необходимости; пустые папки коммитить не обязательно.

# Транскрипции встреч

Если для встреч используются автоматические сервисы транскрипции, типичный набор - два движка, дополняющих друг друга. Хранить рядом, использовать взаимодополняюще.

## Источники транскрипций

- **KTalk (`.txt`)** - встроенная транскрипция. Точные таймкоды и надежная разметка спикеров по ФИО, но слабее распознает русский. **Брать отсюда:** авторство фразы, точные таймкоды, имена спикеров.
- **mymeet.ai (`.md` + `.json`)** - структурированный отчет: супер-краткое, саммари по темам, задачи, транскрипт с таймкодами. **Брать из `.md`:** смысл встречи при чтении глазами. **Брать из `.json`:** для программной обработки - `chapters` (главы с границами в секундах), `word_timings` (поминутные таймкоды слов), второе саммари по шаблону `tasks`, метаданные. mymeet галлюцинирует в шапке (путает имена/стороны), сшивает реплики, укрупняет таймкоды - сверять имена с KTalk.

Старый формат mymeet `.docx` устарел; если встретился - конвертировать в `.md` (через python-docx, маппинг стилей `Heading 4` → `**название**`, `Heading 3` → `**секция**:`, `Heading 2` → `### подсекция`, `List Bullet/Number` → `-`).

## Где что брать

- **Смысл и чтение глазами:** mymeet `.md`.
- **Точное авторство фразы и таймкод:** KTalk `.txt`.
- **Программная обработка** (главы, точные таймкоды слов, метаданные): mymeet `.json`.
- **Имена и стороны** в mymeet всегда сверять с KTalk (mymeet ошибается).

## Резюме `.summary.md`

Для каждой встречи рядом с raw-транскрипциями кладется файл `<имя-встречи>.summary.md` - верхнеуровневое резюме под отправку заказчику/команде.

- Raw НЕ удалять - это источник истины для спорных формулировок и таймкодов.
- Стиль резюме - верхнеуровневый, не детальный, не как у mymeet (детальный mymeet-стиль не подходит для рассылки).
- Шаблон: тема, дата, участники, ключевые обсуждения, решения с владельцами и сроками, action items, открытые вопросы.
- Имена при первом упоминании - в однозначной форме (ФИО или Имя + Фамилия в скобках), чтобы не путать тезок. См. `name-cross-check.md`.

# Сверка имен из транскрипций

Автоматические транскрипции (KTalk, mymeet, и любые подобные) часто искажают русские имена - особенно нерусифицированный движок mymeet. Перед записью в саммари, заметки, отчеты или любые другие артефакты, которые увидят люди, **сверять имена** с проектным справочником.

## Где справочник

В управленческом проекте обычно ведется:
- Таблица команды (ФИО, должность, ФИО в Redmine/Jira/чате) - часто Google Sheets.
- Реестр стейкхолдеров (со стороны заказчика) - аналогично.

Перед записью имени в артефакт сверь его с этими таблицами.

## Правила

- При первом упоминании в файле - давай однозначную форму: ФИО или Имя + Фамилия в скобках. Это критично, когда у тезок одинаковое имя ("Дима - это Фамилия1 или Фамилия2?", "Миша - Фамилия3 или Фамилия4?").
- При сомнении (распознанная форма не совпадает ни с одним именем из справочника) - явно отметь "[имя?]", не записывай как факт.
- Типичные искажения, которые стоит проверять: усечения ("Артыш" вместо "Фамилия5 Артыш"), фонетическая замена ("Сабебек" вместо "Асылбек"), удвоение/сшивка соседних реплик.

## Когда сверять

- В саммари встреч (`.summary.md`).
- В action items и решениях, попадающих в `Планы/` и `Решения/`.
- В любой коммуникации наружу (письма, отчеты, статусы).

В сыром транскрипте имена не правим - он остается как источник истины с искажениями.

# Google Sheets через MCP `google-workspace`

Если в проекте используется MCP-сервер `google-workspace` для чтения/записи Google Sheets - вот рабочие нюансы.

## Чтение и запись

- `mcp__google-workspace__read_sheet_values` - читать диапазон.
- `mcp__google-workspace__modify_sheet_values` - писать. По умолчанию `value_input_option="USER_ENTERED"` - формулы и даты интерпретируются.

## Адресация

- `spreadsheet_id` берется из URL после `/d/`.
- `gid` из URL - это **внутренний sheetId**, а НЕ имя листа.
- В диапазоне (`range_name`) надо указывать **имя листа в одинарных кавычках**, если оно содержит дефисы, пробелы или спецсимволы: `'1-1'!C100`. Без кавычек Sheets API вернет "Unable to parse range".
- Если имя листа неизвестно - не перебирать варианты вслепую: получить список листов через `mcp__google-workspace__get_drive_file_content` (по ID файла) или прочитать без указания листа (вернет первый) и уточнить у пользователя.

## Безопасность записи

- Перед записью **всегда** читать текущее значение ячейки/диапазона, чтобы не затереть данные.
- Если запись сложная (несколько ячеек, формулы) - сначала сделать предпросмотр на тестовом листе, потом писать в основной.

## Аккаунт

- Для всех вызовов `mcp__google-workspace__*` в параметре `user_google_email` использовать **рабочий** Google-аккаунт пользователя. Системный `userEmail` из контекста Claude может не совпадать с рабочим - уточняй и фиксируй в memory.

# Оценки трудоемкости

Все оценки работ - **в часах**, не в человеко-днях.

- 1 человеко-день = 8 часов.
- При импорте оценок из систем, где трудоемкость хранится в днях - конвертируй в часы.
- В планах, графиках, ФБ, отчетах для команды и заказчика - единица измерения "часы".
- Если источник оценок дает дни - явно отметь конвертацию: "8 ч/д = 64 ч".

**Why:** часы дают более тонкое разрешение для коротких задач (1-4 ч), не округляются до полудня; в планировании при разных размерах команд проще считать в часах, не пересчитывая дни.

## 5а. Встречи

Расшифровки организованы по адресатам и периодам. Формат имени файла: `ГГГГ-ММ-ДД <короткая-тема>.<ext>`.

Источники транскрипций (см. `meeting-transcripts.md`):
- `.txt` - KTalk: точные таймкоды и спикеры.
- `.md` + `.json` - mymeet.ai: смысл, структура, программная обработка.
- `.summary.md` - верхнеуровневое резюме под отправку (не удаляем raw).

Структура:
- `Встречи/с заказчиком/<год>/<период>/`
- `Встречи/с командой/<год>/<месяц>/` - дейли
- `Встречи/с руководством/`
- `Встречи/1-1/<ФИО>/`
- `Встречи/Чаты/` - экспорты рабочих чатов (опционально)

Регулярное расписание (если применимо):
- Синк с заказчиком - <день недели> в <время>
- Дейли с командой - <день/каждый день> в <время>
