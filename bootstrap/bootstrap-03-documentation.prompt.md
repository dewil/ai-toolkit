# Промт: scaffold для проектов документации

Этот файл - инструкция для Claude Code. Запускать **после** `bootstrap-02-scaffold.prompt.md`: открой Claude Code в **корне проекта** и попроси выполнить этот файл (например: `выполни инструкции из <путь>/bootstrap-03-documentation.prompt.md`).

Промт безопасен для существующих проектов. Сначала аудит, действия - после "ок". Существующие файлы не перезаписываются.

Добавляет к общему scaffold:

- канон-файлы специализации documentation (агент `copy-editor` - вычитка текстов) - набор = **секция `documentation` манифеста** (`manifest.yaml`), поименно здесь не дублируется
- шаблон `rules/style-guide.md` (тон, структура, термины - копируется один раз, дальше заполняется проектом) + `@`-ссылка в `CLAUDE.md`
- allow для генераторов статсайтов в `.claude/settings.json` (по подтверждению, по стеку)

---

КОНТЕКСТ ЦЕПОЧКИ. Это шаг 03. **Источник этого файла** (всегда HTTP-URL) определяет базу для канонических файлов:

- `canon_base` = подняться на один уровень из `bootstrap/`. Например, если этот файл загружен по URL `.../main/bootstrap/bootstrap-03-documentation.prompt.md`, то `canon_base = .../main/`.
- Канонические агенты специализации: `<canon_base>/agents/*.md`.
- Предыдущий шаг (сиблинг): `bootstrap-02-scaffold.prompt.md` в той же папке.

**Канон только по HTTP.** `<canon_base>` - всегда HTTP-URL; канон тяни исключительно по HTTP. Локальный клон claude-toolkit на машине (даже соседней папкой с проектом) не ищи и не подхватывай. Это держит изоляцию: раскатывается закоммиченный `main`, не чужое рабочее дерево.

Ты в корне проекта документации. Раскатываешь специализацию scaffold под документацию: агент-корректор, шаблон стайлгайда, allow под генераторы. Базовый scaffold должен быть уже на месте (bootstrap-02-scaffold).

ВАЖНО. Промт безопасен для существующих проектов. Сначала аудит, потом план, потом ждешь "ок", только потом действуешь. Существующие файлы НЕ перезаписываешь.

ШАГ 1. Аудит (только чтение).

- pwd - корень проекта.
- Получи секцию `documentation` манифеста (`curl -fsSL <canon_base>/manifest.yaml`) - это целевой набор файлов специализации (единственный источник списка).
- Перечисли существующие:
  - какие файлы секции `documentation` уже есть в проекте (по generic-маппингу: `rules/*` -> `.claude/rules/*`, `agents/*` -> `.claude/agents/*`)
  - .claude/canon.yaml - есть ли (должен быть после bootstrap-02), что в `files` и `file_hashes`
  - CLAUDE.md - какие @-ссылки уже есть
  - .claude/settings.json - какие allow уже есть
- Определи генератор статсайта по маркерам в корне (только маркеры, не глубокий анализ):
  - MkDocs: mkdocs.yml
  - Hugo: config.toml/hugo.toml + content/
  - Sphinx: conf.py, Makefile с целью html
  - Docusaurus: docusaurus.config.js, package.json с зависимостью @docusaurus
  - другое: укажи, какие маркеры нашел (или что генератора нет - чистый markdown)

ШАГ 2. Целевое состояние.

A. Канонический набор documentation = секция `documentation` в `manifest.yaml` (агенты специализации). Источник истины списка - **только манифест**; здесь файлы поименно не перечисляем. На ШАГ 4 фетчнешь манифест и раскатаешь секцию `documentation` по generic-маппингу: `rules/<name>.md` -> `.claude/rules/<name>.md` (+ @-импорт в CLAUDE.md); `agents/<name>.md` -> `.claude/agents/<name>.md`; `scripts/<name>` -> `scripts/<name>` в корне + `chmod +x`.

B. CLAUDE.md содержит `@`-ссылку на каждое правило `rules/*` из секции `documentation` (если правила в секции есть). Дополнительно содержит ссылку `@.claude/rules/style-guide.md` (шаблон, добавляется отдельно на шаге 4b).

C. `.claude/canon.yaml`:
   - `files` дополнен всеми путями секции `documentation`, которых там еще нет;
   - `file_hashes` дополнен sha256 раскатанных файлов;
   - `project_type` - список, и `documentation` в нем (если списка нет/пустой - инициализируется на ШАГ 4; если `documentation` отсутствует среди других типов - добавляется на ШАГ 4).

D. `.claude/rules/style-guide.md` - копируется из `<canon_base>/templates/style-guide.md` (см. ШАГ 4b). Это шаблон, не каноническое правило: тон и термины у каждого проекта свои, sync его не контролирует.

E. .claude/settings.json дополнен allow для генератора статсайта по результату аудита (предложение, по подтверждению).

ШАГ 3. План.

Таблица: файл / действие / статус. Для существующих - "не трону". Для отсутствующих - "создам".

Отдельно покажи список allow генератора, которые предлагаешь добавить в settings.json, исходя из аудита (см. ниже шаблоны). НЕ применяй без отдельного "ок".

Для CLAUDE.md - если файла нет или нет @-ссылок на правила `rules/*` секции `documentation` (если они есть) или нет `@.claude/rules/style-guide.md` - покажи, что добавишь.

Для canon.yaml - покажи, какие пути секции `documentation` допишешь в `files` (и их sha256 в `file_hashes`).

Жди "ок". Без подтверждения - не действуй.

ШАГ 4. Действуй (после "ок").

### 4a. Раскатай секцию `documentation` манифеста

1. Возьми секцию `documentation` манифеста, полученного в ШАГ 1.
2. Для каждого файла секции, которого еще нет в проекте (локальный путь - по generic-маппингу из ШАГ 2 A):
   - получи канонические байты **точными байтами** (`curl -fsSL <canon_base>/<path>`; не `WebFetch` - он лоссовый, ломает sha256 и корежит `.py`);
   - запиши в локальный путь; для `scripts/` поставь `chmod +x`;
   - посчитай sha256 записанных байт (`shasum -a 256 <локальный путь> | awk '{print $1}'`, на Linux - `sha256sum`) - база снимка для `file_hashes` в 4c.

Существующие файлы НЕ перезаписываются (для них хеш не пишем - база определится на первом синке). Для апгрейда к актуальной версии канона есть `migrations/sync-from-canon.prompt.md`.

### 4b. Создай `.claude/rules/style-guide.md` из шаблона

Если файла еще нет в проекте:

- Получи шаблон точными байтами: `curl -fsSL <canon_base>/templates/style-guide.md` -> запиши в `.claude/rules/style-guide.md`.

Существующий файл НЕ перезаписывай.

Это шаблон, а не каноническое правило - после копирования проект владеет файлом сам, sync его не контролирует, в `canon.yaml.files` его НЕ записываем. В `canon.yaml.local_only` тоже не пишем (по умолчанию это понятно).

### 4c. Допиши `.claude/canon.yaml`

- В `files` добавь все пути секции `documentation`, которых там еще нет (в каноническом виде, без `.claude/`-префикса).
- В `file_hashes` добавь sha256 (из 4a) для файлов, которые реально записал; для уже существовавших файлов запись не добавляй. Если секции `file_hashes` в файле еще нет - заведи ее.

Правь точечно, не пересоздавая файл. Если `canon.yaml` нет - значит bootstrap-02 не выполнялся; сообщи об этом и не создавай `canon.yaml` сам (это работа шага 02).

Отдельно про `project_type` (всегда **список**):

- Если поля нет вообще или это пустой список `[]` - инициализируй `project_type: [documentation]`.
- Если поле уже содержит `documentation` - не трогай (идемпотентность).
- Если поле содержит другие типы, но без `documentation` - **добавь** `documentation` в конец списка. Это нормальный случай мультиспециализации; не "миграция типа", не спрашивай - добавляй.
- Если поле - скаляр-строка (старый формат до перехода на список) - перепиши в список и добавь `documentation`. Сообщи в отчете о миграции формата.

### 4d. Дополни существующие файлы

Дополнения CLAUDE.md (@-ссылки на правила `rules/*` секции `documentation`, если они есть, и ссылка `@.claude/rules/style-guide.md`) и settings.json (allow генератора) - по отдельному "ок" на каждый пункт.
