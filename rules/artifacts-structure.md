# Структура артефактов

```text
.
├── Встречи/             # Заметки встреч + raw-транскрипции рядом, по адресату/периоду в подпапках (см. meetings.md)
├── Планы/                # Текущие планы и активные задачи
│   ├── current.md        # Что в работе сейчас
│   └── archive/          # Завершенные планы
├── Решения/            # Важные решения отдельными файлами
│   └── YYYY-MM-DD-<тема>.md
├── Команда/                 # Профили команды, роли, контакты
│   └── people.md
└── docs/                 # Постоянная документация (общая для проекта)
    └── dev/              # Рабочие черновики (если применимо)
```

## Где чьи встречи (проект с несколькими направлениями)

Дерево выше - для проекта с одним направлением. У клиента-зонтика (`client-umbrella.md`) направлений несколько, и тогда встреча живет **внутри своего направления**: `<направление>/Встречи/с командой/<год>/<месяц>/`. Иначе встречи разных направлений оказываются в одной корневой папке и различимы только по содержимому.

В корне зонтика остается только сквозное по клиенту - то, что не привязано к одному направлению:

- 1-1 с самим заказчиком: в таком разговоре темы вперемешку (одно направление, другое, посторонние сюжеты), резать их по темам значит разносить файлы одной даты по разным папкам;
- зеркала чатов, если канал общий по клиенту.

Структура внутри любого корня прежняя (`с заказчиком/`, `с командой/`, `1-1/<ФИО>/`, `чаты/<label>/`) - меняется только то, где этот корень. Как это настраивается у снапшота встреч - см. скилл `mymeet-snapshot` (`meetings_root` и полный путь в `dest`).

## Правила

- Решение становится файлом в `Решения/`, если: меняет курс, требует объяснения "почему именно так", влияет на нескольких людей, дорого откатывать. Иначе - остается только в заметке встречи.
- `Команда/people.md` - единое место с ролями и зонами ответственности. Обновляется при изменении состава.
- Что не подходит ни под одну категорию - класть в `docs/`.
- Папки создаются по мере необходимости; пустые папки коммитить не обязательно.
