# Покрытие тестами

## Цикл TDD (RED-GREEN-REFACTOR)

Формулировка цели как теста ("воспроизведи баг тестом, потом почини") уже есть в `karpathy-guidelines.md` (п.4, goal-driven execution) - это про "зачем". Здесь - операционная механика цикла, "как именно писать код по шагам".

Пиши тест до кода, тремя жесткими фазами подряд:

1. **RED** - напиши тест, который описывает желаемое поведение и еще не проходит. Обязательно запусти его. Обязательно посмотри своими глазами, что он падает. Прочитай сообщение об ошибке и убедись, что причина падения - отсутствие нужной логики, а не опечатка, не сломанный импорт, не неверная настройка окружения.
2. **GREEN** - напиши минимальный код, достаточный, чтобы тест стал зеленым. Не забегай вперед: не добавляй то, что тест не требует.
3. **REFACTOR** - почисти код и/или тест, пока тесты зеленые. Затем коммить.

> Антипаттерн: не пиши тест после кода задним числом. Тест, подогнанный под уже написанный код или под текущее (в том числе багованное) поведение, не выполняет цель TDD - он фиксирует то, что код УЖЕ делает, а не то, что он ДОЛЖЕН делать. Если код написан раньше теста - тест для него по определению не RED-старт.

## Тесты с чистого листа (test-writer)

Для содержательной фичи тесты пишет субагент `test-writer` с чистым контекстом: сессия, писавшая реализацию, пишет тесты под свою же интерпретацию спеки и зелено проходит мимо собственных багов - тот же механизм, ради которого ревью делает вторая модель. Дисциплина:

- **Бриф - только спека и публичный контракт**: пути к ТЗ и сигнатурам плюс образец стиля тестов. Без пересказа задачи своими словами - пересказ и есть канал заражения интерпретацией.
- **Порядок**: в идеале тесты до реализации (RED-фаза выводится из ТЗ); пост-фактум допустимо, но агенту запрещено читать реализацию (запрет зашит в его описание).
- **Разбор расхождений**: красный тест на реализации не "чинится до зеленого" - каждый случай разбирается отдельно: неверна реализация - чинить код; неоднозначна спека - к пользователю. Вопросы агента к спеке - сигнал дыры в ТЗ, возвращаются в фазу требований.
- На тривиальные правки отдельного агента не гонять - тесты пишутся как обычно.

Где тесты вслепую стоят в общем порядке работы над фичей - спека, аудит домена, реализация, сверка второй моделью - описано в `sdd-pipeline.md`; здесь только дисциплина самого шага.

- Каждый новый код должен быть обложен тестами в рамках той же задачи.
- При изменении существующей логики добавляйте или обновляйте соответствующие тесты.
- Если написание тестов не требуется (тривиальные правки, конфигурация, документация) - явно укажите причину.
- Предпочитайте unit-тесты для бизнес-логики; интеграционные - для API и взаимодействия с внешними системами.
- Не мокать то, что должно быть интеграционным: БД, очереди, файловую систему - если тест валидирует именно эту интеграцию.
- Если код не проходит тесты - спроси, можно ли обновить тесты под новый функционал, не правь тесты молча.
- Запускай тесты после изменений и на старте (обязательный прогон фазы RED, см. подраздел выше); не игнорируй падающие.
