# Браузер агента: серверный и пользовательский

У агента бывает две браузерные площадки, и они не взаимозаменяемы. Путать их дорого: симптомы отказа у них одинаковые ("страница не открывается"), а причины и лечение - разные.

| Площадка | Что это | Типичное имя MCP |
| --- | --- | --- |
| **Серверная** | headless Chrome на той же машине, где идет сессия агента | `chrome-devtools` |
| **Пользовательская** | обычный браузер на личной машине пользователя, доступный агенту через обратный туннель (порт CDP проброшен на сервер) | `chrome-local` |

Имена MCP-серверов конкретного устройства смотреть в его конфигурации - канон фиксирует различие, а не имена.

## Какую выбирать

**Дефолт - серверная.** Ее никто не трогает руками, ее не жалко уронить, она не мешает пользователю работать.

**Пользовательская нужна там, где важно, с какого устройства и адреса пришел запрос:**

- сайт привязывает сессию к устройству и IP (например LinkedIn): куки, унесенные на сервер, дают checkpoint или тихий разлогин;
- сайт режет трафик из дата-центров антиботом. Проверяется быстро: настоящий Chrome на сервере отдает страницу-заглушку ("похоже, нет соединения", "выключите VPN", номер инцидента), а с домашнего адреса та же страница открывается. Подмена user-agent тут не помогает - фильтр по адресу, а не по клиенту;
- нужен уже залогиненный аккаунт пользователя, а логин с сервера потребовал бы пароль или второй фактор.

Во всех остальных случаях - серверная.

## Агент поднимает и гасит пользовательский браузер сам

Держать чужой браузер открытым круглосуточно незачем, а просить пользователя каждый раз запускать его руками - лишний шаг. Поэтому в схеме есть управляющий канал: помимо порта CDP туннель пробрасывает SSH на машину пользователя, а ключ агента там ограничен forced command - выполняется только скрипт управления браузером, произвольные команды невозможны.

```bash
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 status     # stopped | running (CDP ok)
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 start      # headless, окна нет
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 start-gui  # с окном, когда нужно смотреть глазами
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 stop
```

Конкретные значения (`<CTL_PORT>`, `<CTL_KEY>`, `<MAC_USER>`) берутся из описания устройства, а не подбираются - см. следующий абзац; те же имена использует ранбук скилла.

**Прежде чем просить пользователя что-то запускать руками - проверить, нет ли на устройстве этого канала.** Ищется он в конфигурации проекта или в `~/.claude/CLAUDE.md` (там, где описаны инструменты машины): порт, ключ и чья это машина. Наличие ключа в `~/.ssh/` и слушающего порта - подсказка, где искать, но не доказательство: на сервере может стоять туннель к другому устройству, и `start`/`stop` вслепую управляли бы чужим браузером. Не нашел явного описания - спроси пользователя, а не угадывай по портам. Схема не развернута вовсе - см. скилл `agent-browser`.

**Что этот канал не защищает.** Forced command ограничивает только SSH; порт CDP аутентификации не имеет - кто дотянулся до него на сервере, тот читает куки профиля и действует в его залогиненных аккаунтах, не открывая ни одного окна. Отсюда прямое следствие: **в агентский профиль не логинят то, что дорого потерять** - банк, госуслуги, почту-восстановление. "Под присмотром через `start-gui`" тут не решение: человек видит свое окно, а параллельное чтение кук и действия в другой вкладке - нет. Нужен такой сайт - это работа человека в его обычном браузере, а не задача для агента.

## Гигиена

- **Не гасить браузер между задачами внутри одного сеанса работы.** Цикл "поднял - сделал - погасил" на каждую мелочь стоит сессий: при завершении Chrome сбрасывает куки на диск, и сбой этого сброса выбивает логин на сайтах с ротацией токена. Поднимать один раз, гасить в конце.
- **Гасить штатно, не убивать.** Команда `stop` дает браузеру время дописать куки. Вернулось "still running" - повторить `stop`, а не идти с `kill -9`.
- **На сервере не гасить Chrome по `pkill`.** Под управлением MCP там может быть браузер соседней сессии, а шаблон "chrome" вдобавок совпадает с процессами самого агента. Вкладки закрывать штатным `close_page`, процессы не трогать.
- **Профиль занят соседом.** Ошибка вида "browser is already running for <profile>" означает, что серверный Chrome держит другая сессия агента. Это не повод убивать чужой процесс: либо работать своим профилем и своим портом, либо уйти на пользовательскую площадку.

## Общий браузер - это гонка

В пользовательском браузере окно принадлежит человеку, и он в нем работает параллельно. Состояние страницы между двумя вызовами агента может измениться - активная вкладка переключится, форма перерисуется.

Поэтому **все необратимое делается одним вызовом скрипта**: проверка адресата, ввод текста, повторная проверка адресата, клик по кнопке отправки - в одной функции. Не совпало - прервать, не отправлять. Разнесенные по разным вызовам "вставил" и "нажал" - это гонка, а отправка необратима.

## Диагностика

| Симптом | Что это значит |
| --- | --- |
| Порт CDP слушается, но соединение сбрасывается (`connection reset by peer`) | Туннель жив, браузера на том конце нет. Поднять через управляющий канал |
| Порт CDP не слушается вовсе | Лег сам туннель - это чинится на машине пользователя, агент отсюда не поможет |
| Страница-заглушка антибота вместо контента | Фильтр по адресу. Уходить на пользовательскую площадку, подменять user-agent бессмысленно |
| `browser is already running for <profile>` | Серверный профиль занят соседней сессией (см. "Гигиена") |
| Логин на сайте слетел | Сессия живет в профиле агентского браузера; восстановление сессии и повторный вход - в скилле `agent-browser` |

Полная установка схемы на устройство (обратный туннель, скрипт управления, forced command, автозапуск, бэкап сессий) - скилл `agent-browser`.
