# Браузер агента: серверный, пользовательский и с домашним выходом

У агента бывает три браузерные площадки, и они не взаимозаменяемы. Путать их дорого: симптомы отказа у них одинаковые ("страница не открывается"), а причины и лечение - разные.

| Площадка | Что это | Типичное имя MCP |
| --- | --- | --- |
| **Серверная** | headless Chrome на той же машине, где идет сессия агента | `chrome-devtools` |
| **Пользовательская** | обычный браузер на личной машине пользователя, доступный агенту через обратный туннель (порт CDP проброшен на сервер) | `chrome-local` |
| **Серверная с домашним выходом** | тот же серверный Chrome, но в сеть ходит через прокси на домашней машине: порт прокси проброшен тем же обратным туннелем, браузер стартует с `--proxy-server` | своего MCP не требует - это та же серверная площадка |

Имена MCP-серверов конкретного устройства смотреть в его конфигурации - канон фиксирует различие, а не имена.

**Площадка и маршрут - две разные оси.** Первые две строки таблицы отвечают на вопрос "чей браузер", третья - "чьим адресом он выходит". Третья площадка существует потому, что чаще нужен не компьютер пользователя, а только его адрес: домашняя машина тогда держит легкий прокси-клиент вместо браузера - дешевле по памяти и не зависит от того, разбужен ли ноутбук.

**Маршрут задается при запуске процесса.** Поднятому браузеру прокси не сменить, поэтому выбор маршрута - параметр запуска площадки, а не отдельного вызова агента. Решать надо до `start`, а не после.

## Какую выбирать

**Дефолт - серверная.** Ее никто не трогает руками, ее не жалко уронить, она не мешает пользователю работать.

**Пользовательская нужна там, где важен сам компьютер человека:**

- нужен уже залогиненный профиль пользователя, а логин с сервера потребовал бы пароль или второй фактор;
- нужно ручное подтверждение глазами и руками через окно (`start-gui`);
- сайт привязывает сессию к устройству: куки, унесенные на сервер, дают checkpoint или тихий разлогин.

**Домашний выход нужен там, где важен только адрес** - сайт режет трафик из дата-центров. Браузер при этом остается серверным со своим профилем, и компьютер пользователя занимать незачем.

Во всех остальных случаях - серверная.

### Сайт не отдает контент: от простого к сложному

Домашний маршрут удлиняет цепочку и добавляет точку отказа, поэтому он эскалация, а не первый ход. Порядок ровно такой:

1. **С той же машины повторить запрос с браузерным User-Agent.** Помогло - на этом все: фильтр по клиенту, лишние звенья не нужны.
2. **Не помогло - повторить с другого адреса** (домашний узел, другая нода). Помогло - фильтр по адресу, вот тут домашний маршрут оправдан.
3. **Не помогло ни то, ни другое** - смотреть глубже: TLS-отпечаток, антибот, нужен настоящий браузер с профилем.

Прецедент: сайт отдавал 403 и с адреса дата-центра, и с домашнего адреса провайдера, а с браузерным UA - 200 отовсюду. Правило "не открылось из дата-центра - строй домашний маршрут" построило бы здесь туннель впустую; обратная крайность ("всегда хватает заголовка") промахнется там, где фильтр действительно по адресу. Два запроса различают эти случаи заранее и стоят секунд.

Практическое следствие: **скрипт, ходящий `curl`-ом, а не браузером, по умолчанию шлет небраузерный UA** - и получает отказ там, где браузер проходит. Если задача сводится к чтению страницы, дешевле открыть ее площадкой, чем чинить заголовки.

### Живой CDP не значит нужный маршрут

`status` отвечает за процесс и порт отладки - про адрес выхода он не знает ничего. На площадке, где маршрут задуман через прокси, проверяется именно выход: открыть эхо-сервис адреса и сверить с ожидаемым ("должно быть <страна/провайдер>").

Проверять после каждого из трех событий, они наступают независимо: перезапуск браузера (маршрут задается флагом при старте - забыли флаг, и процесс поднялся мимо прокси), перезапуск туннеля (порт прокси мог не подняться, тогда флаг указывает в никуда) и перезапуск самого прокси-клиента на домашней машине.

Эхо-сервис держать **один на проект** и записать его в конфигурацию устройства: разные сервисы по-разному сообщают страну и провайдера, и прогоны перестают быть сравнимыми. Годится любой, отдающий чистый адрес текстом (`icanhazip.com`, `api.ipify.org`); сверять надо не только через браузер, но при подозрении и напрямую через прокси (`curl -x`) - расхождение между ними и означает, что флаг до браузера не доехал.

Это секунды; без такой проверки схема выглядит рабочей, будучи настроенной наполовину - браузер жив, CDP отвечает, а трафик идет мимо прокси.

## Агент поднимает и гасит пользовательский браузер сам

Держать чужой браузер открытым круглосуточно незачем, а просить пользователя каждый раз запускать его руками - лишний шаг. Поэтому в схеме есть управляющий канал: помимо порта CDP туннель пробрасывает SSH на машину пользователя, а ключ агента там ограничен forced command - выполняется только скрипт управления браузером, произвольные команды невозможны.

```bash
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 status     # stopped | running (CDP ok)
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 start      # headless, окна нет
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 start-gui  # с окном, когда нужно смотреть глазами
ssh -p <CTL_PORT> -i ~/.ssh/<CTL_KEY> <MAC_USER>@127.0.0.1 stop
```

Конкретные значения (`<CTL_PORT>`, `<CTL_KEY>`, `<MAC_USER>`) берутся из описания устройства, а не подбираются - см. следующий абзац; те же имена использует ранбук скилла.

**Прежде чем просить пользователя что-то запускать руками - проверить, нет ли на устройстве этого канала.** Ищется он в конфигурации проекта или в `~/.claude/CLAUDE.md` (там, где описаны инструменты машины): порт, ключ и чья это машина. Наличие ключа в `~/.ssh/` и слушающего порта - подсказка, где искать, но не доказательство: на сервере может стоять туннель к другому устройству, и `start`/`stop` вслепую управляли бы чужим браузером. Не нашел явного описания - спроси пользователя, а не угадывай по портам. Схема не развернута вовсе - см. скилл `agent-browser`.

**Что этот канал не защищает.** Forced command ограничивает только SSH; порт CDP аутентификации не имеет - кто дотянулся до него на сервере, тот читает куки профиля и действует в его залогиненных аккаунтах, не открывая ни одного окна. Отсюда прямое следствие: **в агентский профиль не логинят то, что дорого потерять** - банк, госуслуги, почту-восстановление. "Под присмотром через `start-gui`" тут не решение: человек видит свое окно, а параллельное чтение кук и действия в другой вкладке - нет. Нужен такой сайт - это работа человека в его обычном браузере, а не задача для агента.

## Гигиена

- **Не гасить браузер между задачами внутри одного сеанса работы.** Цикл "поднял - сделал - погасил" на каждую мелочь стоит сессий: при завершении Chrome сбрасывает куки на диск, и сбой этого сброса выбивает логин на сайтах с ротацией токена. Поднимать один раз, гасить в конце.
- **Освобождая пользовательский браузер, не закрывай последнюю вкладку.** Освобождение - это уборка вкладок в работающем браузере, когда его забирает человек или другая сессия, а не штатное гашение `stop` из пункта выше. Chrome без единой вкладки завершается, и "я убрал за собой" превращается в "я выключил браузер пользователя": восстановление из сессии не гарантировано даже при наличии `start` в управляющем канале (в прецеденте поднимать пришлось человеку), а гибель браузера посреди работы человека - ущерб сам по себе. Правильно - увести свою вкладку на `about:blank` или закрыть все свои, кроме одной. Симптом промаха - `ECONNRESET` на CDP при живом порте туннеля. Серверной площадки не касается: там вкладку можно поднять самому.
- **Гасить штатно, не убивать.** Команда `stop` дает браузеру время дописать куки. Вернулось "still running" - повторить `stop`, а не идти с `kill -9`.
- **На сервере не гасить Chrome по `pkill`.** Под управлением MCP там может быть браузер соседней сессии, а шаблон "chrome" вдобавок совпадает с процессами самого агента. Вкладки закрывать штатным `close_page`, процессы не трогать.
- **Профиль занят соседом.** Ошибка вида "browser is already running for <profile>" означает, что серверный Chrome держит другая сессия агента. Это не повод убивать чужой процесс: либо работать своим профилем и своим портом, либо уйти на пользовательскую площадку.
- **Свой инстанс на сессию.** Чтобы предыдущий пункт не возникал вовсе, параллельные сессии разводятся по **профилю и порту отладки** (`--user-data-dir=<...>-<метка>`, свой порт) - тогда они не ждут друг друга и не делят куки. На **серверной** площадке это доступно сразу: браузер поднимает сам агент, профиль и порт - его выбор. На **пользовательской** так с ходу не выйдет: `chrome-ctl` из ранбуков держит порт и профиль константами, а имя инстанса ему не передать - он намеренно берет из команды только первое слово (`cmd="${raw%% *}"`), и это защита от дописанных команд через forced command, которую нельзя ослаблять ради удобства. Нужны параллельные сессии на чужой машине - заводится второй инстанс со своим ключом, своей строкой forced command и своей парой портов, как вторая машина в ранбуке.

  Граница, которую важно назвать: разведение касается **браузеров**, а не **аккаунтов**. Для сайта два профиля выглядят двумя устройствами, и живой залогиненный аккаунт остается в одном из них. Перенос сессии копированием кук в другой профиль сайт может аннулировать (наблюдалось на LinkedIn: после переноса токен перестал действовать и потребовался ручной вход).
- **Площадка под задачи с логином поднимается с TCP-портом отладки.** Браузер, запущенный с `--remote-debugging-pipe`, TCP-порта не имеет, и залить в него куки нечем - восстановление сессии становится невозможным в принципе. Порт - на loopback.
- **Дамп кук снимать только с проверенно живой сессии.** Прогон с разлогиненным профилем штатно затирает рабочий бэкап гостевыми куками, и восстанавливать становится нечем (поймано на трех пустых прогонах подряд). Признак пригодности дампа - наличие сессионной куки сайта; предыдущую версию бэкапа держать рядом.

## Общий браузер - это гонка

В пользовательском браузере окно принадлежит человеку, и он в нем работает параллельно. Состояние страницы между двумя вызовами агента может измениться - активная вкладка переключится, форма перерисуется.

Поэтому **все необратимое делается одним вызовом скрипта**: проверка адресата, ввод текста, повторная проверка адресата, клик по кнопке отправки - в одной функции. Не совпало - прервать, не отправлять. Разнесенные по разным вызовам "вставил" и "нажал" - это гонка, а отправка необратима.

## Диагностика

| Симптом | Что это значит |
| --- | --- |
| Порт CDP слушается, но соединение сбрасывается (`connection reset by peer`) | Туннель жив, браузера на том конце нет. Поднять через управляющий канал |
| Порт CDP не слушается вовсе | Лег сам туннель - это чинится на машине пользователя, агент отсюда не поможет |
| Страница-заглушка антибота вместо контента | Похоже на фильтр по адресу, но сперва проверить UA - см. "Сайт не отдает контент" |
| 403 у `curl`, но страница открывается браузером | Фильтр по User-Agent, а не по адресу. Открывать площадкой, не подбирать заголовки |
| `about:blank` на конкретном домене, соседние сайты живы | Домен заблокирован на маршруте. Смотреть выход, а не браузер |
| Эхо-сервис показывает не тот адрес, что задуман | Прокси не подключен к браузеру: нет флага при запуске либо перехват не работает |
| `browser is already running for <profile>` | Серверный профиль занят соседней сессией (см. "Гигиена") |
| Сайт просит пароль после переноса кук на другую площадку | Сессия привязана к устройству; нужен ручной вход там, где будет работа |
| Логин на сайте слетел | Сессия живет в профиле агентского браузера; восстановление сессии и повторный вход - в скилле `agent-browser` |

Полная установка схемы на устройство (обратный туннель, скрипт управления, forced command, автозапуск, бэкап сессий) - скилл `agent-browser`.
