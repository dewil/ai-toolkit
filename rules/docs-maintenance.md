# Актуальность документации

## README.md - человеческий манифест, CLAUDE.md - агентский контекст

Проект держит два верхнеуровневых документа с разными аудиториями. Не смешивайте:

- **`README.md`** (в корне проекта) - человеческий манифест: что за проект, зачем, как устроен, как работать. Его читают люди (и GitHub, если репозиторий публичный). Пишите человеческим языком, без служебных @-импортов и агентских инструкций.
- **`CLAUDE.md`** (в корне проекта) - агентский контекст: @-импорты правил, служебные заметки для Claude. `CLAUDE.md` импортирует README (`@README.md`), поэтому человеческое описание тоже попадает Claude в контекст - дублировать его в CLAUDE.md не нужно.

Правило: меняете человеческое описание проекта (цель, устройство, процессы) - правьте `README.md`; меняете поведение Claude, правила, @-импорты - правьте `CLAUDE.md`. Новое человеческое описание не кладите в CLAUDE.md, и наоборот.

## Обезличивание ранбуков и шаблонных доков

Операционный документ (runbook, инструкция по эксплуатации), который шарится наружу или задуман как шаблон под класс систем, обезличивайте:

- Реальные адреса, ключи, токены, имена хостов и людей заменяйте на `<ПЛЕЙСХОЛДЕР>` в угловых скобках. Секретам в тексте документа не место - в файле только заглушка, реальное значение живет в секретах.
- В конце документа - таблица подстановки: `заглушка | что это | пример`. По ней читатель подставляет свои значения.
- Тяжелую систему разбивайте на пару: **explainer** ("как устроено" - архитектура, принципы) и **runbook** ("что делать сейчас" - чеклисты, инциденты, эскалация). Разделяйте по аудитории и задаче так же строго, как README и CLAUDE.md выше, и давайте явную навигацию между ними (что читать первым).

## Общие правила

- Поддерживайте документацию в актуальном состоянии при изменении поведения, команд, моделей данных, конфигурации, структуры файлов или процессов.
- Обновляйте релевантную документацию в рамках той же задачи, где внесены изменения.
- Если обновление документации не требуется, явно указывайте причину.
- Предпочитайте короткие и конкретные правки в существующих документах перед созданием новых файлов.
- Держи актуальной карту структуры проекта - файл `project-structure.md` в корне.
- Постоянная документация лежит в `docs/`.
- Рабочие заметки (тудушки, аудиты, отчеты, диагностика, черновики) кладутся в `docs/dev/`. Эта подпапка только для локальной работы и в production-деплой включаться не должна.
