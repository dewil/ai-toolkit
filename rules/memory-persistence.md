# Проактивная персистентность памяти

Durable-факт, всплывший по ходу работы, сохраняй в общую память **в момент появления** - не дожидаясь конца сессии и не дожидаясь явной просьбы. Смысл правила - проактивность: не дать дорогому знанию испариться, когда контекст сессии обрывается (компакт, новое устройство, следующий день). Формат общей файловой памяти: один подтвержденный durable-факт = один файл с понятным описанием + строка со ссылкой в MEMORY.md. Критерии сохранения приведены ниже. В проекте с `.AI/project.json` общий источник - `.AI/memory/`: читай `MEMORY.md` и релевантные файлы напрямую, записывай факт отдельным файлом и добавляй строку в индекс. Нативная автопамять не считается подключенной без проверки новой сессией. В legacy-проекте используй уже настроенную память.

## 1. Сохранять вовремя, без напоминания

Как только всплыл факт, который переживет сессию и дорого восстановить - решение и почему, неочевидное ограничение, поправка пользователя, указатель на внешний ресурс, состояние проекта - фиксируй сразу. Не откладывай "на потом" и не жди просьбы "запомни": к концу сессии контекст может быть уже срезан.

## 2. Память - не свалка контекста задачи

Не путай два разных "не потерять":

- **durable-факт, переживающий сессию** -> общая память.
- **прогресс текущей задачи** (шаги, сделанное, оставшееся) -> Markdown-файл задачи, НЕ память. В `.AI`-проекте создай или найди его до работы в проектном бэклоге (`docs/backlog/` по умолчанию); сохраняй ID, цель, ограничения, сделанное, проверки, блокеры и следующий шаг сразу при изменениях. После критериев готовности перенеси в `docs/done/` с тем же ID. Todo-инструмент может дополнять файл, но не заменяет его.

Проактивность не означает "сваливай в память все подряд": эфемерное состояние диалога, то что уже фиксирует репозиторий/git, и легко выводимое заново - не сохраняй. Секреты - только заглушкой (см. `rules/secrets-handling.md`).

## Описание записи - это поисковый запрос, а не заголовок

Поле `description` в шапке записи - однострочное описание для оценки релевантности при поиске. Там, где на устройстве поднят машинный поиск по памяти, у него появляется вторая роль: **описание идет в эмбеддинг вместе с телом** и, будучи самой плотной формулировкой факта, заметно тянет попадание.

Практическое следствие: пиши его как **ответ на вопрос, по которому запись будут искать**, а не как название папки. "Публичные контакты dwl для внешних площадок" находится, "Контакты" - нет. Разница ничего не стоит в момент записи и не восстанавливается потом: переписывать описания задним числом по всей памяти никто не станет.

Это не отменяет требований выше - что сохранять и когда - и не зависит от того, есть ли поиск на конкретной машине: осмысленное описание одинаково полезно и человеку, читающему индекс глазами.
