# Проактивная персистентность памяти

Решение с причиной, неочевидное ограничение, поправка, внешний указатель или состояние проекта, которое переживет сессию и дорого восстановить, сохраняй сразу. В `.AI`-проекте общий файловый источник — `.AI/memory/`: один подтвержденный факт на файл и ссылка в `MEMORY.md`. Для новой записи используй helper:

```bash
python3 scripts/memory-write.py --root "$PROJECT_ROOT" --name short-id \
  --description "По какому вопросу искать этот факт" < fact-body.txt
```

В stdin передавай только тело факта; helper создает frontmatter и ссылку. Он принимает короткий ASCII ID, требует существующие `.AI/project.json` и `MEMORY.md`, работает на Linux с `flock` и сериализует cooperative helper-записи на одном хосте. Ручные редакторы, Syncthing и удаленные файловые системы блокировке не подчиняются. Существующие факты не меняй helper'ом; редактирование и уплотнение выполняй отдельно, без конкурентных писателей. В legacy-проекте используй уже настроенную память.

## Что сохранять

Эфемерный контекст, сведения, уже зафиксированные в git, и легко выводимое заново не сохраняй. Секреты записывай только заглушкой (`rules/secrets-handling.md`).

Прогресс задачи (цель, ограничения, сделанное, проверки, блокеры, следующий шаг) веди в одном Markdown-владельце в `docs/backlog/`; до работы найди или создай его, после готовности перенеси в `docs/done/` с тем же ID. Todo-инструмент файл не заменяет.

## Описание и подключение

`description` — обязательное однострочное описание и поисковый запрос: формулируй ответ на вопрос, по которому будут искать («Публичные контакты dwl для внешних площадок», не «Контакты»). При машинном поиске описание входит в эмбеддинг вместе с телом и помогает читать индекс.

Нативная автопамять не считается подключенной без проверки в новой сессии. `.AI/memory/` остается общим файловым источником; глобальную нативную память подключают отдельно. До проверки адаптера читай и записывай файловую память явно.
