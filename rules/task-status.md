# Файловый статус задачи

У каждой задачи один Markdown-владелец в `docs/backlog/`; после приемки перенеси его в `docs/done/` с прежним ID. Ключ обзора — `project_id` из `.AI/project.json` и ID задачи. Название проекта, путь сессии и модель не заменяют эту идентичность.

Новую задачу оформляй в формате v1 ниже. Статус и назначения обновляй при смене этапа, исполнителя, блокера или следующего шага. Человеческое тело сохраняет цель, ограничения, сделанное, проверки, блокеры и следующий шаг; metadata позволяет собрать обзор без толкования прозы. Единственные канонические `id` и `status` находятся в frontmatter. Другие проектные поля, например priority, сохраняются.

Старые Markdown/YAML и JSON без `ai_task` остаются неподключенными. Обзор показывает имя/путь и доступный ID, не угадывает этап и не переписывает файл. Подключение старой задачи выполняет отдельно ее текущий владелец, сохраняя все поля, ID и тело. Массовая автоконвертация запрещена.

## Создание и обновление

Между строками `---` запиши строгий JSON-объект. Это допустимый YAML, но читателю достаточно стандартной библиотеки Python. Повторные ключи запрещены. Поля `ai_task` обязательны; неизвестное поле или версия дают диагностику. Пример новой задачи:

```markdown
---
{
  "id": "TASK-EXAMPLE",
  "status": "queued",
  "ai_task": {
    "schema_version": 1,
    "phase": "queue",
    "owner": "coordinator",
    "assignments": [],
    "updated_at": "2026-10-15T09:00:00Z",
    "updated_by": "coordinator",
    "next_step": {"action": "Уточнить требования", "actor": "coordinator"},
    "blocker": null,
    "handoff": null,
    "excluded_phases": [],
    "evidence": []
  }
}
---
# Название задачи

Цель, ограничения, результаты и проверки.
```

`owner` и `updated_by` — непустые идентичности текущего писателя; при обычном обновлении они совпадают. `updated_at` — фактическое время записи ISO8601 с часовым поясом. `mtime` и возраст чата не заменяют его. Возраст записи не доказывает активность процесса; порог устаревания задается отдельно.

Фазы SDD: `queue`, `requirements`, `domain_audit`, `spec`, `criteria`, `implementation`, `review`, `checks`, `release`, `rollout`, `acceptance`, `done`. Metadata фиксирует текущий этап, а применимость и обязательность проверок задает принятый процесс [SDD](sdd-pipeline.md). Не выводи разрешение пропуска из одного поля.

| status | phase | Каталог и условие |
| --- | --- | --- |
| `queued` | Любая кроме `done` | backlog; следующий этап еще не начат |
| `in_progress`, `waiting_user`, `blocked`, `paused` | Любая кроме `queue`/`done` | backlog; ожидание сохраняет текущий этап |
| `done` | `done` | done; критерии приняты |
| `cancelled` | `done` | done; основание в `blocker.reason`, отмена не означает PASS |

`blocker` — null либо `{"reason":"Причина","actor":"user"}`; actor необязателен. Для `waiting_user`, `blocked`, `cancelled` причина обязательна. `next_step` — объект с непустыми action/actor; только done/cancelled допускают null. Actor указывает назначение, явно названного координатора или пользователя; если исполнитель неизвестен, запиши `unassigned`.

## Исполнители и доказательства

Назначения хранятся в массиве `assignments`. Каждый запуск имеет уникальный внутри задачи id, даже при повторе роли:

```json
{"id":"review-1","role":"reviewer","phase":"review","state":"queued","provider":"codex","model":null,"model_evidence":null,"binding":null}
```

Все восемь полей обязательны. role/provider — непустые строки; phase — из списка фаз. state: `queued`, `in_progress`, `waiting_user`, `blocked`, `paused`, `finished`, `failed`, `cancelled`, `unknown`. `finished` завершает запуск, а не задачу. owner ссылается на назначение либо явно названного координатора. Модель неизвестна — model/model_evidence null; заявленная строка модели без источника запуска не считается подтверждением.

`binding` — null либо `{"kind":"codex_session","sid":"00000000-0000-4000-8000-000000000001"}`. Другой kind остается неподключенной заявленной связью. Context/route/root/generation не принимаются из файла как доверенные данные. Публичный reader не читает native activity: observation остается unknown. Control проверяет доступ и идентичность источника отдельно; совпадение sid само не доказывает работу над задачей.

`excluded_phases` — массив объектов `{"phase":"domain_audit","reason":"Причина","decision_ref":"docs/decision.md"}`. Фазы не повторяются; сохраняй ссылку на принятое решение. Пустой массив означает отсутствие заявленных исключений. Само объявление исключения не разрешает пропуск обязательного этапа.

`evidence` — массив объектов с обязательными type/result/ref, где result: `pass`, `fail`, `notrun`, `unknown`. Необязательные поля: revision (заявленная ревизия), hashes (массив `{"path":"docs/checks.txt","sha256":"64 hex символа"}`), verifier (`{"model":null,"model_evidence":null}`). Сохраняй точную ревизию/хеши, отчет и источник модели проверяющего, когда этого требует процесс. Разные строки model сами по себе не доказывают независимость.

Reader сверяет только локальный SHA256 безопасных относительных файлов; Git-ревизия без доверенного источника остается unknown. Совпадение хеша подтверждает байты, а не смысл PASS. Внешние ссылки остаются заявленными указателями; абсолютные, скрытые, запрещенные пути и symlinks не читаются. Доказательства обязательных критериев оценивает владелец по процессу; обзор не объявляет приемку и не разрешает выпуск.

## Один писатель и передача

Общие поля, назначения и тело изменяет один текущий владелец. Субагенты возвращают результаты ему. Разные строки одного файла не изолируют писателей. Передача выполняется последовательно:

1. Прежний владелец сохраняет актуальное состояние и `handoff: {"to":"next-owner","at":"2026-10-15T10:00:00Z","reason":"Причина передачи"}`, затем прекращает запись. Все три значения непустые; at требует часовой пояс.
2. Новый владелец читает свежий файл, устанавливает `owner = updated_by = handoff.to`, очищает handoff до null и фиксирует прием в человеческом теле перед продолжением. Обновляет время и следующий шаг.

Ненулевой handoff при owner, отличном от to, означает ожидающую передачу. Совпадение owner/to при неочищенном handoff — несогласованность. `next_step.actor` определяет следующего исполнителя и не передает владение. Атомарная замена файла дает целую редакцию читателю, но не гарантирует блокировку между хостами/Syncthing. Конфликтующие редакции сохраняй и разбирай явно; обзор не выбирает победителя.

## Чтение и информирование

`python3 scripts/task-overview.py --root /path/to/client [--root /path/to/other] [--json]` дает один производный снимок без Control. API для встраивания: `read_snapshot(roots, *, now=None)`. Читаются только `.AI/project.json` и непосредственные Markdown-файлы backlog/done; evidence читается лишь для заявленных хешей. Реестр, сообщения, память, настройки и subprocess не используются.

Пределы: 64 корня, 2000 файлов на корень, 1MiB на файл, 32 evidence-файла на задачу, 1MiB на evidence-файл и 32MiB совокупного чтения. Диагностика сохраняет здоровые источники и дает coverage=partial/exit3; чистый снимок — complete/exit0; неверные аргументы — exit2. Дубли ID, неизвестный формат, битые данные и несогласованность каталога/статуса видны явно. Старые задачи остаются диагностическими строками.

В текущем разрешенном чате кратко сообщай назначение, смену этапа, блокер и завершение: задача, агент/модель, этап и следующий шаг. Эти сообщения не являются приемкой пользователя и не разрешают внешнюю рассылку.
